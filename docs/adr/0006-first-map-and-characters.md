# ADR 0006 — First real map and characters (M5)

**Status:** Accepted (task files merged to `m5-map-characters`, 2026-10-31). Amended by **E0** (wave-0 rulings, 2026-10-31), **E1** (review of tasks 08–10, 2026-10-31, `docs/adr/reviews/0006-cosmetics-review.md`), **E2** (dwell rule, 2026-10-31) and **E3** (DM1 bands, link demand, §3 deviations, art-pass gate, 2026-11-01, `docs/adr/reviews/0006-06b-review.md`), see Amendments.
**Scope:** everything `dev`/`dev-hard` need to turn the greybox-only project (M0–M4 on `main` at 3fcd1bc: six weapons, items, FFA/Duel, bots on `L_ItemTest`) into ROADMAP M5: one polished Duel/FFA map with baked lighting, one rigged character with 4+ bright skins, weapon world and view models, and the audio pass — without a GPU on the build host and without a playtest machine until the Apple Silicon Mac arrives. Amendments to this ADR are numbered **E1, E2, …** (ADR 0002 uses A, 0003 B, 0004 C, 0005 D).

## Context

Facts established before writing (probed on this host, 2026-10-31; see also `docs/machine.md`):

- **Build host:** headless Debian VM, 16 vCPU, 30 GB RAM, no GPU (`QEMU stdvga`), UE 5.8.4 installed build at `/opt/UnrealEngine-5.8` with Templates/FeaturePacks/Samples trimmed. Everything runs `-nullrhi`. Disk: 21 GB free of 125 GB; the project rule is ≥ 15 GB free. All content so far is generated by `Tools/editor/create_*.py` through the `pythonscript` commandlet (83 LFS files, 1.3 MB).
- **Lighting tooling present on the VM:** `Engine/Binaries/Linux/UnrealLightmass` and `libUnrealEditor-SwarmInterface.so` with the Linux/Mac *local* Swarm implementation (`Engine/Source/Editor/SwarmInterface/Private/SwarmInterfaceLocal.cpp`: the editor spawns `UnrealLightmass` as a child process; no .NET Swarm Agent is needed). `UResavePackagesCommandlet` in 5.8 has the `-BuildLighting` path (the string "No maps found to save when building lighting" is in `libUnrealEditor-UnrealEd.so`) and refuses to run without `-AllowCommandletRendering`, i.e. it needs a working RHI to export material samples to Lightmass. The host has Mesa's software Vulkan device (`vulkaninfo --summary`: llvmpipe, Vulkan 1.4, `/usr/share/vulkan/icd.d/lvp_icd.json`) — a CPU rasteriser that UE's Vulkan RHI may accept. **GPU Lightmass is not installed** (`Engine/Plugins/Experimental/GPULightmass` absent) and would need hardware ray tracing; it is out.
- **Blender is not installed** on the VM (`which blender` empty, no `bpy`); no PIL/numpy either; `ffmpeg` and `python3` 3.13 exist. The UE FBX SDK (`Engine/Binaries/ThirdParty/FBX`) and the Interchange plugins are present, so FBX import runs headless.
- **Visual verification** happens only on the human's Apple Silicon Mac (STATUS question 26), not yet available. The Intel Mac compiles and runs the automation suite but cannot render UE 5.8.
- **Engine-side state relevant to art:** `AVeloxCharacter` has the `ACharacter` `Mesh` (unused skeletal mesh component) with a `PlaceholderBody` capsule mesh attached and `M_PlayerBody` tinted from `AVeloxPlayerState::PlayerColorIndex` (8-colour palette). `AVeloxPickup` renders a `Placeholder` static mesh. Weapons have cue tags (`FireCueTag`, `ImpactCueTag`, `BeamCueTag`) handled natively by `UVeloxCombatFeedbackComponent::HandleCue` — no meshes, particles or sounds exist. Audio: only `SC_Master/SC_Effects/SC_Music` and `SM_Default`; `UVeloxGameUserSettings` has the volume sliders. Hitboxes are **one rewound capsule** (37.5 × 70, crouched 50; ADR 0003 §6 (c)); ADR 0003 deferred per-bone hitboxes to "when a mesh exists".
- **Map conventions already in force** (ADR 0005 §3, §4, D1, D17, D32, D41, D49; tasks 07f/04j; question 25): one `NavMeshBoundsVolume` per map, `AgentRadius 45` / `AgentHeight 140` / step 45 / slope 45.5°, walkable widths ≥ 120 cm, every pad/drop/gap/rocket-jump gets an `AVeloxNavLink`, D41's "walkable floor carries nav or is sealed" rule, `KillZ −1000` and hidden clip walls/ceiling so knockback cannot leave the arena, no `left_arena`/`world_kill` rounds. The **nav-coverage lint** was deferred to "before M5" and is owed here.
- **Soak evidence base:** `infra/ci/nettest.sh` runs `BotRun`/`BotDuel` on `L_ItemTest` with hard-coded map URLs; `infra/ci/ffa.sh` runs the D36 ten-run FFA set; the D51 bands (BotRun Σ kills ≥ 20, BotDuel Σ frags ≥ 20 and Σ camp episodes ≥ 7, FFA Σ kills ≥ 74, Mega returns ≥ 1 within 3 s and ≥ 2 within 10 s) are calibrated on `L_ItemTest`'s geometry and item layout.

Constraints from CLAUDE.md that bind every decision below: movement feel first (collision geometry must stay simple), high stable frame rate and readability over fidelity (forward renderer, MSAA, baked lighting, no Nanite/Lumen — ADR 0001), bots must play the real map with the same movement component, Git LFS for binaries, C++ for anything performance- or network-relevant.

### 2. Map production pipeline: one layout table, three outputs

**The layout table is the single source of truth.** `Tools/editor/maps/dm1_layout.py` is a declarative Python module: lists of `Room`, `Box`, `Ramp`, `Stairs`, `Door`, `Pad`, `Item`, `Spawn`, `Link`, `Light`, `Clip` records in centimetres on a **100 cm grid** with a **400 cm kit module**. `create_dm1_map.py --mode blockout` writes `L_DM1_Blockout` (greybox: `/Engine/BasicShapes` with `M_Greybox_*`, exactly like the test maps); `--mode art` writes `L_DM1` from the same table, replacing each greybox box by kit instances and keeping the boxes as **invisible clip geometry**. Both modes place the same pickups, pads, spawns, nav bounds, nav links, KillZ and clip ceiling, so the gameplay of `L_DM1` equals the gameplay of `L_DM1_Blockout` by construction; `audit_map.py --diff-collision L_DM1_Blockout L_DM1` asserts it (same blocking boxes, same actors of the gameplay classes, same transforms within 1 cm).

**Collision is clip-first (the Q3 way).** Pawns, projectiles, nav generation and the `Weapon` trace channel collide with the blockout boxes (`Clip_*` actors: `BlockAll`, `bHiddenInGame`, `CanEverAffectNavigation = true`, kinds `floor`/`platform`/`wall`/`ramp`/`stairs` as in `create_item_test_map.py`). Kit meshes are **`NoCollision`** and visual only. Consequences we want: the movement feel of the blockout survives the art pass unchanged (no lip catches on trims, no ramp seams), bots see the identical nav mesh, and the art pass can never regress a soak. Trims and decorations may protrude from the clip surface only where no pawn can touch them (above 250 cm or inside walls); the audit flags any kit instance whose bounds poke more than 5 cm into walkable space. Weapon impacts land on the clip surface, which is flush with the visual surface within 1 cm, so decals and impact cues look right.

**Steps and gates** (tasks in §11):

1. *Blockout* (`L_DM1_Blockout`) — generated, nav-linted (§6), paths between every item pair verified headless (`velox.bots.DumpNav`), reachability FT green.
2. *Bot iteration* — report-only soaks (BotRun ×3, BotDuel ×3, FFA ×10) on the blockout; layout fixes until the map-independent invariants hold (§7); then an architect ruling fixes the DM1 bands (`infra/ci/bands/L_DM1.sh`).
3. *Kit* — Blender script generates the modular pieces with lightmap UVs; imported headless; materials by script.
4. *Art pass* (`L_DM1`) — `--mode art`; lights from the `Light` records; reflection captures; audit budgets (§8); the same soak set must PASS with the DM1 bands.
5. *Lighting bake* (§5) and the performance audit; `L_DM1` added to `MapsToCook`; `ServerDefaultMap` switches to `L_DM1` on acceptance.
6. *Human playtest* on the Apple Silicon Mac (`docs/playtests/m5-map-characters-checklist.md`).

The shared helpers (`box`, `ramp`, `stairs`, `nav_bounds`, `nav_link`, `pad`, `pickup`, `spawn`, `clip_walls`, `kill_z`, `assert_counts`, `static_sun_and_sky`) move from the three test-map scripts into `Tools/editor/veloxmap.py`; the test maps regenerate with unchanged actor counts and soak results (task 02). Everything the generators place carries an actor tag naming its layout record (`Layout:<id>`) so lint and audit output speaks the layout's language.

### 3. DM1 design: a q3dm6-class two-atrium Duel/FFA map

**Class and size.** Enclosed, three-level, two atriums joined by a long north lane and a two-storey south hall, with a central tower; footprint **64 × 44 m**, level step **320 cm**, 4–6 players (Duel first). *Not* a q3dm17 space map: void maps need bots that reason about falling, punish FFA newcomers and showcase a single mechanic; a q3dm6/q3tourney-class map exercises strafe lanes, pads, drops, a rocket-jump shortcut and item timing all at once, and it is what the bots were tuned on (`L_ItemTest` is a miniature of this class). No teleporters (none exist in code; M7). No pits or lava (no out-of-arena ever; `KillZ −1000` only as a safety net).

**Rooms and connections** (coordinates are the layout's job; the graph and the rules are binding):

| Id | Room | Levels | Items | Exits |
|---|---|---|---|---|
| A | Mega Hall (west atrium, 16 × 14 m, 8 m high) | 0, +320 ledge | **Mega** on the ledge; PG lower; 2 × 25 HP lower; 3 shards along the ramp; cells ammo | lower → C, lower → D, ramp (15°) to the ledge, pad lower → ledge, ledge bridge → E mid |
| B | RA Yard (east atrium, 16 × 14 m, 8 m high) | 0, +320 balcony | **RA** on the balcony; SG lower; 2 × 25 HP; 3 shards; shells ammo | lower → C, lower → D, stairs (20 cm risers) to the balcony on both sides, pad lower → balcony, balcony bridge → E mid |
| C | North Lane (28 × 6 m, 4 m high) | 0 (+80 step at mid) | **LG** at mid on the step; **YA-north** 8 m east of the LG; 4 × 5 HP west end; lightning ammo east end | A lower, B lower, two 3 m doors south into E ground |
| D | South Hall (28 × 10 m, two storeys) | 0, +320 balcony along the south wall | **RL** lower centre; **YA-south** on the balcony centre; rockets ammo lower west; 50 HP lower east; 4 × 5 HP on the balcony | A lower, B lower, stairs at both ends up to the balcony, balcony → A ledge and → B balcony, pad from D lower → E top (the RG pad) |
| E | Rail Tower (centre, 12 × 12 m) | 0, +320 mid, +640 top | **RG** on top; 25 HP mid; slugs ammo ground; **Quad** (FFA only) ground centre | ground doors to C (2) and D (1), mid bridges to the A ledge and the B balcony, top reached only by the D pad or a rocket jump from the mid bridges; drops from every edge |

**Flow rules (binding for the layout; checked by the audit where it can be):**

- Every room has ≥ 2 exits; rooms holding a major item (A, B, E top) have ≥ 3 ways in/out counting drops. No dead ends.
- Two independent cycles pass both Mega and RA (upper ring A ledge → E mid → B balcony → D balcony → A ledge; lower ring A → C → B → D → A). Mega → RA path distance on the upper ring ≈ 45–50 m (≈ 6 s at run speed, ≈ 4 s strafing) — the q3dm6 cadence.
- Two strafe lanes ≥ 24 m with ≥ 400 cm width and no step: C, and D lower. Ceiling ≥ 320 cm in corridors, ≥ 480 cm in rooms, 800 cm in the atriums. The clip ceiling is the room ceiling. Surfaces meant for rocket jumps (the two E mid bridges) have ≥ 900 cm of clearance above take-off (07f: a rocket-jump apex is ≤ 880 cm); everywhere else the real ceiling blocks.
- Doors 240–400 cm wide, walkable widths ≥ 120 cm, ledges ≥ 120 cm deep, pad landing zones ≥ 300 × 300 cm; every free platform edge has a `DROP` link (ADR 0005 §4 conventions as in `Tools/editor/README.md`; *E3: only where the landing zone is a clear ≥ 300 × 300 cm floor ≥ 500 cm from a wall and not a pad trigger — six such links were removed in task 06*), one `ROCKET_JUMP` link per RJ shortcut (two: A-ledge bridge → E top, B-balcony bridge → E top), `JUMP_PAD` links for the three pads (A, B, D → E top).
- D41: no walkable floor without nav mesh unless sealed; the bridges and the D balcony are filled below or ≥ 160 cm clear and ≥ 170 cm wide (then they are rooms with their own nav).
- **8 spawns**, each with a weapon ≤ 8 m away, none in line of sight of Mega or RA, none within 10 m of another, facing into the room; `VeloxSpawn::Select` (farthest half + avoid radius) does the rest.
- Items (respawn per ADR 0004 §1: health 35 s, armor 25 s, weapons by game mode, powerups 120 s): 1 Mega, 1 RA, 2 YA, 6 shards, 1 × 50 HP, 5 × 25 HP, 8 × 5 HP, weapons RL/RG/LG/SG/PG (MG is the spawn weapon; no MG pickup), one ammo per weapon type placed 6–12 m away from its weapon, **Quad in FFA only**. Gating: `UVeloxItemDefinition` gains `FGameplayTagContainer DisabledInModes`; the layout gives the Quad `GameMode.Duel`; `AVeloxPickup::BeginPlay` on the server destroys a pickup whose definition is disabled for the running mode before the item registry sees it (bots never route to it; clients never see it because `bNetLoadOnClient` actors destroyed on the server at BeginPlay are torn off before the first replication — dev verifies and, if not, hides + disables instead). No Haste/Regen/Battle Suit on DM1 (readability of the first map; they exist for later maps).

The art theme is the human's choice (question 4); the design does not depend on it. Working name `DM1`; the display name comes with the theme.

### 4. Character pipeline

**4.1 Proportions and the hitbox.** The character is **140 cm tall standing, 100 cm crouched**, torso and head inside the pawn capsule (radius 37.5, half height 70; Q3's 30 × 30 × 56 u box = 75 × 75 × 140 cm, exactly our capsule). ADR 0003 §6's **single rewound capsule stays the only hitbox**; limbs may leave the capsule by ≤ 15 cm in animation extremes and are not hittable there, and the head is not a separate target. Per-bone hitboxes remain deferred (the `FVeloxHitboxPose` type is already per-shape; adding bone capsules later changes nothing above `UVeloxHitboxComponent`). Reason: a per-bone model would multiply the lag-compensation history, needs the animation pose to be reproducible on the server, and Q3's readability came from the box, not from headshots. `PA_Velox` holds one capsule body on `pelvis` and nothing else (no ragdoll; the corpse plays the death animation and holds its last frame). The mesh component is `Mesh` with relative location `(0, 0, −70)` and yaw −90° (FBX forward convention), crouch lowers the capsule as today and the anim instance switches to the crouch sequences.

**4.2 Skeleton.** **UE5 Mannequin bone names and hierarchy** (root, pelvis, spine_01–05, neck_01–02, head, clavicle/upperarm/lowerarm/hand × 2, thigh/calf/foot/ball × 2; fingers and ik_* bones optional; ≤ 70 bones), authored in Blender by `Tools/blender/character.py` with a hand-built deform rig (no Rigify control rig in the export). The reason is retargeting: Epic's Manny/Quinn animation set (present in the Mac's Launcher install under the ThirdPerson template, absent on the VM) can be dropped onto `SK_Velox` with the identity retarget if the human provides it, and any marketplace/Mixamo set retargets through IK Rig; our own procedural animations (4.4) cover the case where nothing is provided. Sockets: `weapon_r` on `hand_r`, `foot_l`/`foot_r` on the balls, `eye` on `head` (for later); `muzzle` is a socket on each weapon mesh. Unit scale: Blender scene unit 0.01 (1 Blender unit = 1 cm), −Y forward, Z up; FBX export with `apply_unit_scale`, `bake_space_transform`, `armature_nodetype='NULL'`, `add_leaf_bones=False`, mesh + armature only, animations as separate FBX files sharing the armature.

**4.3 Mesh and skins.** One low-poly stylised body (≤ 6 000 triangles, one 1024 × 1024 mask texture, one material slot). `M_Character_Master`: base colour = `BodyColor` on the mask's R channel, `TrimColor` on G, skin/visor colour on B, emissive strips on A at `EmissiveStrength` (default 0.35 × `BodyColor` — the "bright skin" reads in shadow but is still lit, so baked lighting grounds the figure). **Skins are material instances, nothing else:** `MI_Skin_Red`, `MI_Skin_Blue`, `MI_Skin_Green`, `MI_Skin_Yellow` (the four future team/duel colours) plus `MI_Skin_Orange`, `MI_Skin_Cyan`; colour rule: body HSV value ≥ 0.6 and saturation ≥ 0.7, while the environment palette stays at value ≤ 0.5 and saturation ≤ 0.25 (`docs/art/style-guide.md`), so a player is the most saturated thing in any frame. `UVeloxCharacterCosmetics` lists `SkeletalMesh`, `AnimClass`, `Skins` (array of `{Name, MaterialInstance}`), `MeshOffsetZ −70`, `bUseSequencePlayback`, `ViewModelSettings`. `AVeloxPlayerState::PlayerColorIndex` becomes **`SkinIndex`** (same replication, same assignment order; the skin list order is the old palette order so the HUD/scoreboard colours stay; `GetPlayerColor()` returns the skin's body colour). **Enemy skin forcing** (Q3 `cg_forceModel` + bright-skin culture): `UVeloxGameUserSettings::bForceEnemySkin` + `ForcedEnemySkin` (default *on*, `Green`; question 6) — a local client renders every non-owned pawn with that skin; teams (M7) will override it per team. `PlaceholderBody` stays as a fallback behind `velox.vis.PlaceholderBody 1` and is otherwise destroyed once the cosmetics have loaded.

**4.4 Animation set** (`ArtSource/Export/A_Velox_*.fbx`, procedural keyframes from `character.py` unless the human supplies Manny clips): `Idle`, `Run_Fwd`, `Run_Back`, `Run_Left`, `Run_Right` (cycle 0.6 s at the reference speed 800 cm/s; play rate = `Speed2D / 800` clamped to [0.5, 1.6]), `Jump_Start` (0.15 s), `Air_Loop`, `Land` (0.2 s), `Crouch_Idle`, `Crouch_Walk`, `Fire_Upper` (0.15 s, upper body only, additive slot), `Death_A`, `Death_B` (0.8 s, hold last frame). Q3 ran at a fixed cadence with hard cuts between leg states; we do the same — no root motion, no IK, no blend spaces beyond the 4-way directional pick.

**4.5 Anim instance: C++ decides, the Blueprint graph only displays.** `UVeloxAnimInstance::NativeUpdateAnimation` reads the owning `AVeloxCharacter`/`UVeloxMovementComponent` (proxies use the smoothed replicated velocity) and exposes `Speed2D`, `DirectionDeg` (−180..180 vs. actor yaw), `bAirborne`, `bCrouching`, `AimPitch`, `bFiring` (set for one frame by the feedback component on `Fire` cues), `bDead`, `LegState` enum (`Idle, Run, JumpStart, Air, Land, CrouchIdle, CrouchWalk, Dead`) with the cadence/duration rules above; the state rules live in a world-free `VeloxAnimState.h` so they are unit-tested. The **AnimGraph is a Blueprint (`ABP_Velox`, parent `UVeloxAnimInstance`)** — a state machine over `LegState` plus the fire slot — and is the one M5 asset that can only be authored in the editor on the Mac (the Python API cannot build anim graphs). Until it exists, `bUseSequencePlayback` makes the anim instance call `USkeletalMeshComponent::PlayAnimation(Sequence, bLoop)` on state change (hard cuts, no blend): the game is complete without the Mac; the Mac adds blends. `docs/art/character-spec.md` contains the exact state machine so the human (or a `dev` with Mac access) builds it in 30 minutes.

**4.6 First person: weapon view model only, no arms** (Q3). `UVeloxViewModelComponent` on `AVeloxCharacter`, created only for the locally controlled pawn, attached to the camera, holding a `UStaticMeshComponent` with the weapon's `ViewMesh` (same mesh as the world model, offset by `ViewOffset`/`ViewScale` from `UVeloxWeaponCosmetics`), `bOnlyOwnerSee`, and rendered through UE 5.8's first-person primitive path (`FirstPersonPrimitiveType = FirstPerson` on the component, `FirstPersonFieldOfView 70`, `FirstPersonScale 0.6` on the camera's `FMinimalViewInfo`; `dev` verifies the 5.8 names in `Components/PrimitiveComponent.h` and `Camera/CameraTypes.h` and falls back to a plain owner-only mesh if the path is unavailable) so the weapon neither clips into walls nor stretches at 110° FOV. Motion is procedural from movement state, not animated: bob (distance-driven, ground only, Q3 `cg_bobup`-style), sway from the view-rotation delta, recoil kick from the `Fire` cue, raise/lower following the inventory's predicted switch (`UVeloxWeaponInventoryComponent` switch state and `SwitchEndTime`), all tunables in `UVeloxViewModelSettings`. The third-person pawn carries the `WorldMesh` on `weapon_r`, hidden for the owner (`SetOwnerNoSee`). Cheap, readable, and it meets the ROADMAP's "first-person view models for all six weapons" without a hand rig.

### 5. Lighting: static only, CPU Lightmass, headless bake with a defined fallback

**Light rules** (`docs/art/style-guide.md`): all lights `Static`; no `Stationary` light anywhere; the only movable lights are muzzle flashes and rocket lights (`CastShadows false`, ≤ 2 concurrent, owned by the feedback component). `SkyLight` static with the small cubemap `TC_Sky_DM1`. Lightmap resolution: floor tiles 128 (3.1 cm texels on a 400 cm tile), walls 64, trims/pillars 32, bridges 64; kit pieces get a generated lightmap UV in channel 1 (`import_art.py` sets `bGenerateLightmapUVs = true`, `MinLightmapResolution 64`, `DstLightmapIndex 1`). Volumetric lightmap detail cell 200 cm (characters and projectiles are lit by it; the forward renderer samples it per object). 6–8 sphere reflection captures at 128 px. `LightmassSettings`: 3 bounces, `IndirectLightingQuality 1`, `StaticLightingLevelScale 1`, compressed lightmaps; **Preview** for iteration, **Production** for the accepted map. Expected bake on 16 vCPUs for 64 × 44 m: 10–40 min Preview, 1–3 h Production.

**Bake path A — headless on this VM** (`infra/ci/bake.sh <Map> <Quality>`): `UnrealEditor-Cmd Velox.uproject -run=ResavePackages -BuildLighting -Quality=<Preview|Medium|High|Production> -MapsOnly -Map=<Map> -AllowCommandletRendering -vulkan -RenderOffscreen -unattended -nopause -nosplash -stdout -FullStdOutLogOutput` with `VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json` so the Vulkan RHI binds the llvmpipe device, under the soak lock (`flock -o <scratchpad>/soak.lock`) because Lightmass takes every core. Task 01 probes this on `L_ItemTest` before anything depends on it and records: does the RHI initialise (`LogVulkanRHI` device line), does `UnrealLightmass` start (`LogLightmassSolver`, a child process), does the map save with build data, wall time. Success = a Preview bake of `L_ItemTest` completes and `audit_map.py --lighting` finds a populated `UMapBuildDataRegistry`.

**Fallback B — bake on the Mac**: identical commandlet via `infra/ci/build-mac.sh --bake <Map> <Quality>` (Metal; `SwarmInterfaceLocal` is also the Mac path), the human (or a `dev` with Mac access) runs it and commits the `.umap` (LFS). The VM then only *verifies*: the `Velox.Maps.LightingBuilt` automation test fails when a map in `MapsToCook` other than the test maps and `L_MainMenu` has no build data, so an unbaked `L_DM1` cannot merge to `main`.

**Fallback C — explicitly not an M5 acceptance state**: if neither A nor B is available at the time, `L_DM1` runs with its static lights rendered as unbuilt preview lighting (UE's default; ≈ 0.3–0.5 ms at 1080p, no shadows) for bot soaks and flow playtests only. The ADR forbids accepting M5 in this state; the lead escalates with question 7.

GPU Lightmass is rejected (not installed, needs RT hardware, and its output differs from CPU Lightmass, which would make the Mac and the VM disagree).

### 6. Nav-coverage lint (owed from M4)

`velox.bots.NavCoverage [Grid=50] [MinClusterM2=1]` (server console command, `Bots/VeloxNavCoverage.cpp`, also run by `infra/ci/navlint.sh <Map>` as `-server -nullrhi -ExecCmds=...` with a 120 s timeout): after `VeloxNav built`, iterate every component that blocks `ECC_Pawn` and affects navigation, take the top faces of its bounds whose slope ≤ `AgentMaxSlope` (boxes and the generators' ramps; arbitrary meshes are sampled by downward line traces on the grid), sample points on a `Grid` cm lattice 5 cm above the surface, discard points with < `AgentHeight` free headroom (sealed by rule, fine) or outside the nav bounds, and project each remaining point to the nav mesh with the D41 extent `(AirborneProjectRadiusCm, AirborneProjectRadiusCm, OnMeshHalfHeightCm)`. Points with no projection within `AgentRadius` horizontally are *uncovered*; connected uncovered points form clusters; clusters ≥ `MinClusterM2` are reported with centre, extent and the owning actor's `Layout:` tag. Output `VeloxNavCoverage walkable_m2=<x> covered_pct=<y> clusters=<n>` plus one line per cluster; a second pass reports *nav under low clearance* (polys whose centre has < `AgentHeight` headroom — D32's class). Exemptions by actor tag `NavLintIgnore` (item pedestals, the deliberate D17 bed slots). Gate: `clusters = 0` for `L_DM1_Blockout`/`L_DM1`; the three test maps run report-only first and the report is attached to task 03 (they may legitimately show the known D17 slot). Unit test: `Velox.Bots.NavCoverageClusters` on the world-free clustering helper.

### 8. Performance budget and how it is checked without a GPU

Target (ROADMAP): 240 fps at 1080p on a mid-range GPU, no hitches → ≤ 4.1 ms per frame. ## Consequences

- The map's gameplay geometry exists only in one Python table; art can never change collision; soaks and the lint judge the blockout and the art map identically. Cost: the art pass is a *replacement* of boxes by kit instances, so organic shapes (arches, curved walls) are out of M5's scope — accepted; Q3 maps are boxes too.
- Everything art-related is scriptable and the scripts are the deliverable; if Blender is unavailable on both hosts, the human receives exact specs and the import path is still automated. The one unavoidable editor asset is `ABP_Velox`, and the game runs without it.
- Lighting correctness depends on either the VM's software-Vulkan path (unproven until task 01) or the Mac; the ADR makes the unbaked state a non-acceptance state rather than hiding it.
- The hitbox stays a capsule, so no headshots and no limb hits; the character design must keep the silhouette inside the capsule. Per-bone hitboxes remain a possible later ADR without touching the trace or replication paths.
- Enemy skin forcing on by default makes the game more readable and less "personalised"; teams in M7 will override it.
- New LFS volume (≤ 600 MB) is a real cost on a 21 GB-free disk; the audit prints the running total and the lead prunes `Saved/`.

**Deliberately deferred:** teleporters, pits/void, per-bone hitboxes, ragdolls, first-person arms, blend spaces/IK/root motion, a second surface type for footsteps, reverb/occlusion, music, Haste/Regen/Battle Suit placement on DM1, GPU Lightmass, Nanite/Lumen (forbidden anyway), level streaming/World Partition (single persistent level), decals, particle effects beyond what the cues already draw.

## Alternatives considered

- **Author the map in the editor on the Mac** (the normal UE workflow): rejected while the Mac is unavailable and because every M1–M4 regression tool assumes regenerable maps; the generator costs a day and pays back on every layout change.
- **Collision on the kit meshes (simple collision per piece):** rejected — seams and trims change the movement feel the blockout was tuned on, and nav generation would depend on art.
- **q3dm17-class space map:** rejected for map 1 (§3).
- **Per-bone hitboxes with the mesh:** rejected (§4.1).
- **Custom skeleton / Rigify rig in the export:** rejected in favour of Mannequin bone names (§4.2) to keep every animation source retargetable.
- **First-person arms with a separate rig:** rejected (§4.6) — doubles animation work for a game that historically has none; readability is in the weapon.
- **Blend-space ABP as the only animation path:** rejected as a hard dependency on the Mac; `bUseSequencePlayback` keeps the VM self-sufficient.
- **Anim-notify footsteps:** rejected — proxies and bots must sound identical with or without an ABP; distance cadence is deterministic and matches Q3.
- **Stationary lights for muzzle flash/rocket light:** rejected — forward-renderer cost and ADR 0001.
- **GPU Lightmass** and **Lumen:** not installed / forbidden.
- **Install Blender on the VM without asking:** not done (question 1); the `apt` package is ≈ 1 GB with dependencies and the ADR works either way.
- **Lyra reference, adopted vs. not:** adopted — cosmetics as data assets loaded through the asset manager and never on the dedicated server (Lyra's `ULyraPawnData` plus cosmetic components idea, reduced to one data asset per pawn and per weapon), tag-driven cues for all weapon feedback; *not* adopted — Lyra's `ULyraControllerComponent_CharacterParts`/`B_PickRandomCharacterParts` (modular bodies: needless here), Lyra's layered AnimBP with linked anim layers and foot IK (too heavy for Q3 cadence and editor-bound), Lyra's anim-driven first-person arms, Lyra's MetaSounds-based audio (we use plain `USoundWave`/`USoundCue` so the VM can create every asset by script).

#### E0.3 — Soak runner and invariants (§7)

- (a) **Item coverage on `L_ItemTest`: the exemption stands, with reasons in the band file.** `DA_Item_Ammo_Bullets` (grid slot): the MG is the spawn weapon, every respawn refills its ammo, so `Need = deficit/max` is small and a grid of 18 items 300 cm apart always offers a higher-valued neighbour. `DA_Item_Ammo_Rockets` (rocket-jump platform, Z 350): reachable only through a `ROCKET_JUMP` link whose eligibility needs rockets — the item gives what reaching it costs (the ADR 0005 §14 fixture; the FFA ×3 table shows no `RocketJump` attempts at all, the same fact). The exemption does **not** transfer: `BAND_FFA_COVERAGE_EXEMPT` is honoured only for the three test maps (enforced in `ffa_set.py`, task 04b) and `bands/L_DM1.sh` has none. DM1 has no bullets pickup (§3) and its rockets ammo lies on D's lower floor. - (b) **Link success: definition corrected, threshold kept, sample raised.** `AVeloxBotController::NotifyLinkFinished` writes `result=aborted` for *every* outcome that is neither `ok` nor `missed`, so the runner's `result != aborted` rule counts only `missed` as a failure and silently drops `timeout`, `noimpulse` and `tooslow`. Ruling: judge by `reason=`. **Failed = `missed`, `timeout`, `noimpulse`, `tooslow`. Not an attempt = `replaced`, `below_start`, `ineligible`** (re-plans, D28). Success = ok / (ok + failed) per link type, pooled over the set. ### E2 — 2026-10-31 — Dwell invariant: item-timing waits are excluded like camp episodes, the 5 s cap stays (§7, E0.3 (d); `notes/dwell-report.md`; architect)

*Evidence.* The 6–7 s `BotDuel` dwells on `L_ItemTest` (03b, the dwell report) are ADR 0005 §7 item timing: a Hard dueller (`ItemTimingSkill 1.0`, `MaxWaitSeconds 8`, widened by D16's `CommittedScore`, i.e. `Wait ≤ 8 + CommitTravel`) chooses an unavailable major up to ≈ 16 s early, walks to its spawn point and stands there (`arrived=1 speed=0 stuck=0`) until the `VeloxPickupRespawn`, then takes it in the same frame. D39 even prescribes this ending for a camp ("the timing path turns the camp into an Item goal for the last 8 s, so the bot ends standing on the spawn point"). The route line of such a wait reads `goal=Item … camp=0 available=0 respawn_in=R`, so the D34 `camp=1` exclusion does not see it; under the old 8 s cap it fitted, under E0.3 (d)'s 5 s cap it does not. In the 41 stored and fresh Duel rounds re-scanned for this ruling (32 under `docs/adr/evidence/0005-D47…D50`, the 3 D51 rounds, the 6 fresh rounds of the report) **no timed wait ran past its respawn** (0 of ≈ 1 000 episodes exceed `respawn_in + 1 s`; no route line's lead came near the 16 s gate — the report's largest was 8.2 s, the stored rounds' 7.9 s), and the 2 rounds in the report's 61 that stay above 5 s after the exclusion are the two real stalls (`goal=roam`, stuck strikes 1-2-2) — the exclusion hides nothing the band exists for. `arrived=1` is **not** usable as the per-sample criterion: `bGoalArrived` is cleared whenever knockback or a fight moves the bot off the goal point (`VeloxBotController.cpp` "walk back if pushed away"), and the YA/Quad waits of the report show `arrived=0101111`, `0100000` while the bot strafes within 150 cm of the item. The runner has the item position instead: `VeloxPickupSpawn item=<DA> at=V(…)` (every log since D48; `ToCompactString` drops zero components, so `V(X=500.00)` means Y = Z = 0).

*Rulings.*

- (a) **Log-derived classification, no `wait=1` field.** The classifier uses only three lines the two runners already parse for other bands — `VeloxBotRoute … goal=Item item=X camp=0 … travel=T available=0 respawn_in=R lead=L` (the camp label comes from the same line), `VeloxPickupRespawn item=<DA(X)>` (the Mega band reads it), and the 1 Hz `VeloxBot name=… goal=item item=<DA(X)> … pos=` sample (the dwell scan reads it) — plus `VeloxPickupSpawn … at=`. The route line's fields are the ADR 0005 §14 contract the camp band already depends on; a format change breaks camp exclusion and this rule alike, and it is made **visible rather than silent** by the FLAG in (e). A `wait=1` field on the debug line would carry state that is already derivable (`Goal.Item && !Item->IsAvailable()`), costs a controller change, a build and a live run, and does nothing for stored evidence (`--reeval` of the D51 sets must keep working). *Deferred, not planned:* it is reconsidered only if the FLAG in (e) ever fires on a legitimate log.
- (b) **Definition (both runners, verbatim).** A **timed-wait episode** of bot B opens at a `VeloxBotRoute bot=B goal=Item item=X … available=0 respawn_in=R` line at time t₀ (any phase, like the camp label) and closes at the first of: the `VeloxPickupRespawn item=DA(X)` line; the next `VeloxBotRoute bot=B goal=` line (which may open a new episode, also for the same X with a fresh R); or t₀ + min(R, `WAIT_MAX_S` 20) + `WAIT_SLACK_S` 1. A Live 1 Hz `VeloxBot` sample of B is a **timed-wait sample** iff an episode is open for B, the sample reads `goal=item item=DA(X)`, and — when X has a `VeloxPickupSpawn at=` position in the log — the sample lies within `WAIT_RADIUS` **300 cm** (2-D) of it; without a spawn position the positional test is skipped and the round prints `wait_pos=n/a` (the D47 fixture; nothing newer). Timed-wait samples are treated **exactly like `camp=1` samples**: the bot's current dwell run is dropped and the next non-excluded sample starts a new run. `DA(X)` is `DA_Item_` + X with `.` → `_` (`Powerup.BattleSuit` → `DA_Item_Powerup_BattleSuit`). The radius is "at the item" (D39's `CampOffsetCm` 200 plus a strafing pawn; the observed fighting waits stray ≤ 130 cm; 150 / 300 / unbounded give identical verdicts on the 32 stored Duel rounds, 300 is chosen so that a bot stuck 3 m or more from its unavailable goal still counts). The 20 s cap is the D39 camp horizon (`DuelCampMaxLeadSeconds`): no preset legitimately waits longer as an Item goal (Hard 8 + 8, Nightmare 10 + 8), and it bounds the exclusion when a respawn line never comes.
- (c) **Scope: every bot script on every map**, the same constants in `nettest.sh` (BotRun, BotDuel) and `ffa_summary.py` (the FFA set), next to `DWELL_RADIUS`/`DWELL_MAX`: `WAIT_RADIUS 300`, `WAIT_MAX_S 20`, `WAIT_SLACK_S 1`, `WAIT_LEAD_FLAG_S 16`. A map-independent invariant has one definition; at Medium (`0.5 × 4` = 2 s early plus the commit widening) the waits are shorter but real (6–14 episodes with samples per D51 BotRun/FFA round), and the fresh FFA ×10 D51 round 4 moves 5 → 4 under it. Easy (`ItemTimingSkill 0`) produces episodes only with `lead ≤ 0` and seldom any sample.
- (d) **The cap is unchanged: `max_dwell_s ≤ 5` inclusive, on every map, not loosenable by a band file (§7, E0.3 (d)).** E2 adds a second **exclusion class** beside `camp=1`, each bounded by an external quantity the runner prints (camp: `camp_max_lead_s` against `DuelCampMaxLeadSeconds`; timed wait: `wait_max_s` against `respawn_in` and the 16 s gate). Standing **after** the closing event — past the respawn, past a camp's end — is judged by the plain cap because the run restarts there; a refused pickup still fails as `refused` and, 6 s later, as a dwell. Excluding samples never raises the cap; it can move the *measured* max in either direction by anchor re-seeding (the D34 run is anchored at its first sample; a new anchor after an excluded stretch can collect a different set — observed 2 → 3 in 2 of the 110 stored and fresh rounds, 7 → 2 in the three stored 6–7 s rounds). Keeping the anchor across excluded samples was not chosen: it would sum a fight-stand before the wait with a stand after the take into one number.
- (e) **Report fields and FLAGs, no new band.** Per round, on the dwell report line and in `stats.json` / the FFA `.json`: `timed_waits` (episodes with ≥ 1 excluded sample), `wait_samples`, `wait_max_s [<bot>:<item>:R=<r>,lead=<l>]` (the largest sample time − t₀ over excluded samples), `wait_capped` (episodes whose respawn came later than R + 1 s after t₀). FLAGs (printed, never a FAIL): `FLAG no timed-wait sample although <n> Item routes had available=0 (log-format drift? ADR 0006 E2)` — suppressed when any sample of the round carries `difficulty=DA_Bot_Easy`; `FLAG timed wait beyond the gate <bot>:<item>:lead=<l> > 16 s (router gate ADR 0005 §7/D16)`; `FLAG timed wait capped x<k>`. The set lines print `timed_waits=[…] wait_max_s=[…]`; `ffa_set.py` prints the set's `max wait_max_s`. The router's gate itself is a unit-test matter (`Velox.Bots.ItemValue`), not a soak band.
- (f) **Tooling.** The rule is implemented inside the two runners, which are the single source; the report's `dwellprop.py`, `dwellclass.py` and `dwellscan.py` are superseded by the runner's own output and are **not** copied. `dwellwhy.py` (per long run: route line in force, `arrived`/`speed`/`stuck`/`vis` per sample, respawns and takes inside the run) is copied to **`infra/ci/dwellwhy.py`** as the triage tool, extended with the class label `camp | timed-wait | other` per run so that the next dwell question (task 06 on DM1) starts from it. The acceptance figures on the stored evidence are in task **04c**.
- (g) **Letters.** Task 07's DM1 band ruling, planned as "E1", is **E3**; E0's "E0 precedes E1" sentence is corrected above. Task 07 no longer decides the dwell measure (E0.3 (d) is closed here); it confirms E2's figures on DM1 (`timed_waits`, `wait_max_s`, no FLAG) and keeps the 5 s.

*Not chosen:* raising the cap back to 8 s (lets a 6–8 s stall pass again; E0.3 (d)); lowering Hard `MaxWaitSeconds` (a behaviour change to §7/D39 to fix a measure); the `wait=1` field now (see (a)); `arrived=1` as the sample test (see evidence); a preset table of `MaxWaitSeconds × ItemTimingSkill` in the runner (duplicates data assets; the fixed 20 s cap and the 16 s FLAG do the same job).
