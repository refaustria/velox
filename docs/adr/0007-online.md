Proposed (architect, 2026-11-01). Decisions 1–5 below are the recommendation; human questions 41–49 (§"Questions for the human") settle the open points. Tasks marked "start now" in the implementation notes do not depend on any answer.
**Scope:** everything M6 needs (ROADMAP M6): a Linux server binary people can connect to, a server browser, hosting on this machine (systemd, firewall, status JSON), client downloads for Linux/macOS/Windows on `https://games.inceptum.at`, and the security pass that was deferred to M6 by ADRs 0003 and 0004. ## Context

Where the project stands: M0–M4 merged, M5's VM part merged (`L_DM1` "Praesidium", character, weapons, audio); the M5 bake and the human playtests wait for the Apple Silicon Mac. The client already connects by IP from the main menu (`UVeloxGameInstance::ConnectToServer`, ADR 0004 §7), names come from `?Name=`, the online subsystem is `Null`, replication is classic (no Iris, no Replication Graph; ADR 0001 §3), every soak runs a dedicated server through `UnrealEditor-Cmd … -server -nullrhi` (`infra/ci/nettest.sh`).

Hard facts about the environment (verified 2026-11-01 unless marked "from docs"):

1. **Engine.** `/opt/UnrealEngine-5.8` is an *installed* UE 5.8.4 build (CL 58902052, `Engine/Build/InstalledBuild.txt`), trimmed to 32 GB. Its precompiled build environments are `Engine/Intermediate/Build/Linux/x64/UnrealGame/{DebugGame,Development,Shipping}` and `UnrealEditor/Development` only — there is no `UnrealServer` or `UnrealClient` set. `Build.sh VeloxServer Linux Development` fails in 4 s with `Targets with a unique build environment cannot be built with an installed engine` (RulesError); without the unique environment it would fail on the missing precompiled server modules. `Build.sh Velox Linux Shipping` **succeeds** (75 s, 174 MB binary, `NullDrv` is in both the Development and the Shipping precompiled sets). The `ReplicationGraph` plugin was removed by the 2026-10-24 trim (it is in the restore list). `OnlineSubsystemSteam` (Steamworks SDK 1.64, Linux x86_64 redistributable) and `OnlineSubsystemEOS`/`OnlineServicesEOS` + `libEOSSDK-Linux-Shipping.so` are present with Linux editor binaries, so either subsystem can be enabled later without an engine change.
2. **`-server` does not make a packaged Game build a dedicated server.** `IsRunningDedicatedServer()` (`Runtime/Core/Public/Misc/CoreMisc.h:152`) returns `true` for server-only binaries, **`false` whenever `FPlatformProperties::IsGameOnly()`** (every packaged Game build), and only then consults the command line (the editor path). The stand-in ADR 0001 §5 relied on therefore exists only for the editor binary, which is exactly what `nettest.sh` runs. A cooked Game build can host a **listen** server (`Map?listen`), not a dedicated one.
3. **Disk.** `/` is 125 GB with 19 GB free; the floor is 15 GB and the disk cannot be enlarged (STATUS q1). Reclaimable under the standing authorisation: `~/.cache` 3.1 GB, docker build cache 2.7 GB (dangling images 3.5 GB would need the human's word) → about 25 GB free, 10 GB of headroom. A UE source build needs well over 100 GB; a server-capable *installed* build made elsewhere is 36–42 GB trimmed and would replace the current 32 GB engine. STATUS q3 "installed engine now, source build before M6" and q1 together are unsatisfiable on this host.
4. **Hosts.** This VM: Debian 13, 16 vCPU, 30 GB RAM (17 GB available; two of the human's llama-servers hold the 4 GB swap), no GPU, no X; `-nullrhi` only. The human's Mac is Intel and cannot render UE 5.8 (q26); an Apple Silicon Mac is coming and is the only machine that will render anything. No Windows host exists; UE cannot cross-compile Mac or Windows from Linux. GitHub Actions: nothing in STATUS or memory says it is available after 2026-11-01; hosted runners cannot hold a UE install anyway — CI stays local (q49).
5. **Network/host.** Public IP 77.244.242.34, `games.inceptum.at` → CNAME → this host; nginx 1.26 holds 80/443 with Let's Encrypt (valid to 2027-01-22, auto-renew); `/downloads/` (autoindex) and `/status/` (JSON, `no-cache`) locations already exist (`infra/nginx/`). **No host firewall is active** (`nftables`, `ufw`, `firewalld` all inactive; `/etc/nftables.conf` is the Debian stub with empty chains). Public listeners today: TCP 22, 80, 443, 8765, 3000. UDP 7777 is free. Rust toolchain present (`cargo 1.99`). Docker active (co-tenant containers of the human; never touched).
6. **The VM slows down under a 120 Hz UE client** (q29, M4-08b: instruction-fetch-heavy code on every vCPU 3–5× slower 20–60 s after a 120 Hz client starts). Soak dedicated servers at 60 Hz never triggered it; a packaged listen host pinned to 60 fps under NullRHI is a new case and must be measured (task 02).
7. **Deferred items this ADR must close** (from ADR 0003/0004 and the post-M4 follow-ups): the late-retarget cheat surface (B42: ≤ Drop + Raise = 0.45 s once per switch, B37 (ii)'s 0.5 s switch tolerance, B32's burst after idle, B35's withheld-RPC rocket; all "deferred to M6, only on evidence"); server-side gating of item-timer data to spectators (ADR 0004 deferred list), which per ADR 0004 C11 amendment 3 (vii) **must treat dead players as spectators** — i.e. a dead human in the engine's spectating state must not receive spectator-grade data, or the death camera leaks it; Replication Graph / Iris evaluation (ADR 0001 §3); platform player names (ADR 0004 §6); `ViewAPlayer` follow-cam (C11, with the server browser).
8. **Engine security facts** (read in `/opt/UnrealEngine-5.8/Engine/Source`): `APlayerController::ServerExecRPC_Implementation` executes **any console command on the server** in every non-Shipping build (`PlayerController.cpp:1879`, body under `#if !UE_BUILD_SHIPPING`); its `_Validate` returns true; both are `virtual` in the UHT-generated body (`PlayerController.generated.h:181–182`), so a project override can refuse it. `AGameModeBase::AllowCheats` returns true only for `NM_Standalone` or the editor (`GameModeBase.cpp:1411`), so no remote client gets a `UCheatManager` on any networked server. `AGameNetworkManager` ships with `bMovementTimeDiscrepancyDetection=false` (`BaseGame.ini:40`). `FNetworkVersion` hashes `GeneralProjectSettings.ProjectVersion` (`UnrealEngine.cpp:2541`; our `DefaultGame.ini` has none, so it is the engine default `1.0.0.0`). SIGTERM is handled gracefully on Unix (`UnixPlatformCrashContext.cpp:176`, `RequestExitWithStatus(false, 128+signal)`). `-UserDir=<path>` redirects `Saved/` (`Paths.cpp:45`). `FObjectReplicator::PostReceivedBunch` calls `PostNetReceive()` **before** `CallRepNotifies` (`DataReplication.cpp:1604/1609`).
9. **Velox code that keys on the server kind** (for the listen-host decision): 22 sites use `NM_DedicatedServer`/`IsRunningDedicatedServer()` to skip cosmetics, audio, HUD, view models, flight lights and asset-manager loads; `AVeloxJumpPad.cpp:86` and the B12/B25 "listen host" rules already handle `NM_ListenServer`; `UVeloxLagCompensationSubsystem::ShouldCreateSubsystem` is "best effort" and registers hitboxes authority-only (not dedicated-only). None of the 22 sites is a correctness rule; all are cost savings that a listen host simply does not get. *(Correction 2026-11-01, task 02: the hitbox component reads the capsule, not bone transforms — skipping cosmetic meshes/animation on a headless host cannot change a hit. One listen-only correctness difference does exist, outside the 22 sites: the engine forces Exponential smoothing on `NM_ListenServer`, which stopped proxy stamp replication; fixed by ADR 0003 B45.)*

## Decision

### 1. Server binary: the cooked Linux Game build, run as a headless listen server with a spectator-only host; editor `-server` as the fallback; the real `VeloxServer` target when a build host exists

**(a) M6 ships the server as the same cooked Linux package players download.** `infra/ci/package.sh` (task 01) cooks once for Linux and stages twice: `Velox-<ver>-Linux.tar.zst` (Shipping — players; console and cheats compiled out, test RPCs compiled out) and `Velox-<ver>-LinuxServer.tar.zst` (Development — the server; logs, `stat`, the soak instrumentation; same cooked content). The server process is

```
Velox/Binaries/Linux/Velox L_DM1?listen?game=FFA?SpectatorOnly=1?Name=Server?MaxPlayers=16?MaxSpectators=4?Bots=3?BotsFill=1?BotDifficulty=Medium \
  -nullrhi -nosound -unattended -nopause -nosplash -log -port=7777 -UserDir=/srv/velox/saved/ffa \
  -ExecCmds="t.MaxFPS 60" -ServerId=ffa -ServerName="Velox FFA | games.inceptum.at" -NoVerifyGC
```

i.e. a **listen server whose local player is a spectator-only `AVeloxPlayerController`** (`?SpectatorOnly=1` on the host URL goes through `UWorld::SpawnPlayActor` → `AGameModeBase::Login/InitNewPlayer` → `MustSpectate` like any login; ADR 0004 §5's `PostLogin` rule and C11 amendment 3 (ii) already make such a controller a Velox spectator). The host counts as a spectator (not toward `MaxPlayers`, `AGameSession::AtCapacity`), never possesses a pawn, never fires, never reads item timers (§5.5 gates on `IsOnlyASpectator()` — the host *is* one, and it has no HUD anyone sees), and is excluded from `AllHumansReady`/`NumHumans` by being inactive (task 02 verifies that `FVeloxMatchPlayer` rows are built from active players only; if the host counted, Duel ready-up would deadlock — that is the one semantic trap and it is a unit row). The server tick is the host frame rate pinned at 60 (`t.MaxFPS 60`; NullRHI frames are sub-millisecond, so pacing is the engine's sleep), matching `NetServerMaxTickRate=60`.

Why this and not the editor binary (fallback (b)): one artefact for client and server (the server runs the bits players run, versions cannot drift), ≈ 1.5 GB per release on disk instead of a source checkout + compiled editor module + DDC (3–5 GB, and the `velox` service user would need read access to the development checkout), ≈ 1–2 GB RSS instead of 3–5, 5 s start instead of 40, and the artefact is portable to any Linux box later. Why not "fix" it by shipping a Server target: fact 1.

**Gate (task 02, before anything is deployed):** `nettest.sh --server-mode listen [--server-binary <staged Velox>]` runs the **whole default list** (13 scripts, 100 ms / 2 % both ways) plus the BotRun ×3 / BotDuel ×3 sets against the headless listen host with the same bands as today; the host sidecar must show no cost windows (fact 6) and the D46 classification unchanged; the 22 server-kind sites (fact 9) are audited and the ones that matter for cost on a host that never renders (`UVeloxAssetManager` cosmetics preload, `UVeloxAudioSettings` asset loads, anim ticking of remote pawns under NullRHI — set `VisibilityBasedAnimTickOption = OnlyTickPoseWhenRendered`? — *corrected 2026-11-01 (task 02):* the hitbox history reads the capsule (`UVeloxHitboxComponent::GetCurrentPose`, ADR 0006 §4.1 "the capsule is the only hitbox"), not bone transforms, so remote-pawn poses on a headless host are pure cost; see ADR 0003 B45 for the listen-server stamp fix) are extended to `GetNetMode() == NM_ListenServer && IsRunningHeadlessHost()` (a small `VeloxServerKind.h` helper: `IsVeloxHeadlessHost()` = `-nullrhi` listen host with a spectator-only local player, read once from the command line) where that saves measurable work — only where measured. The step-up from "dedicated" to "headless listen" is accepted only on that evidence. If the gate fails for a reason that is not a bug: **fallback (b)**.

**(b) Fallback: the editor binary as the dedicated server**, `UnrealEditor-Cmd <checkout>/Velox.uproject L_DM1?game=FFA… -server -nullrhi -log -port=7777 -UserDir=…`, exactly the soak configuration, from a tagged checkout under `/srv/velox/releases/<ver>-editor/` with the editor module built by `build.sh --targets VeloxEditor` and a warmed local DDC (`-ddc=` pointing into the release dir). Zero code change, proven by every soak; costs listed above. The systemd template (task 06) supports both through `VELOX_SERVER_MODE=listen|editor` in the instance env file, so switching is a config change.

**(c) The real `VeloxServer`/`VeloxClient` targets** need a server-capable engine. The only path that fits this disk is a **server/client-capable installed build made elsewhere** with BuildGraph (`Engine/Build/InstalledEngineBuild.xml -set:WithLinux=true -set:WithServer=true -set:WithClient=true -set:WithDDC=false -set:HostPlatformOnly=true -set:WithWin64=false -set:WithMac=false …`) on a rented or borrowed Linux box (≥ 16 cores, ≥ 64 GB RAM, ≥ 300 GB disk, 6–10 h, Epic GitHub organisation access for the source), trimmed with `infra/engine/trim-plugins.py`, then **swapped in** for the current engine (delete 32 GB → install ≈ 40 GB; the floor is breached by ≈ 5 GB during the swap and the human must accept that or the swap waits). After the swap `build.sh` detects server capability by `test -d "$UE_ROOT/Engine/Intermediate/Build/Linux/x64/UnrealServer"`, not by `InstalledBuild.txt`, `VeloxServer` builds in Shipping with `bUseLoggingInShipping` (already in `VeloxServer.Target.cs`), and the `velox-server@` unit switches to it. **Not an M6 gate** (question 41); task 15 holds the recipe.

Rejected: a source build here (disk, fact 3), a slimmed source build (≥ 80 GB before building), source build on the Mac (no Linux cross-compile), Epic's `ghcr.io/epicgames/unreal-engine:dev` container here (40–60 GB on disk; it is the same installed-build-with-server idea and belongs on the rented box), a Shipping Game build as the server (no logging at all in Shipping on an installed engine — `bUseLoggingInShipping` needs a unique environment; a public server without logs cannot be diagnosed).

### 2. Sessions and the server browser: plain IP plus a tiny Velox directory service; Null online subsystem stays; Steam/EOS deferred to an identity decision

**Decision.** Dedicated public servers only, reached by IP:port. There is no NAT problem to solve: the servers have a public address, every client's outbound UDP traverses any NAT, and player-hosted listen servers are not a shipped feature (the menu's "Host local" stays a LAN/test button). The server browser therefore needs a **list**, nothing more, and the Null subsystem has no internet listing — so the ROADMAP's conditional "Rust master-server/status service only if the online subsystem's listing is insufficient" resolves to **yes, needed**, and it doubles as the status JSON the ROADMAP asks for anyway.

- **`veloxmaster`** (Rust, `infra/master/`, axum + tokio, task 03): `POST /api/v1/heartbeat` on **`127.0.0.1:8790` only** (nothing new is exposed publicly — all servers live on this host; the bind is loopback and nginx does not proxy it in M6), in-memory table keyed by `id`, TTL 90 s, writes `/var/www/games.inceptum.at/status/servers.json` atomically (temp + rename) on change and at least every 15 s, so nginx keeps serving a static, cacheable-as-`no-cache` file even if the service is down (stale `generated_at` tells). Config by environment (`VELOXMASTER_LISTEN`, `VELOXMASTER_OUTPUT`, `VELOXMASTER_PUBLIC_ADDRESS=77.244.242.34`, `VELOXMASTER_TTL_S`, optional `VELOXMASTER_TOKEN`); the public address replaces a loopback source address. Runs as its own system user (`veloxmaster`) owning only the `status/` directory. When servers on other hosts appear (M7+), nginx gets a `location /api/v1/heartbeat` with the token — one added block, no protocol change.
- **Heartbeat** from the game (task 04): `UVeloxServerHeartbeatSubsystem : UGameInstanceSubsystem`, created only on a server (`HasAuthority` world, `-ServerId=` present or `UVeloxOnlineSettings::bHeartbeatEnabled`), posts every `HeartbeatIntervalSeconds` (30) and, debounced 2 s, on phase change / join / leave, with `FHttpModule` (modules `HTTP`, `Json`, `JsonUtilities` added to `Velox.Build.cs`). Body (built by the world-free, unit-tested `VeloxServerStatus::BuildHeartbeat(const FVeloxServerSnapshot&) → FString`): `{ "schema":1, "id", "name", "port", "map", "map_display_name", "mode", "phase", "time_left_s", "players", "max_players", "bots", "spectators", "version", "net_version", "password":false }`. `players` counts active humans (`!IsOnlyASpectator() && !IsABot()`), `bots` the AI PlayerStates, `spectators` the remaining PlayerStates minus the host. No player names in M6 (privacy; question 45 can flip it).
- **`servers.json`** = `{ "schema":1, "generated_at": "<RFC 3339>", "servers":[ heartbeat fields + "address":"77.244.242.34:7777", "host":"games.inceptum.at", "updated_s_ago":N ] }`.
- **Map registry** (task 04): `UVeloxMapRegistry : UDeveloperSettings` (`Core/VeloxMapRegistry.h`, `DefaultGame.ini` `[/Script/Velox.VeloxMapRegistry]`): `TArray<FVeloxMapInfo { FSoftObjectPath Map; FString ShortName; FText DisplayName; TArray<FGameplayTag> Modes; bool bPublic; }>` with `L_DM1` → "Praesidium" (ADR 0006 E0.5 said the UI binding waits for this), the test maps `bPublic=false`. The heartbeat, the browser, the scoreboard header and M7's map rotation read it. Data, no asset authoring.
- **Client side** (task 05): `UVeloxServerDirectorySubsystem : UGameInstanceSubsystem` — `Refresh()` GETs `UVeloxOnlineSettings::ServerListUrl` (`https://games.inceptum.at/status/servers.json`), parses with the world-free, unit-tested `VeloxServerList::Parse(const FString& Json, TArray<FVeloxServerEntry>&, FString& Error)`, classifies each entry with `VeloxServerList::Compatibility(Entry, LocalVersion, LocalNetVersion) → Ok | VersionMismatch | NetVersionMismatch | Stale`, broadcasts `OnServersUpdated`. `UVeloxServerBrowserWidget` (C++ UMG per ADR 0004 §7, `UI/`): rows name / map display name / mode / players (+bots) / phase / version, refresh button, Connect → the existing `ConnectToServer("ip:port")`; incompatible rows greyed with the reason; the direct-IP box stays beside it. Main menu gains "Servers". Ping is **not** shown in M6 (UE has no ICMP; a beacon needs a second UDP port; the scoreboard shows ping after connecting) — deferred, see below.
- **Versioning rule.** `DefaultGame.ini` gets `[/Script/EngineSettings.GeneralProjectSettings] ProjectVersion=0.6.0`; a release is a tag `vX.Y.Z` on a commit whose `ProjectVersion` is `X.Y.Z` (`package.sh` refuses otherwise; `--dev` builds are named `<ver>+<sha>` and never published). Because `FNetworkVersion` hashes `ProjectVersion` (fact 8), a client of another release is refused by the engine at connect with a version failure — the browser just explains it earlier. Mac and Linux builds of the same tag are compatible: the hash depends on engine CL, project version and net-version history, not on the compiler.
- **Steam / EOS** are **not** enabled in M6. What they would buy: persistent player identity (bans, stats, names), friends/invites, Steam's master server or EOS Sessions as the list, EOS P2P for player-hosted games. What they cost: Steam needs an AppID (the SpaceWar test ID 480 lists every SpaceWar test server on the internet and requires Steam running on every player's machine; Mac arm64 Steam support is uncertain); EOS needs a product in the Epic Developer Portal (organisation, product, sandbox, deployment, client policies for a trusted server, Device-ID identity provider enabled, client credentials embedded in the build) that nobody but the human can create or inspect, and misconfiguration shows up as opaque SDK errors on a machine that cannot render. Neither solves a problem M6 has. The seam for later: the browser consumes `TArray<FVeloxServerEntry>`; an OSS session search is a second producer of the same struct; identity would land in `AVeloxPlayerState` (`UniqueId` is already plumbed by the engine). Question 42.
- **Lyra:** nothing adopted from `CommonSession`/`CommonUser`/OSS v2 — those exist to abstract three platforms' sessions and logins; we have none. Adopted: the idea that the game instance owns session entry (`ConnectToServer` already does) and that the browser is data-driven.

### 3. Hosting: user, layout, unit, firewall, status, downloads

- **User and layout** (task 06, `infra/deploy/install-server.sh`, idempotent, needs sudo — each root step is stated before it runs): system user `velox` (`--system --home /srv/velox --shell /usr/sbin/nologin`); `/srv/velox/releases/<ver>/` (an extracted `…-LinuxServer.tar.zst`, read-only), `/srv/velox/current → releases/<ver>` (switched by `infra/deploy/release.sh <ver>`, which keeps the previous release and prunes older ones: at most two on disk, the 15 GB floor checked first), `/srv/velox/config/<instance>.env` (mode 0640 root:velox; holds `VELOX_MAP`, `VELOX_MODE`, `VELOX_PORT`, `VELOX_MAXPLAYERS`, `VELOX_BOTS`, `VELOX_SERVER_NAME`, `VELOX_SERVER_MODE`, optional `VELOX_SERVER_PASSWORD` — the game reads this variable directly, it never goes on the command line; F1.3), `/srv/velox/saved/<instance>/` (the `-UserDir`: logs rotate through UE's own `Logs/Velox-backup-*.log`; a weekly `tmpfiles.d` age rule deletes backups older than 14 d).

One instance in M6: `velox-server@ffa` on UDP 7777 (`L_DM1`, FFA, `Bots=3 BotsFill=1 BotDifficulty=Medium`). A `duel` instance is one env file plus one more UDP port (question 43).
- **`veloxmaster.service`**: `User=veloxmaster`, `ProtectSystem=strict`, `ReadWritePaths=/var/www/games.inceptum.at/status`, `Restart=always`, binary at `/srv/veloxmaster/veloxmaster` built with `cargo build --release` on this host.
- **Firewall.** Today nothing filters. Decision: an **nftables allow-list** in `infra/firewall/nftables.conf` (loopback, established/related, ICMP/ICMPv6, TCP 22/80/443, UDP 7777, plus the two public services the human runs today — TCP 8765 and 3000 — unless the human says otherwise; everything else dropped on `input`; `forward`/`output` untouched because docker manages `forward`). Applied **only after question 44 is answered**, in one stated step (`nft -f`, then `systemctl enable nftables`), with a 10-minute `at` rollback armed first so a mistake cannot lock SSH out. If the human prefers the provider's firewall, the file still documents the rule set and only UDP 7777 is requested there.
- **Status JSON:** `https://games.inceptum.at/status/servers.json` (above). Nothing else under `/status/` in M6.
- **Downloads:** `/var/www/games.inceptum.at/downloads/<ver>/` with `Velox-<ver>-Linux.tar.zst`, `Velox-<ver>-macOS.zip` (from the Mac), later `Velox-<ver>-Windows.zip`, `SHA256SUMS`, and `/downloads/latest.json` (`{ "version", "files": { "linux": {"url","sha256","size"}, "macos": …, "windows": … } }`), written by `infra/deploy/publish-download.sh <ver> <file>…` (rsync into place, sums, regenerate `latest.json` and `downloads/index.html`; keeps the two newest versions, prunes the rest). The landing page (task 12) renders `latest.json` and `servers.json` with a few lines of JavaScript, no framework, and carries the per-platform instructions (Linux: Vulkan driver and glibc ≥ 2.28; macOS: Gatekeeper note, question 47; Windows: question 46).

### 5. Security and hardening

5.1 **RPC gate (task 07, dev-hard).** `AVeloxPlayerController::ServerExecRPC_Validate` is overridden to return `false` for every remote connection (and `true` only for `IsLocalController()` — the unattended host never calls it), so a client sending `ServerExec <cmd>` to the Development server is **disconnected by the engine's validation failure** instead of executing a console command (fact 8); `ServerPause_Validate` gets the same rule and `bPauseable=false` is set, because the engine lets any client pause a non-Shipping server (F1.2). The nine project server RPCs are classified: gameplay (`ServerSetReady`, `ServerRequestJoin`, `ServerRequestRespawn`) keep their current validation; the test RPCs (`ServerGiveTestHaste`, `ServerKillSelfTest`, `ServerApplyTestKnockback`, `ServerTeleportTestPawn`, `ServerAddBot`, `ServerKickBot` — all `#if !UE_BUILD_SHIPPING` in the implementation already) gain a server cvar gate **`velox.net.AllowTestRpcs`** (default 0; `nettest.sh` sets it on its server; the public unit never does): `_Validate` returns false when the cvar is 0 → disconnect, logged `VeloxRpcRefused controller= rpc=`. `UCheatManager` is never created for remote players (engine `AllowCheats`, fact 8; Velox does not override it — a unit row pins that). Shipping clients have no console and no cheats; Development *clients* are not distributed (that is why the player archive is Shipping only — a Development client's `viewmode wireframe` is a wallhack).

5.2 **Connection policy (task 07).** `?MaxPlayers=` / `?MaxSpectators=` through `AGameSession` (`AtCapacity` already rejects with "Server full"); **`VELOX_SERVER_PASSWORD`** in the instance env file on the deployed server (`-ServerPassword=` / `?ServerPassword=` are developer conveniences that appear in the log; an empty value at any level falls through to the next, the password is off only when all three are empty; F1.3, F1.4) → `AVeloxGameMode::PreLogin` compares `?Password=` (constant-time compare; the menu's connect field accepts `ip:port` plus an optional password box; the heartbeat reports `password:true`); **player-name sanitation** in `InitNewPlayer` (strip control and bidi characters, collapse whitespace, clamp to `UVeloxOnlineSettings::MaxPlayerNameLength 24`, replace empty with `Player`, dedupe with `(2)`… — the world-free `VeloxNames::Sanitize`, unit-tested); engine timeouts `[/Script/OnlineSubsystemUtils.IpNetDriver] InitialConnectTimeout=30 ConnectionTimeout=20` for the server (`-ini:Engine:` in the unit, not in the client's config). Rate limits on connection attempts stay the engine's stateless handshake.

5.3 **Speed-hack guard (task 07, soak-verified).** `AGameNetworkManager`: `bMovementTimeDiscrepancyDetection=true`, `bMovementTimeDiscrepancyResolution=true`, `MovementTimeDiscrepancyMaxTimeMargin=0.25`, `MovementTimeDiscrepancyMinTimeMargin=-0.25`, `MovementTimeDiscrepancyDriftAllowance=0.005` (F1.1: forgives real clock drift, which the same-host soak cannot show), `MovementTimeDiscrepancyResolutionRate=1.0` (engine default, kept — F1.1), in `DefaultGame.ini` (engine defaults are off, fact 8). The speed-hack criterion is **no gain, measured on the server** (F1.1, restated by F1.4): with detection on, a `DebugTimeScale 1.3` client's server-side displacement over 10 s of real time is ≤ 1.05× and ≥ 0.5× the honest client's (expected ≈ 0.8×: the engine's per-tick payback bound and the walking restart after each payback cost only the client in resolution — F1.4), its client-side displacement is ≤ the honest client's, and the server logs ≥ 5 `VeloxTimeDiscrepancy` lines; with detection off the server-side gain is ≥ 20 %. The cheater's own view being slower is the engine's sawtooth, not a defect (F1.1). Accepted only if the nettest default list (incl. StrafeRun/PadRun stray sums and the ADR 0002 A24–A34 correction bands) is unchanged at 100 ms / 2 %; a logged `VeloxTimeDiscrepancy` line (the engine's `LogNetPlayerMovement` resolution message re-emitted per player) joins the anomaly counters. If the soak degrades, the margins are widened once (0.5 / −0.5) and the result recorded; if it still degrades, detection stays off and that is recorded in this ADR as an amendment.

5.4 **Cheat surfaces deferred by ADR 0003 — anomaly counters now, the move-time switch gate on evidence (task 09, dev-hard).** Every bounded surface the combat ADR accepted (B25 clamp window, B32 burst after idle, B35 withheld RPC/orphans, B37 (ii) switch tolerance, B42 `Late` retargets, origin snaps `VeloxShotOriginSnap`, time clamps `VeloxShotTimeClamp`, fire rejections by reason, 5.3's discrepancy resolutions) is already *logged*; what is missing is the **per-player rate** that separates an honest player at the ping limit (hits a surface once per lost packet) from a modified client (hits it every time). `FVeloxPlayerAnomalyStats` on the server side of `AVeloxPlayerState` (not replicated): counters per surface, switches, shots; `UVeloxAnomalyLog` (server, 60 s cadence) prints `VeloxAnomaly player= id= shots= rejects{…} snaps= clamps= late_retargets=/switches= orphans= discrepancies= rtt_ms=` for players with any non-zero counter, and once at logout. `velox.net.AnomalyKickThresholds` stays **0 = log only** in M6; the heartbeat does **not** carry it. The **move-time switch gate** (B37's deferred design: switch target data with `SwitchMoveTimeStamp`, fire gated on `FireMoveTimeStamp ≥ SwitchStamp + Wait + Drop + Raise − ε`, cheat bound 0.30 s jitter-immune) is **not** built in M6: it is a change to the predicted switch path two milestones after it stabilised, for a 0.45 s-once-per-switch gain that the counters make visible. Trigger for building it (M7): any player with `late_retargets / switches > 20 %` over ≥ 20 switches in the anomaly log, or a playtest report of instant switching. Same rule for B32's per-shooter tolerance.

5.5 **Server-side gating of item-timer data; dead players are not spectators (task 08, dev-hard).** Today every client receives every pickup's `RespawnServerTime` (`AVeloxPickup`, `bAlwaysRelevant`, `DOREPLIFETIME`), so a modified client has exact item timers and the HUD rule (`PlayerState->IsOnlyASpectator()`) is cosmetic. Decision: the information leaves the server only toward connections entitled to it.
- `AVeloxPickup` stops replicating `RespawnServerTime`. It replicates `bool bAvailable` (`ReplicatedUsing`), `uint8 TakeCount` (`ReplicatedUsing`; wraps) and `LastTakenBy` as today. Client cosmetics key on `bAvailable` (hide/show, respawn cue when it flips to true) and on `TakeCount` increments (take cue, pickup message, `velox.bots.Watch` placeholder takes). ADR 0004 C10's **age rule is replaced by a baseline rule** that needs no clock: `PreNetReceive()` clears `bSuppressNetEvents`; `PostNetReceive()` sets it when this is the first bunch the actor received (`!bReceivedInitialState`); the two `OnRep`s adopt the value silently while it is set (engine order: `PostNetReceive` before `CallRepNotifies`, fact 8). A late joiner never hears a take that predates it; a take 0.5 s before joining is not announced either — accepted (C10 announced it only because the time was there). `VeloxPickupRules::IsStaleTake` and `PickupTakeEventMaxAgeSeconds` are deleted; `OnRep_RespawnServerTime` is renamed/split accordingly; owner prediction (`IsPredictedTaken`) is untouched.
- Spectator timers travel **owner-only on the receiver's own PlayerState**: `AVeloxPlayerState::ItemTimers : TArray<FVeloxItemTimerEntry { uint8 ItemIndex; float RespawnServerTime; }>` (`COND_OwnerOnly`, push model, ≤ 23 entries × 5 B, updated on take/respawn by `UVeloxItemRegistry` for every PlayerState the rule entitles). Entitlement is evaluated on the server from `UVeloxGameModeDefinition::ItemTimers` and `IsOnlyASpectator()`: `Spectators` → only `bOnlySpectator` PlayerStates; `Everyone` (the ADR 0004 q4 casual-FFA option, not enabled) → all. A **dead human — controller in `NAME_Spectating`, `bOnlySpectator == false` — is a player** and receives nothing (C11's HUD rule, now enforced server-side; this is how amendment 3 (vii) is satisfied: the death camera cannot leak what the connection never gets). `ServerRequestJoin` → the array is cleared with the flag; `Logout` frees it. `UVeloxHUDViewModel` reads the array (the pickup actor no longer knows the time); the scoreboard's spectator timer column too. Bots read the server registry as before.
- Not gated in M6: pawn relevance/visibility (anti-wallhack PVS). Q3 sends every entity in the PVS and Velox's arenas lie within the 150 m cull distance in full; a visibility gate is an M7+ item with its own measurement, and it would have to apply to the death camera too (same (vii) logic). Recorded in "Deliberately deferred".

5.6 **Replication topology (task 10 measures; decision now).** Classic replication stays for M6. Numbers that would revisit it: server frame mean > 8 ms or p99 > 16 ms at 60 Hz with 16 connections, or per-client downstream > 100 KB/s at 16 players + 8 bots on `L_DM1` (ADR 0001's `MaxInternetClientRate`). Task 10 measures with the headless listen server, 4 headless clients at `t.MaxFPS 60` (not 120 — fact 6) and 12 bots, reports frame-time percentiles (`stat unit` dump every 10 s) and `stat net` per connection; extrapolation to 16 connections is linear in connection count for classic replication. `ReplicationGraph` would need the plugin restored (fact 1); Iris is not evaluated (changes replication semantics, no need shown).

5.7 **Operational security.** No secrets in the repo (`infra/env.example` pattern; `VELOXMASTER_TOKEN`, `VELOX_SERVER_PASSWORD` in root-owned env files; the engine echoes each client's login URL incl. `?Password=` at `LogNet` Log level — accepted for M6, F1.3). The `velox` user cannot write anything but its `saved/` dirs. Core dumps off (`LimitCORE=0`); `.debug`/`.sym` kept beside the server binary for `addr2line` on a crash log. Logs contain IP addresses (UE's `LogNet`); retention 14 d by the `tmpfiles.d` rule — stated on the landing page.

## Consequences

- The public server runs a configuration (headless listen host) that no soak has run before; task 02 pays for that with the full default list before the first deploy, and the editor fallback costs nothing but RAM and disk if the gate fails.
- Client and server come from one cook; `ProjectVersion` must be bumped per release, and the engine refuses cross-version connects — the browser shows why.
- Steam/EOS are a later identity decision; nothing in M6 blocks either, nothing in M6 needs either. Until then there are no persistent player IDs: no bans beyond IP, no stats.
- `AVeloxPickup` loses `RespawnServerTime` on clients; anything that read it client-side (HUD, scoreboard, bot watch) moves to the PlayerState array or to `bAvailable`/`TakeCount`. ItemRun and the FT item map must stay green.
- The Development server keeps the soak instrumentation and `check()`s; a failed check restarts the server (systemd). Shipping clients cannot be debugged with `-log`; the Mac Development build (`build-mac.sh`, not published) is the debugging client.

This holds the 15 GB floor with ≈ 4 GB to spare; a bigger disk remains the real fix.
- The firewall change is the only risky root action in M6; it happens once, with the human's answer and an armed rollback.

### F1 — 2026-11-06 — task 07 rulings: speed-hack criterion, `ServerPause` gate, password in logs (architect)

#### F1.1 — Speed-hack guard: config stays (`ResolutionRate` 1.0), `DriftAllowance` 0.0 → 0.005, the criterion is restated to measure on the server (§5.3)

*Evidence.* Honest client, detection on: 199.8 cm/s, 0 `VeloxTimeDiscrepancy` lines over the full default list (17 scripts) and StrafeRun+PadRun ×10 at 100 ms / 2 %; stray sums and corrections unchanged against the detection-off baseline. Client at `velox.move.DebugTimeScale 1.3`: detection off +29.7 %, detection on **−20.3 %** measured on the *client* (`VeloxTimeScale pos=`), 14 resolutions in ~11 s, 62 non-echo corrections.

*Analysis.* The engine's resolution is a sawtooth: while the client's stamps run ahead the server simulates its moves at the client's rate until the accumulated excess passes `MaxTimeMargin` (0.25 s — at 1.3× that is every ≈ 0.83 s), then it enters resolution, bounds every move to real server time and, at `ResolutionRate` 1.0, pays the 0.25 s back by simulating the next 0.25 s of server time at `MIN_TICK_TIME` (the pawn stands still). Over one cycle the server therefore simulates ≈ 1.083 s of movement in ≈ 1.083 s of real time: **the server-side rate of a time-scaled client is the honest rate by construction**, up to one margin's worth of sawtooth (0.25 s × 200 cm/s = 50 cm, 2.5 % of a 2000 cm run). The −20 % was read on the cheating client, whose own view is snapped back to the frozen server position at every payback (62 corrections; ADR 0002's correction path replays only the unacked moves, so the discarded excess is lost on the client each cycle). That number is the cheater's experience, not the guard's output. The acceptance's "within 5 %" was written to mean "the hack gains nothing"; it named the wrong observer. Lowering `MovementTimeDiscrepancyResolutionRate` (0.5: spend half of each resolution tick moving, half paying back) only makes the cheater's own view smoother and lengthens the sawtooth; it cannot change the server-side rate and buys honest players nothing — they never enter resolution. **Rejected.** `bMovementTimeDiscrepancyForceCorrectionsDuringResolution` is irrelevant: Velox's position tolerance is the engine's 1.73 cm (`MAXPOSITIONERRORSQUARED=3.0`), every resolution tick already corrects.

*False positives.* The soak cannot show clock drift: server and client share one VM clock. A real client's stamps are its own monotonic clock deltas (`FPlatformTime::Seconds`), typically ±50 ppm against the server's, worst cases (VMs, power-saving laptops) a few hundred ppm; `MovementTimeDiscrepancyDriftAllowance=0.0` would turn +100 ppm into a 0.25 s freeze plus a 50 cm rubber-band about every 40 min per player. Burst loss and hitches are not a risk: a client hitch makes the client delta *smaller* than the server delta (negative error, bounded by `MinTimeMargin` −0.25), and a burst of late moves carries the stamps it had, so `ClientDelta − ServerDelta` nets to the real time that passed. **Decision:** `MovementTimeDiscrepancyDriftAllowance=0.005` (0.5 %/s = 5 000 ppm: forgives any real clock, resolves a hack to at most +0.5 %, which is worthless). The margins stay ±0.25 s, resolution and detection stay on, rate stays 1.0. `LifetimeRawTimeDiscrepancy` (logged as `lifetime_raw_s=`) is unaffected by the allowance, so task 09's anomaly line still sees sub-threshold cheating. If the public server's anomaly log ever shows `VeloxTimeDiscrepancy` for players who are not cheating, the next knob is `DriftAllowance` 0.01, never the margins and never the rate.

#### F1.2 — `ServerPause_Validate`: keep, and set `bPauseable=false` (§5.1)

*Evidence.* Engine `APlayerController::ServerPause_Validate` returns `true` in every non-Shipping build and `IsLocalController()` only in Shipping; `ServerPause_Implementation` → `SetPause(!IsPaused())` → `AGameModeBase::SetPause` → `AllowPausing(PC)` = `bPauseable || NM_Standalone`, and `bPauseable` defaults to **true** (`GameModeBase.cpp:68`). The public server is a Development build (§1). Without the gate, any client typing `Pause` freezes the match for everyone, and the pauser's `PlayerState` owns the unpause. No Velox code calls `ServerPause` or `SetPause` (the pause menu is a widget, nothing more), so no honest client ever sends it.

*Decision.* **Keep** the override exactly as written (same rule and logging as `ServerExecRPC`; the unit row in `Velox.Net.NoCheatManagerForRemote` stays). The disconnect is the right response: only a modified or console-driven client can send it. **Add** one line of defence in depth: `bPauseable = false` in the `AVeloxGameMode` constructor, so a listen host's own console (or any future local path) cannot pause a networked match either; standalone PIE still pauses through `AllowPausing`'s `NM_Standalone` clause. Add an assertion to the same unit row (`GameMode->AllowPausing(Remote) == false` on the listen-URL fixture). The other engine server RPCs were checked and need no gate: `ServerToggleAILogging` is a no-op without a `CheatManager` (none for remotes, fact 8), `ServerChangeName` now runs through the sanitizing `ChangeName`, `ServerCamera`/`ServerSetSpectatorLocation`/`ServerViewNextPlayer` are spectator-state plumbing. Noted for task 08, not ruled here: `ServerViewNextPlayer`/`ServerViewPrevPlayer` work in the engine's spectating state, which a dead player is in during the death camera (ADR 0004 C11) — a modified client can request another player's view target while dead; task 08's entitlement rule should cover `ViewAPlayer` for dead players the same way it covers item timers.

#### F1.3 — Server password: `VELOX_SERVER_PASSWORD` in the EnvironmentFile is the production path; no log redaction in code for M6 (§3, §5.2, §5.7)

*Evidence.* The engine echoes the full command line in the server log (`LogInit: Command Line:` via `FCommandLine::GetForLogging`, which only filters when the build was compiled with a command-line allow list — not on an installed engine), in the CSV profiler metadata and in the crash context (`GenericPlatformCrashContext.cpp:468`). Every client's login URL, including `?Password=`, is echoed at `LogNet` Log level (`Login request:`, `Join request:`). `?ServerPassword=` on the host URL is echoed by `LoadMap`/`Browse`. Velox code never writes the value (`VeloxNet password=on|off source=cmdline|url|env` only), and the dev-hard agent added the environment fallback `VELOX_SERVER_PASSWORD` (read in `InitGame`, lowest precedence after `-ServerPassword=` and `?ServerPassword=`).

*Decision.* (a) **Confirmed:** the deployed server receives the password **only** through `VELOX_SERVER_PASSWORD` in `/srv/velox/config/<instance>.env` (`EnvironmentFile`, 0640 root:velox; `run-server.sh` `exec`s the binary, so the variable is inherited and never appears on a command line, in `ps`, in `LogInit`, in the CSV metadata or in a crash report). The env-file key and the variable the game reads are the **same name**, `VELOX_SERVER_PASSWORD`; the ADR's earlier `VELOX_PASSWORD` (§3, §5.7, task 06) is renamed, and `run-server.sh` must not translate it into `-ServerPassword=`. `-ServerPassword=` and `?ServerPassword=` stay as developer conveniences (nettest, local runs) and are documented as "appear in the log". (b) **No redaction in code now.** The one echo that remains on the production path is the engine's `Login request:`/`Join request:` line per connecting client. The options are all worse than the leak: raising `LogNet` above Log removes the connection diagnostics M6 operations depend on; a global `FOutputDevice` filter that rewrites `Password=` in every log line is fragile, costs on every line and is exactly the kind of code that hides a bug later; hashing the password on the client only changes which bearer string is echoed. The password is a friends-only gate (question 45: the server starts open), the logs are readable only by `velox` and root, and the 14-day retention already stands; a leaked password is rotated by editing the env file and restarting the unit. Revisit when identity (Steam/EOS) replaces shared passwords with invites. (c) The leak is **measured, not ignored**: `PasswordRun` keeps its FAIL rule for the value appearing anywhere outside the engine's echoes.

*Instruction for the implementer.* (i) `nettest.sh` `run_password`: start the server with `VELOX_SERVER_PASSWORD="$PASSWORD_RUN_PW"` in its environment instead of `-ServerPassword=` (the production path), assert `VeloxNet password=on source=env`, add `pw_cmdline_echo_lines` (lines containing the value and `Command Line:`/`commandline=`) and FAIL when it is non-zero; `Login request:`/`Join request:` echoes stay counted in `pw_engine_echo_lines`, not judged. (ii) Extract the source selection into a world-free `VeloxNet::ResolveServerPassword(const TCHAR* CmdLine, const FString& HostOptions, const FString& EnvValue) → {Password, Source}` in `Net/VeloxNetCheats.h` and add four rows to `Velox.Net.PasswordRule` (cmdline wins over url over env; an empty cmdline value falls through). (iii) Task 06 (dev): `velox-server.env.example` carries `#VELOX_SERVER_PASSWORD=` commented, `run-server.sh` never emits `-ServerPassword=`, the README states the `Login request:` echo and the rotation rule. (iv) `docs/adr/0007-online.md` §3/§5.7 and task 06 renamed to `VELOX_SERVER_PASSWORD` (done with this amendment).

#### F1.4 — 2026-11-11 — Speed-hack guard: the two server-side losses are verified in the engine, no fix, criterion restated to "no gain"; empty `?ServerPassword=` falls through (architect)

*Evidence.* `docs/adr/evidence/0007-discrepancy/README.md` (2026-11-06 re-run and the `p.DebugTimeDiscrepancy 2` diagnostic), `notes/07-report.md` (update 2026-11-06), engine `CharacterMovementComponent.cpp` 9438–9625 (`ProcessClientTimeStampForTimeDiscrepancy`), 5653–5890 (`PhysWalking`), 3866/4431/5657 (`CalcVelocity`/`PerformMovement`/`PhysWalking` early-outs, all `< MIN_TICK_TIME`), 9311/10022/10142 (`GetServerMoveDeltaTime` feeds every server move incl. old moves), 9316/10031/10146 (`ServerData.ServerTimeStamp` is stamped after each processed move), 12625–12635 (the override is returned only while `bResolvingTimeDiscrepancy`), `PrimitiveComponent.cpp` 3282–3295 (`MoveComponentImpl` minimum sweep distance), `Config/DefaultEngine.ini` `NetServerMaxTickRate=60`, `Config/DefaultGame.ini` `ClientNetSendMoveDeltaTime=0.0166`, `nettest.sh` (`t.MaxFPS 60` both sides), `Source/Velox/Movement/VeloxMovementComponent.cpp` `CalcVelocity`/`RestoreGroundEndVelocity`/`MaintainHorizontalGroundVelocity`.

*Measured.* Honest `dx_server` 1998.3 cm; 1.3× detection on 1588.8 cm (−20.5 %, 15 resolutions, `dx_client` 1513.0 ≤ honest); detection off 2591.7 cm (+29.7 %). F1.1's "server-side rate equals the honest rate by construction" is **withdrawn**: it assumed every second of server time in resolution is either simulated or paid back. The engine does neither for part of it, and it restarts the walking pawn from rest after each payback. Both effects are gated by `bResolvingTimeDiscrepancy`, which an honest client never sets (0 lines in every honest set, incl. the ×10 and ×3 sets).

*Loss 1 — accounting (verified, cause refined).* During resolution the per-move delta is `ServerBound = min(BaseDelta + Accumulated, ServerDeltaSinceLastMovementUpdate)` (9591), `Accumulated` collects only the non-first moves of a server tick (9588) and is **cleared at every first move of a tick** (9598), and `TimeToPayBack = min(ServerBound × Rate, TimeDiscrepancy)` (9603). So the payback a server tick can credit is bounded by the client time *delivered in that tick*, and any surplus is thrown away. Velox: server 60 Hz, client one 21.7 ms stamp per 16.7 ms frame (1.3×), 100 ms netem delay with 2 % loss → arrival jitter. A tick that receives no move lets `ServerDelta` grow to 33 ms, but the next tick's single move credits only `min(21.7 + 0, 33.3) = 21.7 ms`; a tick with two moves carries 21.7 ms that the next tick cannot use (`min(43.4, 16.7)`). The server time not credited is neither simulated (the move runs at `MIN_TICK_TIME`) nor paid back: it is simply lost to the client in resolution. README sums: 5.73 s of client stamps while resolving = 4.41 s of server time in resolution, of which 3.46 s were paid back → 0.95 s uncredited = 6.2 % of the 15.41 s run, which is the "≈ −6 %". The README's wording ("client time sent during each payback is neither simulated nor counted") describes the symptom; the cause is the per-tick bound plus the discarded carry. `ResolutionRate` < 1 does not touch this bound (`TimeToPayBack + DeltaAfterPayback = ServerBound` for every rate) and lengthens the window in which it applies, so it makes loss 1 larger — F1.1's rejection stands with a better reason.

*Loss 2 — standstill after each payback (verified, now proven, not "likely").* With `Rate` 1.0 every resolving move has `DeltaAfterPayback = max(ServerBound − TimeToPayBack, MIN_TICK_TIME) = 1e-6 s` (9607). All early-outs test `< MIN_TICK_TIME`, so `PerformMovement` → `PhysWalking` runs one iteration with `timeTick = 1e-6`. Velox `CalcVelocity` (`>=` passes too) hands PhysWalking the mean velocity of a 1 µs ground step (≈ the current velocity); `MoveAlongFloor` requests `Velocity × 1e-6` ≈ 2×10⁻⁴ cm at 200 cm/s; `MoveComponentImpl` skips any sweep with `DeltaSizeSq ≤ (4 × KINDA_SMALL_NUMBER)²` = (4×10⁻⁴ cm)² and returns without moving (3283–3295; the threshold is 400 cm/s × 1 µs, so every Velox ground speed is affected). "Make velocity reflect actual move" (5869–5873) then runs because `timeTick >= MIN_TICK_TIME`: `Velocity = (NewLocation − OldLocation) / timeTick = 0`. Velox's `RestoreGroundEndVelocity` keeps the engine's velocity whenever it is not the mean within 0.05 cm/s (a clipped move), so the zero stands. The pawn's walking velocity is therefore zeroed at the first payback move of every resolution and the server pawn re-accelerates from rest after each of the 15 cycles; the 1 Hz server samples that fall into a payback read `speed2d=0.0` for the same reason. Air moves are not affected (`PhysFalling` has no reflect step); the SpeedHackRun is a ground run. For the honest path the override is never returned (12625–12635), so no honest move ever runs at `MIN_TICK_TIME`.

*Decision.* **No fix, criterion restated.** (a) Both losses have the precondition "in resolution", which an honest client cannot reach with `DriftAllowance` 0.005 (F1.1); they cost only the time-manipulating client, and the guard's purpose is that the hack gains nothing, not that the cheater is simulated fairly. (b) `MovementTimeDiscrepancyResolutionRate` < 1 stays rejected: it would remove loss 2 (payback moves would simulate `ServerBound × (1 − Rate)` > 0) but doubles the resolution window and with it loss 1, and buys honest players nothing. (c) A `Movement/` change is rejected for M6: keeping the end velocity on a sub-minimum move (`MaintainHorizontalGroundVelocity`) or overriding the virtual `ProcessClientTimeStampForTimeDiscrepancy` to credit the full `ServerDelta` would run on the server's authoritative path for every client, touch the A24–A34 band code, and benefit only cheaters; if it is ever wanted it needs its own task, ADR 0002 amendment and the full nettest default list. (d) The expected server-side result of a 1.3× client with this config is ≈ 0.8× honest; it is recorded here so a future re-run is not read as a regression.

*Criterion (replaces F1.1's and the §5.3 bullet).* With detection on: `dx_server(1.3×) ≤ 1.05 × dx_server(honest)` (no gain; judged), `dx_server(1.3×) ≥ 0.5 × dx_server(honest)` (the pawn keeps moving — a frozen pawn would mean resolution never exits or the stamps are rejected; judged), `dx_client(1.3×) ≤ dx_client(honest)` (judged), ≥ 5 `VeloxTimeDiscrepancy` lines in the run (judged); with detection off: `dx_server(1.3×) ≥ 1.2 × dx_server(honest)` (judged). All `dx_*` over 10 s of real time from the first 1 Hz sample that moved 1–600 cm, as committed in `nettest.sh`. Honest clients: 0 `VeloxTimeDiscrepancy` lines over the full default list and over BotRun ×3 / BotDuel ×3 (the per-round FAIL rule stays). The 2026-11-06 table meets this criterion (0.795 / 0.766 / 1.297, 15 lines), but its `dx_*` were computed offline with the committed window rule; the three rows are run once more with the committed analyzer so the evidence and the code agree (one round each, ~3 min of soak).

*Empty `?ServerPassword=` (ruled).* **Accepted.** The resolver rule is now uniform: an empty value at any level falls through to the next, and the password is off only when `-ServerPassword=`, `?ServerPassword=` and `VELOX_SERVER_PASSWORD` are all empty. The production path has no command-line or URL option at all (F1.3: `run-server.sh` never emits one), `nettest.sh` unsets the variable globally and exports it only around the `PasswordRun` server, and a developer who wants an open server on a host whose environment carries the variable unsets it; the `VeloxNet password=on source=env` line names the source. No explicit "off" token is added. Nit, not blocking: `ResolveServerPassword` uses `Strifind(CmdLine, "ServerPassword=")`, which also matches a `?ServerPassword=` inside a map URL given on the command line, so such a value is labelled `source=cmdline` instead of `url`; same password, same precedence — fix only if a PasswordRule row ever needs the distinction.
