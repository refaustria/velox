# ADR 0003 — Combat: GAS layout, weapons, lag compensation, projectiles, death (M2)

**Status:** Accepted (2026-10-25, project lead; human defaults pending, see STATUS open questions 12–16) (architect, 2026-10-25) → accepted by the lead when the M2 task files are written.
**Scope:** everything `dev`/`dev-hard` need to turn the M0 GAS stubs (`Combat/VeloxAbilitySet.h`, `Combat/VeloxAbilitySystemComponent.*`, `Core/VeloxPawnData.h`, `GameModes/*`) and the M1 movement component into the Q3 weapon set with server-side lag compensation, server-authoritative projectiles with client fakes, death and respawn. Builds on ADR 0001 §2 (GAS, tags, cue policy), §3 (lag-comp sketch, projectile sketch) and ADR 0002 §4/§5 with amendments A11 (crouch), A17 (recorded knockback channel is binding), A18/A19 (response snapshot, correction teleport), A24 (echoes), A32/A33 (partition principles). Pickups, powerups, HUD, scoreboard are M3; per-bone hitboxes, art, audio are M5; Gauntlet is deferred to M3 (needs no new machinery).
**Engine facts verified against UE 5.8.4 source:** `CharacterMovementComponent.cpp` l.3138–3160 (`ServerLastTransformUpdateTimeStamp` of a *remote player* pawn is `ServerAccumulatedClientTimeStamp`, i.e. that client's move-time domain, not world time — `p.NetUseClientTimestampForReplicatedTransform` default on; AI/listen pawns use world time), l.8285–8312 and l.8400–8440 (Linear smoothing: the rendered pose of a proxy sits at `SmoothingClientTimeStamp`, interpolated towards `SmoothingServerTimeStamp` = the replicated stamp), `GameStateBase.cpp` l.36 (`ServerWorldTimeSecondsUpdateFrequency` default already 0.1), `AbilitySystemComponent.h` l.1573/1725 (`ServerSetReplicatedTargetData`, `ServerTryActivateAbility` are reliable server RPCs), `AbilitySystemComponent.cpp` l.1679 (executed-cue multicast is skipped on the predicting client when the cue carries its own prediction key), `GameplayCueInterface.h` l.52 (native cue handling on the avatar actor). Lyra is not on disk; Lyra patterns below are cited from memory and marked *(Lyra, from memory)*.

## Context

CLAUDE.md non-negotiable #3: server-authoritative, client-predicted movement, lag-compensated hitscan; #2: frame rate and readability over fidelity. ROADMAP M2: GAS with Health/MaxHealth/Armor/MaxArmor and the Q3 2/3 armor rule, self-damage factor, knockback through the movement component; six weapons as data-driven abilities with Q3 defaults; hitscan rewind with a bounded window; server projectiles with client fakes; rocket jumps and plasma climbing via self-knockback; death, respawn with spawn protection, spawn selection away from enemies; unit tests for damage math, ammo, rewind pose, projectile ownership; "hits register where the client aimed" at 100 ms / 2 %.

Constraints inherited from M1: the only way velocity enters the pawn is `UVeloxMovementComponent::AddKnockback` (ADR 0002 §4); carried Velox state chains through the replay and `PrepMoveFor` restores nothing (A17) — a predicted self-knockback the replay cannot regenerate needs a *recorded* channel; the response container is snapshotted at check time (A18); corrections are followed by invisible echoes (A24); fire events must not depend on move partition (A33) — shots therefore do not travel in moves. The build host is headless: every M2 asset that can be C++ is C++ (gameplay effects, cue handling), data assets are created by the existing Python bootstrap path; Blueprint cue notifies and FX arrive in M5 under `/Game/GameplayCues` without code changes.

Units: `UnitScale 2.5` (1 Q3 unit = 2.5 cm). Q3 numbers below are vanilla `g_*`/`bg_*` defaults; CPMA variants are an open question.

## Decision

### 1. GAS layout: ASC on PlayerState, Mixed, explicit init, C++ gameplay effects

- `UVeloxAbilitySystemComponent` stays on `AVeloxPlayerState` (exists), `EGameplayEffectReplicationMode::Mixed` (owner gets full GE specs, others get tags and cues only; the PlayerState's owner is the PlayerController, which Mixed requires). Bots (M2 target dummies, M4 bots) use `AVeloxBotController : AAIController` with `bWantsPlayerState = true`, so they hold an identical ASC (ADR 0001).
- Init, both sides: `AVeloxCharacter::PossessedBy` (server) and `OnRep_PlayerState` (owning client) call `InitAbilityActorInfo(PlayerState, Pawn)` (exists); add `OnRep_Controller` → `RefreshAbilityActorInfo()` and `UnPossessed` → `InitAbilityActorInfo(PlayerState, nullptr)` so a corpse is never an avatar. **Granting happens once per PlayerState**, not per pawn: `AVeloxPlayerState::GrantDefaultAbilitySets()` (server, first possession) applies `UVeloxPawnData::AbilitySets` through `UVeloxAbilitySet::GiveToAbilitySystem(ASC, &Handles, SourceObject)`; weapon fire abilities are granted/removed by the inventory (§4). Respawn = new pawn + `InitAbilityActorInfo` + `GE_SpawnInit`, no re-grant (ADR 0001 §2).
- `UVeloxAbilitySet` (fill the M0 stub per ADR 0001 §2): `TArray<FVeloxAbilitySet_GameplayAbility{TSubclassOf<UVeloxGameplayAbility> Ability; int32 Level=1; FGameplayTag InputTag}>`, `_GameplayEffect{TSubclassOf<UGameplayEffect>; float Level}`, `_AttributeSet{TSubclassOf<UVeloxAttributeSet>}`; `FVeloxAbilitySet_GrantedHandles` with `TakeFromAbilitySystem`. Attribute sets are instanced on the PlayerState as default subobjects (`UVeloxHealthSet`, `UVeloxAmmoSet`), not granted — simpler replication setup; the `_AttributeSet` entry exists for M3 powerup sets.
- `UVeloxGameplayAbility : UGameplayAbility` *(Lyra, from memory: activation policy)*: `EVeloxAbilityActivationPolicy { OnInputTriggered, WhileInputActive, OnSpawn }`; defaults `InstancedPerActor`, `LocalPredicted`, `ReplicateNo`, `bServerRespectsRemoteAbilityCancellation = false`. `UVeloxAbilitySystemComponent` replaces the M0 press/release stub with Lyra's three-list input processing: `AbilityInputTagPressed/Released` only mark specs; `ProcessAbilityInput(float Dt, bool bGamePaused)` — called from `AVeloxPlayerController::PostProcessInput` (and from the bot controller tick in M4) — activates `OnInputTriggered` specs on press, re-tries `WhileInputActive` specs every frame while held (`TryActivateAbility` is cheap when `CanActivateAbility` fails), forwards `InputPressed/Released` to active specs. Routing rule for `InputTag.Fire`: only the fire spec whose `SourceObject` is the inventory's current weapon definition is considered (§4), so six granted fire abilities cost one `TryActivateAbility` per frame.
- **All M2 gameplay effects are C++ `UGameplayEffect` subclasses configured in their constructors** (`Combat/VeloxGameplayEffects.h/.cpp`): `UVeloxGE_Damage` (Instant, execution `UVeloxDamageExecution`), `UVeloxGE_AmmoCost` (Instant, six modifiers, one SetByCaller per ammo tag), `UVeloxGE_SpawnInit` (Instant, Override modifiers from SetByCaller: Health, MaxHealth, Armor, MaxArmor, six ammo), `UVeloxGE_HealthDecay` (Infinite, Period 1.0, execution `UVeloxDecayExecution`), `UVeloxGE_WeaponSwitching` (HasDuration, SetByCaller duration, grants `Velox.State.WeaponSwitching`), `UVeloxGE_SpawnProtection` (HasDuration, grants `Velox.State.SpawnProtected`), `UVeloxGE_Dead` (Infinite, grants `Velox.State.Dead`, removed by `GE_SpawnInit`'s `RemoveGameplayEffectsWithTags`). Tunables never live in the GE: they come from `UVeloxCombatSettings` via SetByCaller at apply time.
- `UVeloxCombatSettings : UPrimaryDataAsset` (`Content/Data/DA_CombatSettings_Default`, referenced from `AVeloxGameMode` config): `SpawnHealth 125`, `MaxHealth 100`, `HealthHardCap 200`, `SpawnArmor 0`, `MaxArmor 200`, `ArmorProtection 0.6667`, `SelfDamageScale 0.5`, `SelfKnockbackScale 1.0`, `KnockbackSpeedPerDamage 12.5` cm/s (Q3 `g_knockback 1000 / mass 200` = 5 ups), `MaxKnockbackDamage 200`, `RadiusKnockbackZOffset 60` cm (Q3 +24 u), `WeaponDropTime 0.2`, `WeaponRaiseTime 0.25`, `bSwitchWaitsForRefire true`, `MaxRewindSeconds 0.25`, `HistoryWindowSeconds 1.0`, `MaxOriginErrorCm 75`, `FireRateBurstAllowance 3`, `ProjectileForwardPredictionMax 0.1`, `MinRespawnDelay 1.7`, `ForceRespawnDelay 20`, `SpawnProtectionSeconds 0` (open question), `bSpawnProtectionEndsOnFire true`, `CorpseLifetime 3.0`, `SpawnAvoidRadiusCm 500`, `TArray<FVeloxAmmoTypeInfo{FGameplayTag Tag; FGameplayAttribute Attribute; int32 MaxAmount=200}> AmmoTypes`, `TObjectPtr<UVeloxWeaponTable> WeaponTable`, `TArray<FVeloxSpawnWeapon{Def, Ammo}> SpawnLoadout` (default MG/100; the `L_CombatTest` game mode asset lists all six). Non-shipping cvars `velox.combat.<Field>` mirror the floats as in ADR 0002 §6.

### 2. Attributes and Q3 damage math (world-free, integer semantics)

- `UVeloxAttributeSet : UAttributeSet` base with `ATTRIBUTE_ACCESSORS`, push-model `DOREPLIFETIME_WITH_PARAMS_FAST` + `GAMEPLAYATTRIBUTE_REPNOTIFY`. `UVeloxHealthSet` {Health, MaxHealth, Armor, MaxArmor; meta, not replicated: IncomingDamage, IncomingArmorDamage, IncomingKnockback, IncomingHealing (M3)}. `UVeloxAmmoSet` {Bullets, Shells, Cells, Rockets, Lightning, Slugs} — one attribute per type, as ADR 0001 says (attributes replicate individually, UI binds by attribute, GE modifiers need attribute identity; a map buys nothing for six floats). All values are integral; attributes are floats holding integers; `PreAttributeChange` clamps Health to `[0, HealthHardCap]`, Armor to `[0, MaxArmor]`, ammo to `[0, MaxAmount]` from `AmmoTypes`.
- Health/armor over the maximum decay 1 per second (Q3 `ClientTimerActions`): `GE_HealthDecay` applied by `GE_SpawnInit`, execution subtracts 1 from Health if `> MaxHealth` and 1 from Armor if `> MaxHealth` (Q3 decays armor towards max *health*).
- `FVeloxDamageMath` (`Combat/VeloxDamageMath.h`, includes only `CoreMinimal.h`, fully unit-tested) is the single implementation of Q3 `G_Damage`/`CheckArmor`/`G_RadiusDamage`, used by the execution, the projectile, and the client's self-knockback prediction:
  ```cpp
  struct FVeloxDamageInput { int32 Damage; int32 Armor; bool bSelf; bool bNoArmor; bool bNoKnockback; bool bProtected; float KnockbackScale; };
  struct FVeloxDamageResult { int32 HealthLoss; int32 ArmorLoss; float KnockbackSpeed; };   // cm/s, before direction
  static FVeloxDamageResult Apply(const FVeloxDamageInput&, const FVeloxCombatParams&);
  static int32 RadiusPoints(int32 Damage, float Dist, float Radius);                // Q3: (int)(Damage * (1 - Dist/Radius)), 0 outside
  static float ClosestCapsuleDistance(const FVector& Origin, const FVeloxHitShape&);
  static FVector RadiusKnockbackDir(const FVector& Origin, const FVector& TargetCentre, float ZOffset);
  ```
  Order (Q3): knockback speed = `min(Damage, MaxKnockbackDamage) × KnockbackSpeedPerDamage × KnockbackScale × (bSelf ? SelfKnockbackScale : 1)` from the **raw** damage; then `if bSelf: Damage = Damage / 2` (integer); then armor save = `min(Armor, ceil(Damage × ArmorProtection))` unless `bNoArmor`; `HealthLoss = Damage − save`. `bProtected` (spawn protection) → zero health/armor loss and zero knockback. Shotgun pellets are applied per pellet in a loop (Q3 rounding: 11 pellets × 10 vs 100 at once consume 77 vs 67 armor) — the execution receives `PelletHits` and loops.
- `UVeloxDamageExecution : UGameplayEffectExecutionCalculation`: captures target Armor, reads `SetByCaller.Damage`, `SetByCaller.PelletHits`, and the context `FVeloxGameplayEffectContext : FGameplayEffectContext` *(Lyra, from memory: context subclass carrying hit data)* {`FVector_NetQuantizeNormal HitDirection; FVector_NetQuantize100 HitLocation; float KnockbackScale; uint8 ShotSeq; uint8 Flags{Self, Radius, NoArmor, NoKnockback}`} plus the damage tag on the spec (`Velox.Damage.<Weapon>`, `Velox.Damage.Self` added for self hits); writes `IncomingDamage`, `IncomingArmorDamage`, `IncomingKnockback` meta attributes. `UVeloxHealthSet::PostGameplayEffectExecute` (authority only — executions are never predicted) moves them: `Armor −= IncomingArmorDamage`, `Health −= IncomingDamage`, and if `IncomingKnockback > 0` calls `Avatar->GetVeloxMovementComponent()->AddKnockback(HitDirection × IncomingKnockback, false, EVeloxKnockbackSource::Server)`; then zeroes the metas and broadcasts `OnDamaged(Instigator, Damage, Tags)`; `Health == 0` → `OnOutOfHealth`. Knockback thus has exactly one entry point and one math (`FVeloxDamageMath`), and the grace is `KnockbackGraceFor` as in M1 (100 dmg → 1250 cm/s → 0.2 s; A7).
- `UVeloxHealthComponent` on the pawn (ADR 0001) subscribes to the set's delegates and exposes `OnDeathStarted/OnDeathFinished`, `GetHealth/Armor`; UI and game mode never touch the ASC.

### 3. Knockback channels: chained (server, pads) and recorded (predicted self-knockback, A17)

`AddKnockback(FVector Impulse, bool bOverride, EVeloxKnockbackSource Source = Overlap)`; the two-argument call sites of M1 are unchanged.

- `Overlap` (pads) and `Server` (every server-side impulse: enemy rockets, the server's own self-knockback) accumulate into the existing `PendingKnockback` — chained, A17 unchanged.
- `Predicted` is accepted **only on the autonomous proxy** and accumulates into a new `FVeloxPredictedKnockback { FVector Velocity; uint8 Seq; }` `PendingPredictedKnockback`; `Seq` is the shot sequence of the fake projectile that detonated (§7). `ConsumePendingKnockback` applies both channels (predicted first, then chained; both set grace). `FSavedMove_Velox` gains `SavedPredictedKnockback` captured in `SetMoveFor` (before the move consumes it, like `SavedPendingKnockback`), `bForceNoCombine` when set, `CanCombineWith` false when either move has one. **`PrepMoveFor` assigns `PendingPredictedKnockback = SavedPredictedKnockback` iff `ShouldReplayPredictedKnockback(Saved.Seq, ConfirmedSelfKnockbackSeq)`** (wrap-aware `int8(Seq − Confirmed) > 0`), the one deliberate exception to A17's "restore nothing": this impulse has no replayable source event.
- Dedup against the server: the CMC gets `uint8 ConfirmedSelfKnockbackSeq` (server: the highest `ShotSeq` of this pawn's own projectiles that have detonated, set by the projectile on explosion whether or not the owner was in the radius; client: last value received). It is snapshotted into `FVeloxCorrectionState` at check time (A18) and sent in `FVeloxMoveResponseDataContainer` (one byte, corrections only, `SerializeOptionalValue` against 0). On a correction the client stores it before the replay; replayed moves whose predicted impulse the server has already resolved re-apply nothing (the server's `NewVelocity` already contains the real impulse, or correctly contains none), unresolved ones are kept. Residuals: (a) the server's impulse differs slightly in magnitude/time from the prediction → one small correction plus A24 echoes, like any server impulse; (b) a prediction the server never produces (fake hit a wall the real one missed) is re-applied in replays until its move is acked, at most one RTT → bounded by one extra correction; (c) out-of-order resolution (a later plasma explodes before an earlier long-range rocket) drops the rocket's predicted impulse early and the server's version arrives as a normal correction — accepted, plasma self-knockback is 75 ups. The client never sends its predicted impulse; the server never reads client knockback.
- Rejected: re-simulating the fake projectile inside the replay (needs world sweeps in `PerformMovement` and projectile state in saved moves).

### 4. Weapons: definitions, inventory, switching

- `UVeloxWeaponDefinition : UPrimaryDataAsset` (`Weapons/VeloxWeaponDefinition.h`, assets `Content/Weapons/DA_Weapon_<Name>` created by `Tools/editor/create_combat_content.py`): `WeaponTag`, `Slot` (Q3: MG 2, SG 3, RL 5, LG 6, RG 7, PG 8; 1/4/9 reserved), `DisplayName`, `TSubclassOf<UVeloxGameplayAbility_Fire> FireAbility`, `FireInterval`, `Damage`, `PelletCount`, `SpreadAngleDeg`, `RangeCm`, `bPenetratesPawns`, `MaxPenetrations`, `bBeam`, `TSubclassOf<AVeloxProjectile> ProjectileClass`, `ProjectileSpeed`, `ProjectileLifetime`, `SplashDamage`, `SplashRadiusCm`, `KnockbackScale`, `AmmoTag`, `AmmoPerShot`, `PickupAmmo`, `DamageTag`, `FireCueTag`, `ImpactCueTag`; M5 adds view-model/audio soft refs. Q3 defaults (the initial tuning, ROADMAP): MG 7 dmg, 0.1 s, spread atan(200/8192)=1.4°; SG 11 pellets × 10, 1.0 s, spread 4.9°; LG 8 dmg, 0.05 s, range 1920 cm, beam; RG 100 dmg, 1.5 s, penetrates (max 4); RL projectile 2250 cm/s, 100 direct, splash 100 / 300 cm, lifetime 15 s; PG projectile 5000 cm/s, 20 direct, splash 15 / 50 cm, lifetime 10 s. Hitscan range otherwise 20480 cm. `UVeloxWeaponTable : UPrimaryDataAsset` lists the six in slot order; the table index is the weapon's network id.
- `UVeloxWeaponInventoryComponent : UActorComponent` on `AVeloxPlayerState` (replicated): `uint16 OwnedMask` (bit = table index), `uint8 CurrentIndex` (`OnRep`), `uint8 PendingIndex`, server-only `TArray<FGameplayAbilitySpecHandle>` per weapon. Server API: `AddWeapon(Def, Ammo)` (sets bit, grants the fire ability with `SourceObject = Def` and dynamic source tag `InputTag.Fire`, adds ammo), `ResetToLoadout()` on respawn (Q3 loses everything on death), `SetCurrentIndex`. Owning a weapon = its fire ability is granted (ability specs replicate to the owner in Mixed mode, so the client can predict the first shot right after a pickup); equipping does **not** grant/remove anything. *(Lyra, from memory)* Lyra's inventory manager + equipment manager + spawned weapon instance actors are rejected: per-instance stats, equipment actors and grant-on-equip are more than six fixed weapons need, and grant-on-equip makes the first shot after a switch unpredictable for one RTT.
- `UVeloxGameplayAbility_WeaponSwitch` (one spec, `OnInputTriggered`, `LocalPredicted`, bound to `InputTag.Weapon.Slot1..9/Next/Prev`; the slot comes from the triggering input tag via the ability spec's dynamic tags): validates owned (ammo is not required, Q3), if `bSwitchWaitsForRefire` waits until the current weapon's `NextFireTime`, applies `GE_WeaponSwitching` (duration `DropTime + RaiseTime`), after `DropTime` sets `CurrentIndex` (server: authoritative; client: local prediction, `OnRep` reconciles). Fire abilities have `ActivationBlockedTags = {Velox.State.WeaponSwitching, Velox.State.Dead}`.

### 5. Fire abilities: predicted activation, target data, server resolution

Two concrete classes under `UVeloxGameplayAbility_Fire` (`WhileInputActive`, `LocalPredicted`, `InstancedPerActor`): `_FireHitscan` (MG, SG, LG, RG; pellet count, spread, beam and penetration from the definition) and `_FireProjectile` (RL, PG). Every shot is one activation that ends in the same frame; automatic fire is the `WhileInputActive` re-try. *(Lyra, from memory: `ULyraGameplayAbility_RangedWeapon` — local targeting → `OnTargetDataReadyCallback` → `CallServerSetReplicatedTargetData`, server waits on `AbilityTargetDataSetDelegate`; adopted.)*

- Fire rate is **not** a cooldown GE (predicted duration GEs re-anchor on the server echo and jitter 50 ms weapons). The ability instance keeps `NextFireTime` in local world time on each side; `CanActivateAbility` requires `Now ≥ NextFireTime`, the current weapon to be this ability's `SourceObject`, ammo ≥ `AmmoPerShot` (`CheckCost` override reading the ammo attribute). Server validation uses a token bucket per weapon instance on **server receive time** (`FVeloxFireRateBucket`, world-free: refill `1/FireInterval` per second, capacity `FireRateBurstAllowance`), which absorbs ±20 ms jitter and bounds the long-term rate exactly; a shot that finds the bucket empty is dropped with `VeloxShotRejected seq=` (Log) and the ability ends without firing (ammo re-syncs from the server value). No "aim clamp": rotation is client-authoritative in UE; the direction is only required to be unit length.
- Target data `FGameplayAbilityTargetData_VeloxShot : FGameplayAbilityTargetData` (`Weapons/VeloxShotTargetData.h`, `NetSerialize`, `TStructOpsTypeTraits WithNetSerializer`): `FVector_NetQuantize100 Origin` (the eye; Q3 muzzle = view origin), `FVector_NetQuantizeNormal Dir`, `float ViewServerTime`, `uint8 ShotSeq`, optional hint `TWeakObjectPtr<AActor> HintTarget` + `float HintTargetStamp` (§6). `ShotSeq` is a per-PlayerState `uint8` counter incremented on every predicted shot; it names the shot in validation logs, matches fake and real projectile, and keys the predicted self-knockback.
- Client flow: `ActivateAbility` → `FScopedPredictionWindow` → local shot resolution for cosmetics only (hitscan: `FVeloxHitMath` ray vs the *rendered* capsules of simulated proxies plus a world trace on the `Weapon` channel; projectile: spawn the fake, §7) → build target data → `CallServerSetReplicatedTargetData` → predicted `GE_AmmoCost` (Instant on the own ASC inside the prediction window; the known caveat that a stale replicated value can briefly overwrite the predicted one is accepted, as Lyra does) → `ExecuteGameplayCueWithParams(FireCueTag, {Location = muzzle/beam end, Normal})` locally → `NextFireTime = Now + FireInterval` → `EndAbility`. **No predicted hit marker**: the hit confirm is server-driven (Q3 behaviour; a revoked hit marker is worse than a 100 ms late one).
- Server flow: `ActivateAbility` → `AbilityTargetDataSetDelegate` → validate (bucket, `|Origin − ServerEye| ≤ MaxOriginErrorCm` else snap Origin to the server eye; `Dir` normalised) → hitscan: `UVeloxLagCompensationSubsystem::TraceShot` (§6) and one `GE_Damage` spec per victim (`SetByCaller.Damage = Def.Damage`, `PelletHits = n`, context direction = `Dir`, `KnockbackScale`), rail continues through up to `MaxPenetrations` pawns and stops at world; projectile: spawn `AVeloxProjectile` (§7) → `GE_AmmoCost` → `ExecuteGameplayCueWithParams(FireCueTag)` with the activation prediction key (the predicting client skips the echo, l.1679) and, for hitscan hits, `ImpactCueTag` at the hit location → `AVeloxPlayerController::ClientConfirmHit(uint8 ShotSeq, uint8 TotalDamage, uint8 Flags{Kill})` (unreliable client RPC; *(Lyra, from memory)* `ULyraWeaponStateComponent::ClientConfirmTargetData` idea) → `EndAbility`. LG: each 50 ms activation is a shot with its own target data (20 reliable RPCs/s, ≈ 30 B each, Q3 does the same server-side trace per 50 ms); the beam cue is a looping cue tagged `GameplayCue.Weapon.LightningGun.Beam` started by the ability on first fire and stopped on release/switch/death.
- Shotgun pellet pattern: `FRandomStream(ShotSeq ^ PlayerId)` so client tracers and server pellets agree; pellets outside the pattern are impossible.
- Cue handling in M2: `AVeloxCharacter` implements `IGameplayCueInterface::HandleGameplayCue` and forwards to `UVeloxCombatFeedbackComponent` (non-shipping debug draw: tracer line, beam, impact sphere, explosion sphere; HUD hit-marker tick and damage flash) — native handling needs no assets. `UVeloxGameplayCueManager::ShouldAsyncLoadRuntimeObjectLibraries` returns false on the dedicated server (ADR 0001); M5 adds `GCN_*` Blueprints under `/Game/GameplayCues` for the same tags.

### 6. Lag compensation: server rewind of capsule hitboxes, per-target rendered stamp

- `UVeloxHitboxComponent : UActorComponent` on `AVeloxCharacter`: `FVeloxHitboxPose GetCurrentPose() const` = `TArray<FVeloxHitShape>` (M2: one capsule from the collision capsule's current radius/half height — crouch shrinks it — at the actor transform; M5: per-bone shapes through the same type, `BoneId`, `DamageScale` stays 1 — **no locational damage, as Q3**), `GetRenderedPose()` on clients (same shape at the mesh component's smoothed transform, for the client's cosmetic trace), registers with the subsystem on authority in `BeginPlay`, unregisters on death/`EndPlay`.
- `UVeloxLagCompensationSubsystem : UTickableWorldSubsystem`, created only when `NetMode != NM_Client`, tickable objects run after all tick groups so every pawn moved this frame (autonomous pawns move inside the net-dispatch RPCs, before that). Per registered pawn a ring buffer of `HistoryLength = ceil(HistoryWindowSeconds × 60) = 60` samples `FVeloxHitboxSample { double WorldTime; float PawnStamp; FVeloxHitboxPose Pose; }` — `PawnStamp` = `CMC->GetServerLastTransformUpdateTimeStamp()`, i.e. the value the engine replicates to viewers (`ServerAccumulatedClientTimeStamp` for remote players, world time for bots/listen pawns; verified l.3138–3160). Memory: 16 pawns × 60 × ~64 B ≈ 61 KB.
- `NetworkSmoothingMode = Linear` for `UVeloxMovementComponent` (constructor; engine default Exponential). In Linear mode the rendered proxy pose is the server trajectory interpolated at `SmoothingClientTimeStamp` in that pawn's stamp domain (l.8400–8440), so the client can state exactly which pose it aimed at. `UVeloxMovementComponent::GetRenderedServerStamp()` exposes `GetPredictionData_Client_Character()->SmoothingClientTimeStamp` for simulated proxies.
- Client payload (§5): `ViewServerTime = GameState->GetServerWorldTimeSeconds() − InterpolationDelay`, where `InterpolationDelay` is measured each frame as the mean over simulated Velox proxies of `(SmoothingServerTimeStamp − SmoothingClientTimeStamp)` plus the proxies' mean age `(Now − last update receive time)`, falling back to `PlayerState->GetPingInMilliseconds()/2000 + NetworkSimulatedSmoothLocationTime` with no proxies. **Hint:** when the client's cosmetic ray intersects a rendered proxy capsule, `HintTarget` = that pawn and `HintTargetStamp` = its `GetRenderedServerStamp()`.
- Server `TraceShot(Shooter, Origin, Dir, Range, Pellets, bPenetrate, MaxPen, ViewServerTime, Hint)`: (1) world trace on `Velox_TraceChannel_Weapon` (pawn capsules **ignore** this channel — `AVeloxCharacter` constructor sets the response; world blocks) → `WorldDist`. (2) `T = clamp(ViewServerTime, Now − MaxRewindSeconds, Now)`. (3) For every registered pawn except the shooter: pose = for the hinted pawn, the sample pair bracketing `HintTargetStamp` by `PawnStamp` **if** that pair's `WorldTime ≥ Now − MaxRewindSeconds` (else fall through), otherwise the pair bracketing `T` by `WorldTime`; interpolate location/half-height linearly, rotation is irrelevant for a capsule; older than the window → oldest sample, newer than the latest → current pose. (4) `FVeloxHitMath::RayCapsule` (`Combat/VeloxHitMath.h`, world-free) per pellet ray; keep hits with `Dist < WorldDist`; nearest wins, rail collects up to `MaxPenetrations` nearest. Returns `TArray<FVeloxShotHit{Pawn, Dist, Location, PelletHits}>` and the per-shot `RewindMs` for the log line `VeloxShot seq= shooter= hit= rewind_ms= hint= dist_cm=` (Log, `LogVeloxCombat`). `velox.combat.LagComp 0` (non-shipping, server) uses current poses for the control run.
- Validation tolerances: `MaxRewindSeconds 0.25` (Q3 unlagged allowed more; modern titles 0.2–0.25 — a 250 ms-ping player hits what he sees, a 400 ms player hits late), `MaxOriginErrorCm 75` (≈ two 1/60 moves at 1400 cm/s plus radius — the fire RPC and the move RPC of the same client frame may arrive in either order), fire rate per §5.
- **Crouch (A11) decision: (c).** Geometry becomes class defaults: `AVeloxCharacter` constructor `InitCapsuleSize(37.5, 70)`, `BaseEyeHeight 55`, `CrouchedEyeHeight 40`, CMC `SetCrouchedHalfHeight(50)` (Q3 crouch box −24..16 u = 100 cm, viewheight 12 u → 16 u above the crouched centre), `NavAgentProps.bCanCrouch = true`; `UVeloxPawnData::{CapsuleRadius, CapsuleHalfHeight, EyeHeight}` are deleted along with `ApplyPawnGeometry` and the `RecalculateBaseEyeHeight` override; a Blueprint subclass may override the defaults and `PawnData->PawnClass` points at it (Lyra's model, one source of geometry, the engine's own crouch code untouched). `UVeloxMovementComponent::CanCrouchInCurrentState()` → `Super && IsMovingOnGround()` (no mid-air capsule shrink, which the engine turns into a +20 cm crouch-jump Q3 does not have; Q3's air duck is cosmetic). `CrouchSpeedScale 0.25` (A10) and the `!bWantsToCrouch` jump checks already exist; `bWantsToCrouch` travels in the engine's compressed flags, so crouch is predicted and the server snapshot (half height per sample) is authoritative for hitboxes. `create_bootstrap_content.py` stops writing the removed fields.

### 7. Projectiles: server-authoritative, client fake, dead-reckoned proxies

- `AVeloxProjectile : AActor` (`Weapons/VeloxProjectile.*`), `bReplicates`, `SetReplicateMovement(false)`, `NetUpdateFrequency 10`, `NetPriority 2.5`, `SetNetDormancy(DORM_DormantAll)` after the first replication (destruction still replicates). Replicated once (`COND_InitialOnly`): `FVector_NetQuantize100 StartLocation`, `FVector_NetQuantize10 Velocity`, `float SpawnServerTime`, `uint8 ShotSeq`, `TObjectPtr<const UVeloxWeaponDefinition> Def`, owner (engine). No `UProjectileMovementComponent`: `FVeloxProjectileSim::Advance(State, Dt)` is constant velocity, no gravity (Q3 rockets/plasma fly straight); the server moves by `AddActorWorldOffset(Delta, bSweep = true)` with a `USphereComponent` (radius 2 cm, ObjectType `Projectile`, Block WorldStatic/WorldDynamic/Pawn, Ignore `Projectile` and the `Weapon` trace channel; `IgnoreActorWhenMoving(Owner)` — Q3 missiles never touch their owner directly, only by splash). Pawn collision is at current server time, no rewind (Q3, ADR 0001). Lifetime from the definition → explode in place.
- Explosion (server): direct victim (if a pawn) gets `Def.Damage` with direction = velocity; then radius damage to every registered pawn except the direct victim: `Dist = ClosestCapsuleDistance`, `Points = RadiusPoints(SplashDamage, Dist, SplashRadius)`, LOS = world-only traces on the `Weapon` channel from the explosion origin to the capsule centre, top and bottom (Q3's five-point `CanDamage`, reduced to three), direction `RadiusKnockbackDir(Origin, Centre, RadiusKnockbackZOffset)`, `bSelf` when the victim is the owner (half damage, full knockback → rocket jump: a floor rocket at the feet gives ≈ 1250 cm/s mostly upward plus the 675 cm/s jump). Then `OwnerCMC->ConfirmedSelfKnockbackSeq = ShotSeq` (always, §3), `ExecuteGameplayCueWithParams(Def.ImpactCueTag, {Location, Normal})` on the owner's ASC (unreliable multicast — the authoritative explosion position for every client), `Destroy()`.
- Owning client: `_FireProjectile` spawns the same class locally with `bFake = true` (never replicated), from the eye along `Dir` at `Def.ProjectileSpeed`, advancing with the same sim and sweeping against world and the *rendered* capsules of proxies (`FVeloxHitMath`). When the replicated real projectile with `(Owner, ShotSeq)` arrives it is hidden on this client (`SetActorHiddenInGame`); the fake stays until it detonates locally or the impact cue for this `ShotSeq` arrives (cue location wins for the FX). **On local detonation the fake calls the self-knockback prediction**: if the owner pawn is within `SplashRadius` and has LOS (same math) → `AddKnockback(RadiusKnockbackDir × Apply(points, bSelf).KnockbackSpeed, false, Predicted, ShotSeq)`. A fake whose real counterpart never arrives (shot rejected) self-destructs after `Lifetime`. Reversal of ADR 0001's "destroy the fake, show the real one": the fake is the earlier, intent-faithful object; the real one carries authority through the cue, not through visibility.
- Server forward simulation at spawn: `FwdSim = min(PlayerState->GetPingInMilliseconds()/2000, ProjectileForwardPredictionMax)`, performed as a sweep (a hit inside the window explodes immediately), `SpawnServerTime = Now − FwdSim`. Other clients dead-reckon `Location = StartLocation + Velocity × (ServerWorldTimeEstimate − SpawnServerTime)`, sweep locally against world only for the visual stop, and explode where the impact cue says; no per-tick replication exists.
- Relevancy M2: default relevancy with `NetCullDistanceSquared` = 100 m² (whole test map) and no replication graph (ADR 0001); 16 players × 1.25 rockets/s × 15 s worst case is bounded by map geometry. Projectile-vs-projectile is ignored by the channel setup.

### 10. Readability and performance constraints

- Pawns get `UStaticMeshComponent PlaceholderBody` (capsule mesh) attached to the skeletal `Mesh` so it receives the smoothing offset, with an unlit emissive material coloured from `AVeloxPlayerState::PlayerColor` (replicated, 8-colour palette, assigned by the game mode) — bright, team-less skins exist from M2 on, and the rail lane is where the human checks hit-where-aimed.
- No dynamic lights, no Niagara, no decals in M2 (forward renderer budget); FX are debug draws until M5. Burst cues only, looping only for the LG beam (ADR 0001).
- Budgets: lag-comp sampling 16 × 60 Hz capsule copies (< 0.05 ms); per shot ≤ 16 ray–capsule tests, LG worst case 16 players × 20 Hz; bandwidth per shot ≈ 30 B reliable up + ≈ 40 B cue multicast per client; projectile spawn ≈ 60 B once; `ClientConfirmHit` 4 B. All inside the 100 kB/s client rate with 16 players firing. Server frame budget for combat ≤ 0.5 ms at 16 players.

## Consequences

- Six granted fire abilities per player instead of grant-on-equip: predictable first shot after switch and pickup; cost is a filter in input routing.
- Knockback keeps a single entry point; the recorded channel is a one-byte addition to the correction response and one saved-move field, and the A17 rule holds for everything except that one impulse.
- Hitscan truth is one server subsystem with world-free math; pawn capsules ignore the trace channel, so physics shapes never disagree with rewound shapes. The per-target stamp hint makes "hit what you saw" exact in Linear smoothing; the world-time fallback covers unhinted pawns within one server tick.
- Projectiles cost one replication each, ever; all clients see the same explosion position from the cue. The owner's fake is visibly ahead of the real one by up to RTT/2 − FwdSim; accepted.
- C++ GEs and native cue handling keep M2 buildable and testable on the headless VM; M5 swaps in Blueprint cue notifies without code changes.
- Class-default geometry (A11 (c)) removes three pawn-data fields and the two overrides that fought the engine; crouch is live with Q3 numbers.
- Fire goes over GAS RPCs, not moves: no partition coupling (A33), reliable under loss, at the cost of two reliable RPCs per shot (Lyra's rate).

## Alternatives considered

- **Fire events inside `FVeloxNetworkMoveData`** (Q3 `pmove` weapon timing): exact move-relative timing, but merged/lost/resent moves (A32) would duplicate or shift shots and GAS activation would have to be driven from `MoveAutonomous`. Rejected.
- **Cooldown GEs for fire rate** (Lyra): predicted duration GEs re-anchor on the server echo; 50 ms LG ticks would stutter. Local timers + server token bucket instead.
- **Trust-the-client hits** (Lyra default): rejected in ADR 0001.
- **Exponential smoothing + estimated interpolation delay only**: no exact rendered time exists; the per-pawn stamp domain (l.3154) would make a world-time estimate off by the client's clock offset. Linear smoothing + stamp hint instead.
- **Per-bone hitboxes in M2**: no mesh exists before M5; the pose type is already per-shape.
- **`UProjectileMovementComponent` + replicated movement**: per-tick replication for a constant-velocity body; rejected for bandwidth and determinism.
- **Destroy the fake and show the forward-simulated real projectile** (UT4, ADR 0001 sketch): a visible pop at RTT/2; the fake-stays rule is simpler and authority flows through the cue anyway.
- **Ragdoll corpses**: non-deterministic, costly, unreadable; a death pose in M5.
- **Death/respawn as gameplay abilities** (Lyra `GA_Death`): more moving parts for a fixed server-side flow.
- **Ammo as a map / single attribute with SetByCaller index**: loses per-attribute replication and UI binding.

- **B1 — Combat settings live on the PlayerState, not the GameMode (§1).** The implementer's deviation is accepted: `AVeloxPlayerState::CombatSettingsAsset` (config, `DefaultGame.ini`) is the single reference. Clients need the clamps (`PreAttributeChange` runs on replicated values) and the caps (HUD); the GameMode exists only on the server. - **B2 — Armor protection is Q3's exact constant with integer rounding (§2, §9; supersedes `ArmorProtection 0.6667`).** Q3 `g_combat.c`: `#define ARMOR_PROTECTION 0.66`, `CheckArmor`: `save = ceil(damage * ARMOR_PROTECTION); if (save >= count) save = count;` in double arithmetic — `0.66 × d` rounds to an exact integer at multiples of 50, so Q3's table is ⌈0.66 d⌉ everywhere (100 vs 100 armor → 66 armor, 34 health; the well-known rail figure). The ADR's 0.6667 is 2/3, not Q3, and differs exactly at the values that matter: 100 (rail, rocket direct): ADR 67/33 vs Q3 66/34; 50 (self-rocket after halving): 34/16 vs 33/17; 150, 200 likewise. Decision: `UVeloxCombatSettings::ArmorProtection` (float) becomes `int32 ArmorProtectionPercent = 66`; `FVeloxCombatParams::ArmorProtectionPercent`; `Save = min(Armor, Damage, (Damage × Pct + 99) / 100)` in integer arithmetic — exact ceiling, no float, `ArmorSaveTolerance` deleted (a float `0.66f × 100 = 66.00000262` would ceil to 67; the tolerance hack treated a symptom). Reproduces Q3 for every d: 1→1, 3→2, 7→5, 10→7, 50→33, 100→66, 110→73, 200→132. CPMA-style per-armor protection (50/66/75 %) fits the integer field. Corrected §9 table: 100 vs 0 → −100/0; 100 vs 50 → −50/−50; **100 vs 100 → −34/−66**; MG 7 vs 100 → −2/−5; self 100 (→ 50) vs 100 → −17/−33; 11 pellets × 10 vs 100 → 77 armor consumed (unchanged, ⌈6.6⌉ = 7 per pellet), 23 left, −33 health; 110 vs 100 → −37/−73. Cvar `velox.combat.ArmorProtectionPercent` (int); bootstrap field `armor_protection_percent`.
- **B3 — Q3 minimum damage of 1 confirmed, and extended to zero-point hits (§2, §7).** Q3 `G_Damage`: `if (targ == attacker) damage *= 0.5; if (damage < 1) damage = 1;` — the rule applies to every hit (not only self), after the halving, and knockback is taken from the raw damage before it. Q3 `G_RadiusDamage` calls `G_Damage` with `(int)points` for every entity with `dist < radius` that passes `CanDamage`, including points that truncate to 0 → 1 damage, no knockback (knockback = damage = 0). `FVeloxDamageMath::Apply` therefore treats `Damage == 0` as a hit (1 point after the rule, `KnockbackSpeed 0`) and returns nothing only for `Damage < 0` (guard) or `bProtected`. - **B4 — Health/armor decay period fixed at 1 s (confirmed, §2).** Q3 `ClientTimerActions` runs on a 1000 ms residual: health above max −1, armor above *max health* −1. A rule of the game, not a tunable: `UVeloxGE_HealthDecay::Period = 1.0` stays in code, no settings field, no cvar.
- **B5 — `FVeloxAmmoTypeInfo::SpawnAmount` is the interim spawn ammo until task 04 (§1).** Accepted for task 01. Task 04 deletes `SpawnAmount` and `VeloxEffects::MakeSpawnInitSpec` derives the six ammo values from `UVeloxCombatSettings::SpawnLoadout` (sum of `Ammo` per `Def->AmmoTag`; default MG/100), so ammo has one source of truth; `UVeloxWeaponInventoryComponent::ResetToLoadout` grants the weapons from the same list. The `L_CombatTest` game-mode asset lists all six.
- **B6 — Ability input is processed after `UpdateRotation`, not in `PostProcessInput` (§1, §5; corrects the ADR's call site).** Engine facts (UE 5.8 `PlayerController.cpp`): `TickActor` l.5644 `if (PlayerInput) PlayerTick(...)`; `PlayerTick` l.2326 `TickPlayerInput` → `ProcessPlayerInput` → `UPlayerInput::ProcessInputStack` → `PostProcessInput`; `UpdateRotation` runs afterwards at l.2364; the pawn's movement component ticks after the controller (`AController::AddPawnTickDependency`, `Controller.cpp` l.503), so the frame's move still follows the whole `PlayerTick`. Q3 builds the usercmd with the current angles (no lag). Lyra's call site is `PostProcessInput` too and has the lag — not adopted. Decision: `AVeloxPlayerController::PlayerTick(float DeltaTime)` override: `Super::PlayerTick(DeltaTime)`, then `ASC->ProcessAbilityInput(DeltaTime, DeltaTime == 0.f)` (the engine's own paused convention, l.2326); the `PostProcessInput` override is removed. Fire abilities (task 04) take the shot origin from `Pawn->GetPawnViewLocation()` and the direction from `Controller->GetControlRotation().Vector()` — never from the camera manager, which updates after all tick groups and is one frame stale. `ViewServerTime` and the hint stamp (§6) are sampled at the same point; the proxies' smoothing state is that of the last rendered frame, i.e. exactly the pose the player reacted to. Order relative to the move is unchanged: ability before the frame's move on the client, fire RPC before the move RPC on the wire, so both ends resolve the shot against the pre-move pawn position (within `MaxOriginErrorCm` for reordering). The bot controller (M4) processes ability input at the end of its tick, after setting its control rotation.
- **B7 — Instant-GE component order (§1, comment correction).** `UAbilitySystemComponent::ApplyGameplayEffectSpecToSelf` (5.8 l.1159–1165) runs `ExecuteGameplayEffect` (modifiers, executions) *before* `Spec.Def->OnApplied` (GE components). For `GE_SpawnInit` the actual order is: Override MaxHealth/MaxArmor/Health/Armor/ammo → remove Dead, SpawnProtected and the old decay → add the decay. Functionally what §1 wants; the constructor comment claiming the opposite is corrected. `URemoveOtherGameplayEffectComponent` acts on the authority only (`OwnerIsNetAuthority`), fine for a server-applied GE.
- **B8 — Death-flow contract for task 06 (§8).** `UVeloxHealthSet::OnOutOfHealth` fires synchronously inside `PostGameplayEffectExecute` of the killing execution. `AVeloxCharacter::HandleDeath` must apply `GE_Dead` synchronously in that callback (Lyra's death flow applies effects from inside the execution as well), so a second damage GE in the same server frame (two rockets, a rail through two pawns, a pellet volley split over two specs) sees `Velox.State.Dead` in `UVeloxDamageExecution` and yields zero loss and zero knockback — no corpse knockback, no second death. Before the avatar is cleared (`UnPossessed`), in this order: `ASC->CancelAbilities()`, `ClearAbilityInput()`, `RemoveAllGameplayCues()` (Lyra `UninitializeAbilitySystem`); WhileActive cues — the LG beam of task 04 — otherwise outlive the avatar. `PostGameplayEffectExecute` early-outs without authority (`IsOwnerActorAuthoritative()`): `ExecuteGameplayEffect` compiles only `WITH_SERVER_CODE`, but editor and listen clients compile it, and a future predicted application must not commit metas on a client. On clients, the corpse's `UVeloxHealthComponent` is uninitialised when the pawn stops being the avatar (task 06), so HUD bindings never read the next life's values through a corpse.
- **B9 — Grant-once records the pawn data (§1).** `AVeloxPlayerState::GrantDefaultAbilitySets` keeps the `UVeloxPawnData` it granted from; a later possession with a different pawn data (M3 classes/skins, bots with their own data) calls `TakeFromAbilitySystem` and re-grants. Design review of task 03 (`docs/reviews/m2-03-lag-compensation-review.md`, architect, 2026-10-25). B10–B17 are binding for tasks 03b, 04, 06, 08.

- **B10 — Subsystem existence is not the authority gate; registration is (§6).** `UVeloxLagCompensationSubsystem::ShouldCreateSubsystem` refuses worlds whose net mode is already known to be `NM_Client` (`UWorld::InternalGetNetMode` derives it from the pending net game URL, `World.cpp` l.9598–9675); where the mode is unknown at creation an empty instance may exist on a client and never ticks. `RegisterHitbox` accepts only authority pawns in non-client worlds. No code may assume "subsystem exists ⇒ server".
- **B11 — Sampling point and window (§6).** Samples are taken in the subsystem's `Tick` (`FTickableGameObject::TickObjects`, `LevelTick.cpp` l.1821), after `TickDispatch` (remote players' moves, l.1574), the world-time increment (l.1610) and all physics tick groups, before `TickFlush` (replication, l.1929): a sample is exactly the pose the frame replicates. Fixed 60 Hz schedule (`SampleRateHz`), one sample per frame at most; a slower server samples every frame. History window stays **1.0 s** (`HistoryWindowSeconds`, §1), capacity `ceil(max(HistoryWindowSeconds, MaxRewindSeconds + 0.1) × 60)`, read from the settings CDO at subsystem init (the asset's value is not needed there; per-shot tolerances come from the shooter's PlayerState settings, B1). Fire RPCs are processed in `TickDispatch` with `Now` equal to the previous frame's `TimeSeconds`; the live sample clamps to the newest sample's time, which keeps the result correct within one frame.
- **B12 — Stamp domain semantics (§6).** `PawnStamp` is `UCharacterMovementComponent::GetServerLastTransformUpdateTimeStamp()` as the ADR says; it advances only on frames whose move changed the transform. Rules: a run of equal stamps resolves to the newest sample carrying it (exact for a pawn at rest, whose viewers render `SmoothingClientTimeStamp == SmoothingServerTimeStamp`); a stamp at or beyond the live stamp gives the live pose; a stamp whose interpolated world time is older than `Now − MaxRewindSeconds` falls through to the world-time path. The idle→move transition (stamp jump by the idle time) is accepted: the error is bounded by one sample's displacement for at most one smoothing delay (review §3), and no alternative recording (accumulated client time) improves the bound. Float precision is a non-issue: the remote-player domain is per pawn life (prediction data per CMC), bots use world time per map.
- **B13 — Interpolation delay: proxy formula confirmed, fallback corrected (§6, supersedes the fallback sentence).** `AGameStateBase::GetServerWorldTimeSeconds()` already lags true server time by the one-way latency plus ≤ one frame (`GameStateBase.cpp` l.144–192: the delta is the running mean of replicated server time minus client receipt time). The rendered pose of a moving simulated proxy therefore sits at `GetServerWorldTimeSeconds() − [(SmoothingServerTimeStamp − SmoothingClientTimeStamp) + (Now − LastCorrectionTime)]` — the implemented mean over moving proxies (velocity non-zero, last update ≤ 0.5 s old) is right. **The fallback without moving proxies is `NetworkSimulatedSmoothLocationTime + 0.5 / SampleRateHz`** (the Linear smoother's steady-state lag after any stop — `SmoothCorrection` l.8305–8309 clamps the client to at most `SmoothNetUpdateTime` behind and nothing pulls it closer until the pawn stops again — plus the expected age of the last update); **not** `ping/2000 + …`, which counts the one-way latency twice. `ViewServerTime = GetServerWorldTimeSeconds() − InterpolationDelay`, clamped delay `[0, 1]` s.
- **B14 — Hint selection (§6).** The hint is the nearest simulated Velox proxy whose *rendered* capsule (`UVeloxHitboxComponent::GetRenderedPose`) the centre ray intersects within range, provided a world trace on the `Weapon` channel from the origin to that hit is clear; `HintTargetStamp = GetRenderedServerStamp()` (must be > 0). One hint per shot, from the centre ray also for the shotgun. Known residual, accepted: Linear smoothing restarts its lerp on every update, so at a direction reversal the rendered path cuts the corner by up to ≈ v × D / 2 for ≈ D (D ≈ 0.1 s); the stamp names the true trajectory point. Not a bug in either domain.
- **B15 — `TraceShot` contract and the origin occlusion check (§5, §6).** Steps: (1) origin validation — snap to `GetPawnViewLocation()` when farther than `MaxOriginErrorCm`, when the origin contains NaN, **or when a world trace on the `Weapon` channel from the server eye to the client origin is blocked** (new; closes the "fire from behind a wall edge" use of the 75 cm tolerance; skipped when origin and eye agree within 1 cm); (2) poses: one per registered pawn except the shooter via `SelectPose` (stamp for the hinted pawn, clamped world time for the rest, live sample as newest point); (3) per ray: world `LineTraceSingleByChannel(Weapon)` then `CollectRayHits` against the poses with `Dist < WorldDist`, nearest wins, rail takes up to `MaxPenetrations` nearest; pellets merge per pawn (`PelletHits`, nearest entry point). The server builds the pellet directions (`FRandomStream(ShotSeq ^ PlayerId)`); the client sends one direction. Corpses are not registered (task 06 unregisters in `HandleDeath`), see B17. Other non-world actors that must not stop shots (pickups, M3) set `Weapon` to `Ignore` like pawns and projectiles.
- **B16 — History discontinuity instead of reset on teleport (§6).** `FVeloxHitboxSample::bDiscontinuity` is set when the first shape's centre moved more than `UVeloxCombatSettings::HitboxTeleportDistanceCm` (new, default 150 cm; legitimate per-sample displacement is ≤ 42 cm at 2500 cm/s / 60 Hz, ≤ 84 cm at 30 Hz) since the previous sample (also for the live sample against the newest). Interpolation across a flagged later point returns the nearer-in-time pose in both domains. The history is **not** reset: a shot fired within the window at the pre-teleport pose still hits (Q3 teleporter semantics, needed in M7). Clients snap beyond `NetworkNoSmoothUpdateDistance` (384 cm), so this matches what they drew. Respawn is a new pawn and therefore a fresh history anyway.
- **B17 — Corpses are transparent to hitscan; `view_ms` in the shot log; soak assertions (§8, §9).** Dead pawns are unregistered synchronously in `HandleDeath` (B8 order), so a shot in the same or a later frame passes through the corpse to whatever is behind — a deliberate difference from Q3 (`MASK_SHOT` includes `CONTENTS_CORPSE`), chosen for readability (no "the body ate my rail"). The `VeloxShot` line gains `view_ms` = `(Now − clamp(ViewServerTime)) × 1000` beside `rewind_ms` (the hinted pawn's actual rewind when `hint=stamp`, else equal to `view_ms`). `FireRun` (task 08) asserts per rail shot at 100 ms / 2 %: `hint=stamp` for ≥ 9/10, `rewind_ms ∈ [60, 250]`, `|rewind_ms − view_ms| ≤ 60` ms with a mean ≤ 30 ms (the world-time estimate agrees with the exact stamp path), `snap=0`; the expected `rewind_ms` is ≈ one-way latency 50 + steady smoothing lag 100 + update age ≈ 8 → ≈ 160 ms, median recorded in `STATUS.md`. The `velox.combat.LagComp 0` control round must hit strictly fewer than the compensated round (a ±600 cm/s dummy moves ≈ 96 cm in 160 ms, beyond the 37.5 cm radius), otherwise compensation is not acting and the run fails.

Design review of task 04 (`docs/reviews/m2-04-weapons-hitscan-review.md`, architect, 2026-10-25). B18–B24 are binding for tasks 04b, 04c, 05, 06, 08, 09.

- **B18 — Switch timing is local on the shooter's machine and validated on the server with a tolerance (§4, §5; supersedes "Fire abilities have `ActivationBlockedTags = {Velox.State.WeaponSwitching, Velox.State.Dead}`" in §4 and the task-01 review note).** Engine facts: a replicated duration GE is re-anchored on the client to `StartWorldTime = WorldTime − (ServerWorldTime − StartServerWorldTime)` (`GameplayEffect.cpp` l.2952–2955, from `PostReplicatedAdd` l.2848); `ServerWorldTime` lags true server time by one-way latency (B13) and the server applied the GE one-way latency after the press, so the predicted `GE_WeaponSwitching`, once replaced by the server's copy, ends **one RTT** after the client's own timeline — the re-anchoring §5 forbids for fire rate. The implementer's server-side workaround (ignore the tag and the pending index for remote shooters) was built on a wrong premise: switch RPC and fire RPC share the path, so the server's switch timeline is shifted by the same latency as the shot; only jitter and the reliable-resend compression after a lost packet (≤ 1 RTT) remain. Decision, mirroring the fire-rate design: (1) `UVeloxWeaponInventoryComponent::SwitchEndTime` (local world time) is set by `UVeloxGameplayAbility_WeaponSwitch::ActivateAbility` to `Now + Wait + Drop + Raise` on every machine that runs it and cleared by `ResetToLoadout`; on the shooter's machine a fire ability activates only when `Now ≥ SwitchEndTime`. (2) On the server for a remote shooter the gate is `SwitchRemaining ≤ UVeloxCombatSettings::SwitchTimingToleranceSeconds` (new, default 0.25 s, cvar `velox.combat.SwitchTimingToleranceSeconds`, bootstrap `switch_timing_tolerance_seconds`), where `SwitchRemaining` is the largest `GetActiveEffectsTimeRemaining` of the active `GE_WeaponSwitching` (0 without one); the *pending* weapon's fire ability is accepted under the same condition, and the accepted shot finalises the switch (`SetCurrentIndex(Pending)`) before resolving. (3) `State_WeaponSwitching` is removed from the fire abilities' `ActivationBlockedTags` (the tag stays on the GE for M5 animation/UI and for the server gate); the `DoesAbilitySatisfyTagRequirements` override is deleted. A modified client gains at most the tolerance per switch; the per-weapon bucket's "fresh after a switch" burst is bounded by the switch itself. The decision lives in a world-free function with a unit test; the end-to-end check is 08's switch sequence (0 rejections at 100 ms / 2 %).
- **B19 — Fire timing: Q3 one-frame carry locally, minimum spacing on the server (§5).** Q3 `PM_Weapon` decrements `weaponTime` only while positive, so the carried remainder after a shot is at most one frame; the ADR's `NextFireTime = Now + FireInterval` loses the remainder (rate drift at frame boundaries), the implementer's `Now − NextFireTime < Interval` carries up to a full interval (bankable double tap: a 1.5 s rail twice within 10 ms by rhythm). Rule: `NextFireTime = (Now − NextFireTime ≤ FrameDt) ? NextFireTime + Interval : Now + Interval`, world-free (`VeloxFireTiming`), unit-tested. Server: the token bucket (`FireRateBurstAllowance 3`, full at first use) bounds the long-term rate but admits three simultaneous shots after any idle; it gains a minimum spacing on receive time `max(0, Interval − FireRateSpacingTolerance)` with `UVeloxCombatSettings::FireRateSpacingTolerance` (new, default 0.25 s = one RTT of reliable-resend compression at the 250 ms ping limit): rail 1.25 s, SG 0.75 s, RL 0.55 s, MG/PG/LG 0 (bucket only); violation → `VeloxShotRejected reason=spacing`. `NextFireTime` is still not checked on the server for remote shooters.
- **B20 — Machine gun spread confirmed; the task-03 review note "one entry = Dir for MG/LG/RG" is corrected (§4, §5).** The MG fires one ray with Q3 `Bullet_Fire` spread (`SpreadAngleDeg = atan(200/8192) = 1.4°`, `FVeloxHitMath::BulletSpreadDirection`); LG and RG fire `Dir`. `SpreadAngleDeg = 0` gives the laser MG for tests.
- **B21 — The pellet-pattern seed is server-authoritative; impact cues are server-only (§5; supersedes "`FRandomStream(ShotSeq ^ PlayerId)` so client tracers and server pellets agree" and the impact-cue sentence of the server flow).** With a client-chosen seed a modified client picks per shot the `ShotSeq` whose pattern best covers the target (MG spread-free, SG ≈ 11 of 11 pellets) — pattern selection. Q3 draws the seed on the server and sends it in the event. Rule: the server seeds `FRandomStream(ServerPatternSeq ^ PlayerId)` from a per-PlayerState counter it increments per accepted shot (`UVeloxWeaponInventoryComponent::AllocateServerPatternSeq`, also for listen host and bots); the client's `ShotSeq` remains for logs and for matching fake and real projectile (§7). `FVeloxGameplayEffectContext` gains `uint8 PatternSeq` (one byte on the wire), set on every hitscan cue by the server. Cue policy: the **fire cue** is predicted by the owner (keyed; the owner draws one tracer along its centre ray to its own world/proxy trace end) and multicast with the activation key by the server; **impact cues** are executed by the server only, inside `FScopedPredictionWindow(ASC, FPredictionKey(), false)` so the owner receives them (Q3: bullet impacts are server events, ≈ RTT late, always at the true location); the owner predicts no impact. One impact cue per shot: single-ray weapons at the ray end with the impact normal, the SG at the centre ray's end (or the nearest hit); receivers may rebuild the 11 pellet rays from `PatternSeq`, the context origin and `HitDirection` (M5 FX). The LG beam cue is unchanged (B23).
- **B22 — Accepted implementation details (§1, §5).** (a) The client ends each shot with `EndAbility(…, bReplicateEndAbility = false, …)`: `bServerRespectsRemoteAbilityCancellation = false` makes an end RPC a no-op anyway, and `bRetriggerInstancedAbility = true` on the fire abilities ends a server instance whose target data never came when the next activation arrives (the retrigger's `ClientEndAbility` RPC to a finished client instance is harmless). (b) One heap allocation per shot for the target data is inherent to `FGameplayAbilityTargetDataHandle`; `Request.Dirs`, `Result.Rays` and the cosmetic proxy list use inline allocators. (c) `UVeloxGameplayAbility::PrepareInputActivation(InputTag, ActorInfo, OutEventData)` — called on the CDO by `ProcessAbilityInput` for a press of an `OnInputTriggered` spec, returning `Activate | ActivateWithEvent | Skip` — is the pattern for abilities bound to several input tags; `LocalPredicted` activation carries the event data to the server, which validates it (`OwnsIndex`). (d) A press and release of a `WhileInputActive` ability within one frame fires once (Q3 tap). (e) The inventory's replication: `OwnedMask` owner-only, `CurrentIndex` to everyone (M5 view models), `PendingIndex` server-only, the owner shows a predicted index until the replicated value arrives or `PredictionTimeout` (1 s) passes; `ResetToLoadout` runs in `AVeloxPlayerState::OnPawnPossessed` before `GE_SpawnInit`, keeps surviving specs and removes the rest.
- **B23 — LG beam keep-alive lives in the inventory and is tunable (§5).** `EndAbility` clears every timer of the ability object, so the beam's keep-alive timer belongs to `UVeloxWeaponInventoryComponent::KeepBeamAlive`, called by the server per accepted LG shot; the looping cue is added with an invalid prediction key inside `FScopedPredictionWindow(ASC, FPredictionKey(), false)` so the owner receives it by replication like every other client (`ActiveGameplayCues` replicates `COND_None`, `AbilitySystemComponent.cpp` l.1852–1854; `FActiveGameplayCue::PostReplicatedAdd` skips only local client keys, `GameplayCueInterface.cpp` l.299–302). The keep-alive is `UVeloxCombatSettings::BeamKeepAliveSeconds` (new, default 0.25 s; the implemented 2.5 × interval = 125 ms flickers after one lost packet at ≥ 125 ms RTT), stopped on timeout, on `SetCurrentIndex` to another weapon, and on death by task 06 (`RemoveAllGameplayCues()` then `Inventory->StopBeam()` in the B8 block).
- **B24 — Soak warm-up and switch assertions for task 08 (§9; extends B17).** Two engine transients make the first second after a join unreliable for `view_ms`/`hint`: `AGameStateBase`'s server-time delta is a running mean whose first sample is taken during the client's load frame (`GameStateBase.cpp` l.164–193, weight decays as 1/N), and a proxy's Linear smoothing may sit up to `MaxClientSmoothingDeltaTime` behind for its first update cycle, putting the stamp outside `MaxRewind` (B12 → `fallback`). Rule: shots fired within 5 s of possession are logged and reported, not judged. `VeloxShotFired` gains `view_delay_ms` (the `InterpolationDelay` used) and `server_est` (`GetServerWorldTimeSeconds()` at fire time). `FireRun` adds a switch sequence (RG → MG → RG, the first shot of each weapon at its local `SwitchEndTime`) and asserts `VeloxShotRejected` = 0 (all reasons) and `ClientActivateAbilityFailed` = 0 at 100 ms / 2 %, once also at 250 ms / 2 % (reported); `VeloxHitConfirm` lines ≥ server `hit=1` count − 1 (unreliable RPC).

Design review of tasks 05 and 06 (`docs/reviews/m2-05-06-projectiles-death-review.md`, architect, 2026-10-29). B25–B29 are binding for 05b, 06b, 08 and 09.

- **B25 — The owner's self-splash is move-timed on both ends; the recorded channel keys on a per-life shot sequence (§3, §7, §9; supersedes "On local detonation the fake calls the self-knockback prediction" and "`OwnerCMC->ConfirmedSelfKnockbackSeq = ShotSeq` … on explosion" in §7, and the `RocketJumpRun` criterion in §9).** The server explosion is forward-simulated by `ping/2` and would land ≈ 12 moves before the client's prediction, i.e. a ≈ 70 cm correction on every floor rocket — against the movement-feel priority. Rule, as implemented: the projectile target data (`FGameplayAbilityTargetData_VeloxProjectileShot`) carries `FireMoveTimeStamp = ClientData->CurrentTimeStamp` at fire time (the end of the previous move, B6); both ends compute the shot's *world-only* flight (`FVeloxProjectileSim::WorldFlight` from the quantized origin/direction on the `Weapon` channel, owner ignored) and schedule the owner's splash at `EventTime = FireMoveTimeStamp + Flight` in the owner's move timeline (`UVeloxMovementComponent::AddMoveTimedEvent`): it runs at the end of the first live owning-client move or server-processed move whose stamp is `≥ EventTime` (`IsMoveTimeDue`, wrap-aware over `MinTimeBetweenTimeStampResets`), never in a replay and never for simulated proxies. Client: `FVeloxProjectileSim::SelfKnockback` → `AddKnockback(Predicted, ShotSeq)`; server: `GE_Damage` (`bSelf`, `bRadius`) → `AddKnockback(Server)`, then `ServerResolveSelfKnockbackShot`. The server trusts the client stamp within `LastProcessedMove ± MaxRewindSeconds`, treats a difference above half the reset period as a time-stamp reset (accepts the client value) and logs every clamp (`VeloxShotTimeClamp`); the real projectile skips the owner when its explosion matches the scheduled origin within `ProjectileRadiusCm` and arms a deadline of `FwdSim + MaxRewindSeconds` that forces a pending event, cancels the event and resolves the owner at the explosion otherwise (pawn hit, moving geometry); the owner's client cancels its event when the impact cue lands elsewhere. - **B26 — Projectile server validation uses the hitscan machinery (§5, §7).** `OnServerTargetData` of `_FireProjectile` calls `ValidateServerShot` (bucket + spacing + type + NaN origin + direction + finite view time and `FireMoveTimeStamp`, reason `time`; `VeloxShotValidation::Validate` accepts the projectile subclass and `FVeloxValidatedShot` carries the stamp), then `FinalisePendingSwitch(*Definition)` (B18), then launches. Projectile explosions confirm hits like hitscan: `ClientConfirmHit(ShotSeq, Σ health+armor removed from non-owner victims, Kill)` once per explosion with at least one non-owner victim (Q3 `PERS_HITS` excludes self).
- **B27 — Death flow: three synchronous steps, teardown on the next tick (§8; amends B8 "UnPossess last, do not defer").** Inside the killing execution, synchronously and in this order: (1) `GE_Dead`; (2) `CancelAbilities`, `ClearAbilityInput`, `RemoveAllGameplayCues`, `Inventory->StopBeam()`, `CancelAllMoveTimedEvents()`; (3) `UnregisterHitbox` (B17), `StartDeath`, `bIsCorpse = true` (replicated), death cue, `AVeloxGameMode::PlayerDied`, corpse timer. Reason: B25 applies a lethal self-splash inside the owner's `PerformMovement`, where pulling the controller and owner out from under the running ServerMove RPC is unsafe. During the ≤ 1 tick the pawn is Dead-gated (damage, ability input), unregistered (hitscan and projectiles pass through), `bIsCorpse` (excluded from spawn selection and telefrag), so nothing observable changes; respawn timers start ≤ 16 ms late. Clients: `OnRep_IsCorpse` → `ApplyCorpseState` (collision off, health component detached, body visible to the owner, colour dimmed by `CorpseColorScale`); `OnRep_PlayerState(null)` clears the avatar only if still this pawn. `FellOutOfWorld` → `EnvironmentKillDamage` on the victim's own ASC (`bNoArmor`, `bNoKnockback`, `bSelf = false`).
- **B28 — Spawn selection with an avoid radius; dummies respawn in place (§8).** `VeloxSpawn::Select` (world-free, tested): free starts only; among them, when at least one lies `≥ SpawnAvoidRadiusCm` from every living enemy, those within the radius are dropped; rank by nearest-enemy distance, pick uniformly among the farthest half; without enemies uniform over the free starts; telefrag (uniform over all starts, `Velox.Damage.Telefrag`, protection removed first) only when every start is occupied (`IsStartOccupied`: capsule volumes overlap).
