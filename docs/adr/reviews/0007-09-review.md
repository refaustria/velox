## Verdict: APPROVE WITH FOLLOW-UPS

Keep 5361018. Counting has no side effects, runs only on the server and is not replicated. `Movement/` and the
lag-compensation subsystem are untouched. Each accepted shot costs at most three casts and an integer add. One one-line change
(F1) should go in with the merge, because it affects the headless listen host that runs production. Everything else is a
follow-up task or an ADR text correction.

## What was verified (no finding)

- **Every counting line sits at an existing log site or accept point and changes no decision.** Each added line is a

  tolerance, timer or clamp moved:
  - `FireHitscan.cpp:227` (`Reject`).
  - `FireHitscan.cpp:294` (after `NoteAcceptedRemoteShot`).
  - `FireHitscan.cpp:312` (`no_lag_compensation`).
  - `FireHitscan.cpp:345–348`: reads `Result.bOriginSnapped`, which the subsystem sets exactly where it logs
    `VeloxShotOriginSnap` (`VeloxLagCompensationSubsystem.cpp:680–683`).
  - `FireProjectile.cpp`: `Reject`, the accept point, the `source=rpc` snap and the time clamp.
  - `WeaponSwitch.cpp`: the pending, late and fresh cases of `ApplyRetarget`, and the accept line in `ActivateAbility`.
  - `WeaponInventoryComponent.cpp`: `NoteMoveShotOrphan`, and the `source=move` clamp and snap.
  - `VeloxPlayerController.cpp:385` (`NotifyRpcRefused`): the count comes before the log throttle, so a refusal whose log line
    is throttled is still counted. That is correct.
  - `VeloxPlayerController.cpp:430` (`PollTimeDiscrepancy`), which is outside `Movement/`.
- **No `Movement/` or lag-compensation change.** The diff touches neither directory. The ability counts the hitscan snap from
  the result struct.
- **Server-only, not replicated.** `AnomalyStats`, `AnomalyStatsAtLastLine` and `bAnomalySummaryLogged`
  (`VeloxPlayerState.h:250–253`) are plain members, not `UPROPERTY`, and are not in `GetLifetimeReplicatedProps`. `NoteAnomaly`
  returns early without authority, so when `Reject` or `ApplyRetarget` runs on a client nothing is counted.
- **Remote shooters only.** Both fire abilities run `OnServerTargetData` only for target data the client replicated.
  `ApplyRetarget` returns early unless `IsServerForRemoteShooter` holds (`WeaponSwitch.cpp:135`), and the switch count in
  `ActivateAbility` has the same gate. Move-shots exist only for remote clients. So bots and a listen host's own player never
  count (BotRun at 125 ms printed no line), and the shot and switch counts used as denominators hold remote players only.
- **Cost.**
  - Per accepted shot: `NoteAnomalyFor` does at most 3 `Cast`s and an add.
  - Per reject: one `FName(TCHAR*)` lookup and a linear scan over at most 9 reasons. The B32 bucket and the network rate
    bound how many rejects can occur.
  - The log runs from a timer, not a tick. For each printed line it copies one inline-allocated struct and formats one
    `FString`, so the acceptance rule "never allocates per tick" holds.
  - Nine reason tags are possible: the seven `EVeloxShotReject` values, `no_weapon` and `no_lag_compensation`. The inline
    capacity is 8, so a player who hits all nine causes one heap allocation. This does not matter.
- **Logout and teardown.** `GameModeLogoutEvent` fires in `AGameModeBase::Logout`, while the controller still holds its
  PlayerState. The filter `GameMode->GetWorld() == GetWorld()` is correct when PIE runs several worlds. `Reset()` does not
  clear the counters, which is correct because a match restart keeps the connection.
- **Thresholds.** Every value in `FVeloxAnomalyThresholds` defaults to 0. `Exceeds` only appends `exceeds=` to the line.
  Nothing kicks a player, and the heartbeat does not carry the thresholds. This matches §5.4.
- **nettest.**
  - FireRun, FireRunControl, RocketJumpRun and PlasmaRun: `snaps`, `orphans` and `rpc_refused` must be 0, and `shots` must
    be greater than 0.
  - `late_retargets` must equal the number of server `mode=late` lines.
  - SpeedHackRun: the counted discrepancies must equal the `VeloxTimeDiscrepancy` lines.
  - RpcGateRun: at least 2 summary lines must show `rpc_refused` ≥ 1.

  The parser matches on `pid=` and splits on ` player=`, so player names that contain spaces do not break it.

## Findings

### F1 — `IsServerLike` is the wrong gate for printing; use the net mode (fix with the merge; ruling on open point 5)

`Net/VeloxAnomalyLog.cpp:60–62` makes every print depend on `VeloxServerKind::IsServerLike`: the interval lines (`:79`) and
the final line (`:98`). On a listen server, `IsServerLike` is true only while the local player's PlayerState exists and is
`bOnlySpectator`. `VeloxServerKind.h` reserves `IsServerLike` for skipping cost. The anomaly log is bookkeeping, and a missing
line loses evidence without saving anything.

On the production headless listen host, the host's PlayerController and PlayerState can already be gone by
`OnWorldBeginTearDown`, so every `at=shutdown` line is skipped. Every `systemctl restart` or deploy therefore loses the
summaries of all connected players. Only each player's last interval line survives, and it can be up to 60 s old.

The counters are already limited to the server's authority and to remote players. A listen host with a human player would
print nothing about that player and correct lines about its remote players, so the narrower gate protects nothing.

*Ruling:* `IsActive()` returns `NetMode == NM_DedicatedServer || NetMode == NM_ListenServer`. This is the same test that
`OnWorldBeginPlay:54` already uses for the timer. The change is one line. To verify:
- build and run the unit rows;
- run one FireRun round dedicated and one with `--server-mode listen`, each with the server stopped while the client is still
  connected; expect an `at=shutdown` line.

### F2 — `reject_share` divides by accepted shots, so a client whose every shot is rejected never reaches the threshold check (follow-up, before any threshold is set)

`VeloxAnomalyStats.cpp:87` computes `RejectShare = Rejects / max(Shots,1)`, and `:99` checks the threshold only once
`Stats.Shots >= MinShotsForRejectShare`. `Shots` counts **accepted** shots only. A client whose every shot is rejected (bucket
permanently empty, malformed payload) stays below 20 accepted shots, so it never shows `exceeds=reject_share` even though its
share is the highest possible. The share can also exceed 1, which makes the threshold hard to read.

*Ruling:* both the denominator and the minimum count use **attempts = Shots + Rejects**, so `reject_share` lies in [0,1].
The `shots=` field in the line keeps meaning "accepted".

This does not block the merge, because every threshold is 0 in M6. It must land before anyone sets `MaxRejectShare`. It also
needs an update to `Velox.Net.AnomalyRates` and to the task's acceptance text: the task specified `Rejects / max(Shots,1)`, and
this ruling replaces that.

### F3 — The two reject paths caused by server faults are counted inconsistently (low; fix with F2)

(a) At `FireHitscan.cpp:309–314`, `no_lag_compensation` counts a Reject and returns from `ResolveServerShot`. The caller then
counts the same shot as accepted (`:294`).

(b) `VeloxLagCompensationSubsystem.cpp:689` logs `VeloxShotRejected reason=nan_origin` without counting it, because the
subsystem must stay untouched. The shot is again counted as accepted.

Both paths come from a server configuration or state fault, and no client can trigger either. A NaN origin is replaced by the
validated eye, so only a shooter without a pawn reaches `:689`. Neither path moves a player's rate in practice.

*Ruling:* accept for now. With F2:
- have `ResolveServerShot` report that it rejected the shot (it already sets `LastServerShot.bRejected`), and count `Shot`
  only when it did not;
- leave `nan_origin` uncounted and say so in the header comment.

### F4 — Counters restart on reconnect (accepted, record)

When a player logs out, the engine keeps an inactive *duplicate* PlayerState in case the player reconnects. Members that are
not `UPROPERTY` are not copied, so a reconnecting player starts from zero and gets a new series of lines. The logout line has
already preserved the old totals, so an operator reading the log by name or IP loses nothing. Adding up one player's lines
across reconnects is a log-tooling question for M7. It is not a reason to replicate or persist the struct. No change.

### F5 — B32's burst after idle has no counter of its own (ADR text)

By design, an accepted burst is not an event, because the bucket lets it through. The only B32 signal the counters carry is
`rejects{rate:n}`, which a client produces by firing faster than the bucket refills. So §5.4's sentence "Same rule for B32's
per-shooter tolerance" has no measurable trigger other than the rate rejects and playtest reports. This is recorded in the
amendment; no code change.

## Rulings on the implementer's open points

1. **Honest late retargets are reported, and nettest checks counted == logged — ACCEPTED.** B42 accepts `mode=late` within
   the resend tolerance, and at 2 % loss a lost and resent switch press produces one now and then. A hard 0 would make FireRun
   flaky without catching anything. The equality check is the right regression test for the counter.

   The observed honest rate is well below the M7 trigger (0.20 over ≥ 20 switches), which stays unchanged:
   - 2 late retargets in 55 switches (about 0.04) at 50 ms one-way;
   - 0 in 11 at 125 ms one-way.

   The task's acceptance line "`late_retargets=0` for the honest client" is amended to match.
2. **Hold rows move no counter — ACCEPTED. The task text that expected `orphans ≥ 1` was wrong.** B36 validates the origin at
   the fire stamp, so there is no snap. B35/B38 adopt the held projectile RPC through its move-shot record, so there is no
   orphan. A held RPC still *arrives*; an orphan needs one that never does. The hold shows up only in `late_ms` and
   `VeloxShotLate`, which is the intended design. As a result, no row exercises the orphan counter end to end (see follow-up
   T2).
3. **No 2× rate row; `velox.combat.DebugFireRateScale` is WANTED as a follow-up, not blocking.**
   - It is a client-side cvar, compiled only under `#if !UE_BUILD_SHIPPING`. It divides the client's own refire interval and
     its prediction by the scale, and the server ignores it. The server's B32 bucket then rejects the excess shots.
   - Development clients are not distributed (§5.1), so the cvar exposes nothing to players.
   - A new nettest row `FireRunRate` (scale 2.0, MG or plasma) asserts:
     - `rejects{rate}` ≥ 1;
     - `reject_share` > 0;
     - damage per second on the server is not above the honest row's.

   See T1.
4. **Line format — ACCEPTED as implemented:**
   - `at=<interval|logout|shutdown>` is added;
   - `pid=` replaces `id=` (the F3/F6 key rule);
   - `player=` comes last, because names may contain spaces;
   - values are cumulative, with `(+delta)`;
   - `fresh_retargets=`, `late_share=` and `reject_share=` are added;
   - an optional `exceeds=` comes before `player=`.

   This line is now the contract for every evaluator, and the amendment records it.
5. **`at=shutdown` lines go missing on the headless listen host — confirmed. Fix per F1** (gate on the net mode, not on
   `IsServerLike`).

## Amendment text for ADR 0007 (append under "Amendments" after merge)

- **F4 — 2026-11-11 — task 09 rulings: anomaly line format, print gate, denominators, what the hold rows show (Opus 5.5 for
  architect; review `docs/adr/reviews/0007-09-review.md`).**

  *(i) Line format (replaces the §5.4 field list):* `VeloxAnomaly at=<interval|logout|shutdown> pid=<PlayerId> shots=N(+d)
  switches=N(+d) rejects{reason:N(+d),…} snaps=N(+d) clamps=N(+d) late_retargets=N(+d) fresh_retargets=N(+d) orphans=N(+d)
  rpc_refused=N(+d) discrepancies=N(+d) late_share=0.00 reject_share=0.00 rtt_ms=N [exceeds=a,b] player=<name to end of
  line>`. Values are cumulative since login; `(+d)` is the change since that player's previous line; evaluators key on
  `pid=`. `shots` counts the accepted shots of remote shooters. `switches` counts their accepted switch presses: new switches
  plus `pending` and `late` retargets. Bots and a listen host's own player never count. Counters are not carried across a
  reconnect; the logout line preserves them.

  *(ii) Thresholds:* the thresholds are the config struct `[/Script/Velox.VeloxAnomalyLog] Thresholds=(MaxLateShare=…,
  MinSwitchesForLateShare=20, MaxRejectShare=…, MinShotsForRejectShare=20, MaxOriginSnaps=…, MaxTimeClamps=…,
  MaxMoveShotOrphans=…, MaxRpcRefused=…, MaxDiscrepancies=…)`, not a cvar named `velox.net.AnomalyKickThresholds`. All values
  are 0 (off). Exceeding a threshold only appends `exceeds=` to the line. `reject_share` is rejects divided by attempts
  (accepted plus rejected shots), and its minimum count is on attempts (task 09 follow-up T1).

  *(iii) Print gate:* lines are printed on any `NM_DedicatedServer` or `NM_ListenServer` world, not only where
  `VeloxServerKind::IsServerLike` holds, so the headless host's `at=shutdown` lines survive teardown.

  *(iv) What the counters can and cannot show:* a fire RPC that is held but delivered (`DebugHoldShotRpc`) moves no counter.
  B36 validates at the fire stamp, and B35/B38 adopt the RPC through its move-shot record; only `late_ms` and `VeloxShotLate`
  show the hold. An orphan needs an RPC that never arrives. B32's accepted burst after idle is not an event, and its only
  counted signal is `rejects{rate}`. The "same rule for B32" trigger therefore reads: a player's `rejects{rate}` divided by
  attempts is well above the honest distribution seen on the public server. The number is set from the first week of the
  public anomaly log, together with the T1 `FireRunRate` row, or the trigger is a playtest report.

  *(v) Honest baseline:* an honest client at 50 ms one-way and 2 % loss shows about 1 late retarget per 25–30 switches
  (`late_share` ≈ 0.04). nettest checks that the counter equals the server's `mode=late` lines, and fails an honest row on
  non-zero `snaps`, `orphans` or `rpc_refused`. The M7 trigger for the move-time switch gate (`late_share` > 0.20 over ≥ 20
  switches) is unchanged.
