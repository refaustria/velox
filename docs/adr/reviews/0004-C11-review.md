# Review — ADR 0004 C11, free-spectate death camera (task m4-followups/04)

**Reviewer:** architect, 2026-10-31. **Code:** branch `post-m4`, merge 5f5fec6 (feature commit b0ecae0; diff `1be44ee..5f5fec6`, `Source/`, `Tools/`, `infra/`). **Scope judged:** authority and race order between `ClientBeginDeathSpectate`, `OnRep_Pawn` and the respawn; respawn during the spectate; intermission; logout; the view-point clamp and the abuse surface of a dead player's camera in a competitive FPS; the late-unpossess `SetPawn` override; the implementer's questions (a) `-ini` vs cvar, (b) lazy nav-bounds cache, (c) `?SpectatorOnly=1` controllers. ## Verdict: APPROVE WITH FOLLOW-UPS

Keep 5f5fec6 on `post-m4`. The follow-ups are in `docs/tasks/m4-followups/04b-spectate-intermission-and-spectator-pc.md`; D1 and D2 must land before the M4 follow-ups close, the rest are small. ADR 0004 C11 gains a third amendment (this review's rulings, appended to the ADR).

## What is right (and is now the rule)

1. **State machine, both ends.** Server: `CompleteDeath` keeps B8/B27's order (corpse state, `UnPossess`, step 5) and only then `NotifyControllerDied` → `BeginDeathSpectate` → `ChangeState(NAME_Spectating)` → `ClientBeginDeathSpectate`. Every exit is the engine's own transition and is caught in one place, the `ChangeState` override: `Playing` (`OnPossess` on the server, `ClientRestart_Implementation` on the client), `Inactive` (`EnterIntermission` + `ClientGotoState`), `PlayerWaiting` (`Reset`/`ClientReset` at the level reset), and `EndPlay` for the logout. `EndSpectatingState` destroys the spectator pawn and clears `bPlayerIsWaiting` on both ends (engine fact d); `AVeloxGameMode::TryRespawn` → `RestartPlayer` → `RestartPlayerAtPlayerStart` → `Possess` runs with `MustSpectate` = `IsOnlyASpectator()` = false, so the respawn path is byte-for-byte the pre-C11 one. Correct by reading.
2. **The client/server order is irrelevant by construction.** On the owning client three orders are possible for `Pawn = null` (controller property, `OnRep_Pawn`) vs `ClientBeginDeathSpectate` (reliable RPC on the same actor channel):
   - property first, RPC second (the classic driver's order inside one bunch: `FObjectReplicator` writes properties, then queued RPCs): `SetPawn(null)` → engine `AutoManageActiveCameraTarget(this)`; RPC → `ChangeState(Spectating)` → `BeginSpectatingState` spawns the pawn, the override places it at the eye and views it. If a `PlayerTick` runs between the two the client goes `Inactive` first (`IsInState(Playing) && GetPawn()==NULL`), and the RPC's `ChangeState(Spectating)` leaves `Inactive` normally;
   - RPC first, property second: the client spawns the spectator while `Pawn` is still the corpse (`BeginSpectatingState` does not unpossess on a client), then `OnRep_Pawn(null)` → `SetPawn(null)` → engine `AutoManageActiveCameraTarget(this)` steals the view → the override's post-`Super` check puts it back on the spectator pawn. Harmless side effects for ≤ ½ RTT: `GetFocalLocation()` syncs the corpse eye (`GetPawnOrSpectator` prefers `Pawn`), `OnRespawnInput`'s `GetPawn()` guard blocks a respawn press;
   - RPC when already `Spectating` (the engine's 2 s `ClientGotoState(Spectating)` self-heal arrived first): `ClientBeginDeathSpectate_Implementation` places the pawn without a state change.
   None of the three needs a fix. The implementer's "late `OnRep_Pawn`" override is the piece that makes order two safe; see item 5.
3. **Respawn during the spectate.** `OnPossess` → `ClientRestart` → `ChangeState(Playing)` on the server; the client follows in `ClientRestart_Implementation` → `ChangeState(Playing)` (engine fact d). If `ClientRestart` beats the pawn's channel the client stays `Spectating`, keeps flying, and its 4 Hz sync hits the server's wrong-state branch (`Super::ServerSetSpectatorLocation_Implementation`: `AcknowledgedPawn != GetPawn()` → `SafeRetryClientRestart`), which is the engine's own repair loop; the override passes that branch through untouched. The new pawn's `VeloxShotSeqReset` may precede the client's `end reason=respawn` (pawn initialised with the PlayerState's ASC before `ClientRestart`) — the nettest rule was adjusted correctly for that.
4. **Intermission while spectating** (time-limit end with a dead player): `EnterIntermission` moves a death-spectating PC to `Inactive` on the server and sends `ClientGotoState(Inactive)` before `ClientEnterIntermission` (both reliable, same channel, so in order); the client destroys its spectator pawn in `EndSpectatingState`, `BeginInactiveState`'s `SetPawn(nullptr)` no longer triggers the override (`bDeathSpectating` was cleared first), and `SetViewTarget(camera)` lands last. The level reset then goes `PlayerWaiting` → `Playing`. Correct. The *other* order — intermission first, death completion second — is D1.
5. **The late-unpossess `SetPawn` override is safe.** Its condition is `!InPawn && bDeathSpectating && IsInState(Spectating) && GetSpectatorPawn() && GetViewTarget() != GetSpectatorPawn()`. The `SetPawn(nullptr)` callers on the owning client are: `OnRep_Pawn` (the case it is for), `BeginInactiveState` (state is already `Inactive` and `bDeathSpectating` already false, since the `ChangeState` override runs `EndDeathSpectate` before `Super`), `OnUnPossess` (early-outs with no pawn), `ClientRestart` of a torn-off pawn (engine edge, then no spectator pawn survives the state change). On a dedicated server `GetSpectatorPawn()` is null, on a listen host the host's own pawn is local; `SetViewTarget` inside `OnRep_Pawn` is an ordinary camera-manager call. Approved as a pattern; it must stay the *only* place that fights `AutoManageActiveCameraTarget`.
6. **Unreplicated pawn — the claim holds, for a reason the ADR did not state.** `APawn::PossessedBy` calls `SetReplicates(true)` for every player-controller possession in a networked game, which would undo `SpawnSpectatorPawn`'s `SetReplicates(false)` on a listen host; `ASpectatorPawn::PossessedBy` (UE 5.8.4 `SpectatorPawn.cpp`) checks `bReplicates` and skips `APawn::PossessedBy` entirely when it is false. `AVeloxSpectatorPawn::PossessedBy` calls `Super` (= `ASpectatorPawn`), so the chain is intact. Recorded in the amendment as fact (a)'s second correction; the rule "the pawn never touches `bReplicates`" stays.
7. **Clamp.** World-free, unit-tested, applied before `Super` so `LastSpectatorSyncLocation` (the relevance view point, fact b) only ever holds an accepted point; non-finite input falls back to the last accepted point; the speed step measures `Dt` from the last *accepted* point with the 1/60 s floor and is seeded with the death eye at the server time, so a lost or bunched 4 Hz packet cannot trip it. The sync-rate ruling (keep the engine's 4 Hz) is honoured — no second send path, and the soak's `10 ≤ syncs ≤ 20` is the right guard against one appearing.
8. **Dead ≠ spectator** is pinned where it matters: `UVeloxHUDViewModel::bSpectator` and the item-timer rule read `IsOnlyASpectator()`; `RequestJoin`/`SetPlayerReady` refuse non-spectators; `AGameMode`'s player/spectator counters follow `MustSpectate` — a dead player never counts as a spectator anywhere.
9. **Bots and dummies** take neither branch (`IsPlayerController()` false); nothing under `Bots/` moved; `BotRun`/`BotDuel` respawn lines unchanged in the soak.
10. **Soak hooks** (`serverKill`, `ServerKillSelfTest`) follow the `serverHaste` pattern: `_Validate` fails in shipping, the implementation is compiled out, it damages only the caller's own live pawn with environment damage (a scored suicide, same as `velox.combat.KillSelf`). Acceptable.

## Abuse surface (competitive reading)

- **A modified client gains no information a dead honest player lacks.** The spectator pawn exists only on the owning client; the server never reads its position for anything but `LastSpectatorSyncLocation`, which feeds relevance and priority only. On Velox arenas every pawn is inside `NetCullDistanceSquared` (150 m) and pickups are `bAlwaysRelevant`, so the honest dead player already receives everything; flying through walls client-side or sending a forged view point adds nothing. The clamp is hygiene for the server's view point, as the ADR says; it is not a security boundary and the review does not ask it to be one.
- **The synced point reaches no gameplay system.** Not the lag-compensation rewind (`BuildShotTiming` uses the shooter's own `ViewServerTime`; a dead player fires nothing), not hit tests, not spawn selection (`ChoosePlayerStart` reads living enemies' positions), not the knockback or damage path. Verified by reading the C11 call sites: `GetPlayerViewPoint` is the only consumer.
- **The RPC while alive.** The override passes a non-spectating caller straight to `Super`, whose wrong-state branch answers once per server frame with `ClientGotoState` + `ClientSetViewTarget` (reliable). A client can make the server send itself two reliable RPCs per frame; that is the engine's pre-existing behaviour, affects only the sender's connection, and is not C11's to fix.
- **The honest feature is the real exposure.** A dead FFA player may scout for up to `ForceRespawnDelay` = 20 s and pick the respawn moment with full information; Duel is capped at 5 s (human decision 2026-10-31). This review does not change that; it records that the M6 deferred item "server-side gating of what spectators receive" must treat *dead players* as spectators for gating purposes, otherwise the gate will leak through the death camera. A playtest may still flip FFA to `Corpse` or lower the delay through data alone.
- **Camera after respawn.** A client that ignores `ClientRestart` keeps its free camera while its pawn stands idle on the server. Any client can render from any camera it likes; only server-side relevance/occlusion gating (M6) mitigates that class, and C11 did not widen it.

## Defects (ranked)

**D1 — Medium — the victim of the match-ending frag free-flies through the intermission** (`AVeloxCharacter::HandleDeath`, `AVeloxGameMode::NotifyControllerDied`, `AVeloxPlayerController::EnterIntermission`). Evidence: `HandleDeath` calls `GameMode->PlayerDied` → `RequestMatchEvaluation` → `SetTimerForNextTick(EvaluateMatch)` *before* it sets `SetTimerForNextTick(CompleteDeath)`. Both run on the next tick with equal expire times; `FTimerManager` pops the first-pushed of two equal keys first in practice, so for a frag-limit kill `EvaluateMatch` → `SetPhase(PostMatch)` → `EnterPostMatch` → `SendIntermissionTo` runs while the victim still possesses the corpse: `EnterIntermission`'s guard `bDeathSpectating && IsInState(Spectating)` is false, it sets `bInIntermission`, `SetIgnoreMoveInput(true)` and the camera, and `ClientEnterIntermission` goes out. Then `CompleteDeath` → `UnPossess` (the view target is the camera, so `OnUnPossess` leaves it) → `NotifyControllerDied` → `BeginDeathSpectate` → the client spawns a spectator pawn and views it: the player who was just fragged for the win sees a frozen free-fly camera (move input ignored) instead of the intermission camera until the level reset. The `Corpse` rule has the same race (`SetViewTarget(Corpse)` overrides the camera). Not a desync — the reset's `ClientReset` → `PlayerWaiting` ends the spectate cleanly — but it is the single most common match end. The nettest never reaches a frag limit, the unit test calls `EnterIntermission` only *after* the spectate began. **Fix (order-independent, do not rely on timer order):** in `NotifyControllerDied`, when the dying player controller is already in the intermission (`VeloxPC->IsInIntermission()`, which covers both `bInIntermission` and a replicated `PostMatch` phase; for a non-Velox PC `bMatchRulesEnabled && Phase == PostMatch`), take neither branch, leave the view target alone and log `VeloxDeath step=6 spectate=intermission`; keep arming the pending respawn as today (`TryRespawn` refuses at PostMatch, `ClearAllPendingRespawns` clears it at the reset). **Regression test:** in `Velox.GameMode.DeathSpectate`, kill, call `W.PC->EnterIntermission(nullptr)` *before* the tick that runs `CompleteDeath`, advance, assert not spectating, no spectator pawn, `IsDeathSpectating()` false, view target unchanged, step-6 line says `intermission`.

**D2 — Medium (pre-existing; decision (c)) — `?SpectatorOnly=1` logins get a plain `APlayerController`.** `AGameModeBase::SpawnPlayerController` uses `ReplaySpectatorPlayerControllerClass` (engine default `APlayerController`) for that option, so a pure spectator has no Velox binds (`Join`, `Ready`, scoreboard, menu), no view-point clamp, and — more important than C11 — every `Cast<AVeloxPlayerController>` in `SendIntermissionTo` (three call sites) and in the UI (`VeloxHUD.cpp:99`, `UVeloxUserWidget::GetVeloxPlayerController`) silently yields null: spectators get no intermission view and no scoreboard Ready/Join button. ADR 0004 §5 assumes a Velox controller for spectators. **Decision: yes.** `AVeloxGameMode` constructor: `ReplaySpectatorPlayerControllerClass = AVeloxPlayerController::StaticClass();`. Consequences: the spectator pawn's `SetupPlayerInputComponent` then binds the Velox actions from `GetInputConfig()` = `UIInputConfig` (`DA_InputConfig_Default`, the same asset as the pawn data's), the `bAddDefaultMovementBindings` fallback stays for a missing config only; `RespawnInputActions` on a pure spectator reach `TryRespawn` with no pending entry (no-op); M7 replays inherit the Velox controller, which is wanted. **Acceptance:** a `Velox.GameMode.ModeDefinitions` row asserting the class; `BotDuel` PASS with the spectator client logging no `engine default spectator bindings` line and a `VeloxMatch intermission` line at PostMatch if the run reaches it.

**D3 — Low — view snap at spectate begin on a remote client** (`AVeloxPlayerController::PlaceDeathSpectatorPawn`). The client's control rotation is overwritten with the server's `DeathSpectateRotation`, which is the client's rotation as of the last `ServerMove` — up to one RTT plus the B27 tick stale. Mouse movement in that window is undone when the spectator appears: a visible snap on a flick-death. Fix: on a client (`GetLocalRole() < ROLE_Authority`) keep the current control rotation and apply only the server's eye *position*; the listen host and the standalone test keep the server rotation (identical there). The eye must stay the server's: the corpse position is server-authoritative.

**D4 — Low — intermission guard covers only death spectators** (`EnterIntermission`). A pure spectator stays `Spectating` with its pawn alive and merely gets `SetViewTarget(camera)`; its flight input still moves the pawn and the engine's 2 s self-heal keeps it in that state. Pre-existing, becomes reachable through D2. Fix inside the same function: drop the `bDeathSpectating` condition — any `Spectating` PC goes `Inactive` for the intermission (the level reset restores `PlayerWaiting`; `AGameModeBase::RestartPlayer` → `MustSpectate` keeps a pure spectator pawnless, and `APlayerController::Reset` sets `bPlayerIsWaiting = !IsOnlyASpectator()`). Verify in the harness with `StartSpectatingOnly()`.

## Nits (no task needed; fold into 04b where the file is touched)

- `clamps=0` in the soak is strict. A classic-driver client never produces order two above, but if it ever did after an airborne death, the first sync is the corpse eye after a drop of up to `CorpseDropMaxCm` (3000 cm) against the pre-drop seed: one `speed` clamp, harmless, soak red. Leave the rule; add the sentence to the nettest comment so the next reader does not chase it.
- `NumSpectatorSyncs`/`NumSpectatorClamps` count for pure spectators too and are only reset by `BeginDeathSpectate`; `end_server` logs only for death spectates. Cosmetic.
- `GetSpectateBounds` caches for the lifetime of the game mode (one map); say so in the header comment. Accepted as is, see (b).
- `BeginDeathSpectate` seeds `LastAcceptedSpectatorPoint` twice around `ChangeState`; the first seed is dead code (the `ChangeState` override resets only when *leaving* `Spectating`, and a dying controller is in `Playing`). Keep one, after the state change, with the comment.
- HUD: with the CI cvar `velox.combat.ForceRespawnDelay` the client's prompt/countdown still read the asset's 20 s. CI-only; the cvar is non-shipping. Document in `infra/ci/README.md`, no code.

## Decisions on the implementer's questions

- **(a)** Accepted. `UVeloxCombatSettings` is a data asset, not a config class; `-ini:Game:` cannot reach it and the ADR named the cvar as the fallback. The C11 (2) text is amended to name the cvar as the mechanism, not the fallback. No production code reads it in shipping.
- **(b)** Accepted. `UWorld::InitializeActorsForPlay` registers components before `InitGame`, but the implementer measured otherwise for brush volumes; a lazy cache on first sync is strictly more robust and the volumes are static per map. Keep; add the lifetime comment (nit above).
- **(c)** Yes — D2.

## Test gaps

- The remote-client race (property vs RPC order) is not unit-testable and the nettest exercises the classic order only; accepted, the override makes the other order safe by reading (item 2).
- D1 has no test in either layer; the 04b task adds the unit case. A frag-limit nettest is not worth its runtime.
- D2/D4: the BotDuel spectator client is the natural soak; the task re-runs it.

## Rulings recorded in ADR 0004 (amendment 3 to C11)

(i) No death camera for a controller already in the intermission (D1). (ii) `ReplaySpectatorPlayerControllerClass = AVeloxPlayerController` (D2; §5's "Velox spectator controller" made explicit). (iii) A remote client keeps its own control rotation at spectate begin (D3). (iv) Every `Spectating` PC goes `Inactive` at the intermission (D4). (v) Fact (a), second correction: `ASpectatorPawn::PossessedBy` is why `APawn::PossessedBy`'s `SetReplicates(true)` does not re-enable replication. (vi) C11 (2): the soak sets the forced delay through the non-shipping cvar.
