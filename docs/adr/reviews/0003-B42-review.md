## What is right (and is now the rule)

1. **Lifecycle (open point a) — ratified.** The switch ability is an *instant, validated, predicted command*; all switch state (pending target, drop timer, switch end, predicted index, prediction chain) lives in `UVeloxWeaponInventoryComponent` on every machine. `EndAbility(…, false, false)` inside `ActivateAbility` is a sanctioned GAS pattern: `ClientActivateAbilitySucceed` finds no live instance and logs Verbose, `ConfirmActivateSucceed` is harmless on an ended instance, and the press routing in `ProcessAbilityInput` (`Spec->IsActive()` → forward, else `PrepareInputActivation`) is untouched. The pre-B42 `WaitDelay`-held instance was the only reason retargets needed ASC surgery; removing it is the simplest design that meets the rule. B37 (iii) extended to the owning client is the consistent consequence.
2. **Q3 fidelity.** (a) and (b) match `PM_Weapon`: during `WEAPON_FIRING`/`DROPPING` only `cmd.weapon` changes (retarget, drop end fixed, the current weapon re-raised with no shortcut); during `RAISING` `PM_BeginWeaponChange` adds 200 to the running `weaponTime` (= `SwitchStartWait(refire, remaining raise)`); the current weapon again is a no-op in the raise. Total-time rule stated and tested.
3. **Rollback paths are complete for every server refusal.** GAS `CanActivateAbility` refusal → `ClientActivateAbilityFailed` → key's rejected delegate (the engine's own contract for predicted work; both are reliable RPCs sent at call time, so they precede the key catch-up property update of the same frame). `ActivateAbility` refusal → `ClientRejectSwitch(PredictionKey)` (reliable, same actor channel, sent before `ClientActivateAbilitySucceed`), keyed on `LocalSwitchKey` so it does not depend on the delegate map. Every refusal is RPC'd, so the echo rule below can never swallow a rejection.
4. **Server classification** (`ClassifyRemoteRetarget`) is world-free, unit-tested, and the `Late` branch is bounded by the one tolerance already in B37 (ii). Reliable in-order delivery guarantees a retarget RPC is processed before any fire RPC the client sent after it; `Late` + `GetSwitchRemaining ≤ Tol` keeps the fire gate consistent for honest jitter up to 0.5 s. Cheat surface (open point b): ≤ Drop + Raise once per switch, same order as B37 (ii) — accepted, deferred to the M6 move-time switch gate.
5. **Echo rule** (`StalePredictions`, `OnRep_CurrentIndex`): correct by reading for the chain cases (echo of an older step stands; coalesced replication skipping a step confirms silently; quick switch-back equal to the stale replicated value is kept). It is exercised only when RTT > ≈ 0.2 s (second drop end before the first echo), which the CI nettest at 100 ms RTT does not reach — hence follow-up 1.
6. **Bots/listen host** run the shooter path (`ApplyRetarget` local branch); `VeloxBotCombat` checks both current and pending before pressing, so bots never press the lowered weapon (open point e needs no action). `SwitchRetargetLocal` runs on an AI-controlled authority, i.e. the bot path is the tested path.
7. **Out-of-scope touches** are acceptable: `FireRun.json`/`nettest.sh` are required by acceptance criterion 2 ("a new or extended nettest script/phase"); the `VeloxScriptedInputComponent::SelectWeaponSlot` line is the harness mirror of the B42 no-op rule.

## Defects (ranked; none blocking)

**D1 — Medium — a rejected *retarget* rolls back the whole switch** (`UVeloxWeaponInventoryComponent::CancelLocalSwitch`). Chain: switch key1 A→B accepted; retarget key2 →C refused by the server (only reachable via a predicted pickup of C the server refuses, ADR 0004 §2, or a `CommitAbility` failure). The server still runs A→B; the client drops pending, `SwitchEndTime` and the prediction, shows A and may fire A at once — those shots are rejected (`Definition != current/pending`) until B replicates (≈ latency + remaining drop), then A→B pops with no correction logged. Fix: remember the pre-retarget target with the key (`{Key, PreviousPending}`); on cancel of a retarget key whose switch is still pending, `RetargetPendingIndex(PreviousPending)` and keep timer/switch end; full rollback only for a non-retarget key.

**D2 — Low — no client-side switch-state reset at a new life.** `ResetToLoadout` is server-only; the owning client clears nothing at respawn (`AVeloxCharacter::InitAbilityActorInfo` resets only `ShotSeq`). The drop timer's `State_Dead` check covers a death during the drop only because `MinRespawnDelay` (1.7 s) happens to equal the longest wait + drop (RG 1.5 + 0.2) — two unrelated tunables. An expired `PredictedIndex` also survives into the next life and produces a spurious `VeloxWeaponSwitchCorrection reason=timeout` on the first OnRep that precedes a new prediction. Fix: `ResetLocalSwitchState()` (pending, timer, `SwitchEndTime`, predicted index + chain, `LocalSwitchKey`) called next to `ResetShotSeq`; log corrections while `State_Dead` at Verbose with `reason=dead` so the nettest metric stays clean once death scripts are judged.

**D3 — Low — `nettest.sh` server retarget count includes `mode=local`** lines (a listen host or a bot retargeting on the server), so `server saw N … client made M` would fail as soon as a bot appears in a FireRun-family script. Filter `mode != local` for `retarget_s`.

**D4 — Test gap (open point d).** The echo/correction decision in `OnRep_CurrentIndex` (≈ 12 lines on three ints and a 4-entry list) has no unit test and no nettest coverage at the RTT where it matters. Failure modes: flicker (echo not recognised) or a swallowed override (non-rejection server change misread as echo — only death/`ResetToLoadout` qualifies, bounded by `PredictionTimeout`). Not a merge blocker: honest-path impact is cosmetic and ≤ 1 s. Required in 02b: extract the decision into a world-free function (project pattern: `ClassifyRemoteRetarget`) and test it; add a report-only `FireRun --lag 125` row where the stale path is reachable.

## Nits
- `CancelLocalSwitch` logs a correction even when the key is not the latest (then nothing is rolled back); say so in the line (`applied=0/1`).
- `OnRep_CurrentIndex`'s `OldEffective` uses an expired `PredictedIndex`; harmless for the delegate, misleading in logs.
- Header comment of `CompleteSwitchEarly` says "none in practice" — the loop in `CompletePendingSwitch` can go once D4's extraction lands; leave for now.
