## What is right (and is now the rule)

1. **The dedicated server never loads a cosmetic** — verified path by path, not only by the reflection test. `UVeloxAssetManager::LoadCharacterCosmetics` returns before any request on `IsCosmeticsFreeWorld` (process flag *or* world net mode, so PIE dedicated servers are covered); `AVeloxCharacter::RequestCharacterCosmetics`, `EnsureViewModel`, `BindWeaponWorldMesh`, `RefreshWeaponWorldMesh` early-out on `NM_DedicatedServer`; every `LoadSynchronous` in the new audio code sits behind `UVeloxAudioSettings::CanPlayAudio` (`PlayAt`, `Play2D`, `LoadAll`, `UpdateBeamAudio`, `PlayLine`); `UVeloxViewModelComponent::Initialize` checks the owner's net mode before `SettingsAsset.LoadSynchronous()`; the announcer exists only on `IsLocalController() && != NM_DedicatedServer`; `AVeloxPlayerState::GetPlayerColor` reads a weak pointer that only a client ever sets. `Velox.Core.CosmeticsSoftRefs` walks the classes by reflection (arrays, maps, nested structs) and self-checks against `UVeloxPawnData`'s hard pointers, so it tests the rule, not a constant.
2. **Async-load lifetime.** `FStreamableManager` defers completion delegates to the next tick (`StreamableManager.cpp:30`, `FStreamableDelegateDelayHelper` :128), so the callback can outlive a pawn that died the same frame; the character captures a `TWeakObjectPtr` and the asset manager keeps one resident handle per data asset (`CosmeticsHandles`), so later pawns resolve from memory and nothing is unloaded under a live mesh. Dropping the stage-1 handle is safe: the manager holds a shared ref in `FStreamable::LoadingHandles` until completion.
3. **`SkinIndex` rename** keeps `DOREPLIFETIME`, the OnRep, the game mode's assignment order and every call site (inline aliases); the first six skins' `BodyColor` equal the palette, asserted per entry by `Velox.Character.SkinChoice` and on the shipped asset by `Velox.Character.CosmeticsContent`, so HUD, scoreboard and kill-feed colours are unchanged. Forcing is a pure function (`ChooseSkinSlot`), re-applied on `OnRep_SkinIndex`, `OnRep_Controller`, `OnRep_PlayerState`, cosmetics arrival and `OnVeloxSettingsApplied`, which covers late joiners, skin changes and the settings toggle.
4. **Corpses keep their skin.** The server sets `bIsCorpse`, applies the corpse state and unpossesses in one frame (`VeloxCharacter.cpp:1115–1195`), so the client receives `bIsCorpse`, `Controller` and `PlayerState` in one bunch; all properties are written before any RepNotify runs, hence `ApplyCharacterSkin` already sees `bIsCorpse` when `OnRep_PlayerState` fires and does not re-choose. (D5 adds a guard so this does not depend on bunch composition.)
5. **Hitbox mapping (ADR 0003 §6) untouched.** The skeletal mesh gets `NoCollision` when set; the view mesh and `WeaponWorldMesh` are `NoCollision` and `ECR_Ignore` on `Velox_TraceChannel_Weapon`; the muzzle light has no collision; `UVeloxHitboxComponent` and the lag-compensation path are not in the diff. The view model never writes `FMinimalViewInfo::Location/Rotation` (only `FOV`, `bUseFirstPersonParameters`, `FirstPersonFOV`, `FirstPersonScale`), so the B-series eye-origin rules are unaffected and recoil moves the mesh, not the aim.
6. **Prediction surface.** The view model shows `GetCurrentIndex()` (the live predicted index) and listens to `OnCurrentWeaponChanged`, which fires on `PredictCurrentIndex` (drop end), on `SetCurrentIndex` (host/bots) and on `OnRep_CurrentIndex` only when the effective index changed — a `Confirm` is silent, an `EchoOfOlderStep` returns before the broadcast, a `CorrectionRep`/`CorrectionTimeout` swaps the mesh at once. A B42 drop-phase retarget changes only `PendingIndex`: the lowered weapon stays shown until the drop ends and the last target rises (Q3 `PM_FinishWeaponChange`). `LowerAlpha` reads `GetPendingDropRemaining()` and `SwitchEndTime` on the client's own timeline, the same values the fire gate uses. B44 (iii) `ResetLocalSwitchState` precedes `EnsureViewModel` in `InitAbilityActorInfo`, so a new life starts from the authoritative index. Pickup sounds follow ADR 0004 §1 to the letter: the own predicted take plays 2D in `TryPredictTake`, the replicated take skips it (`bWasPredicted`), others play 3D at the item, `bGlobalPickupSound` 2D for everyone, stale takes silent; a mispredicted take yields one own 2D sound and later one 3D sound for the real taker — accepted, same as Q3's server-side race.
7. **Jump-pad cue.** Owner: plays at the live predicted launch (`GetMoveSourceName() == "live"`; replays and corrections silent) and ignores the multicast (`IsLocallyControlled` on `NM_Client`); listen host / standalone own pawn: multicast only; remote pawns: 3D at the pad. No double play on any machine (bots excepted, see D1). Bandwidth: one unreliable multicast with `FVector_NetQuantize` + an actor reference (≈ 12–16 bytes) per launch, sent only to clients for which the pad is relevant — the default `NetCullDistanceSquared` (150 m) exceeds `SA_World`'s 30 m falloff, so relevancy is the right filter, not a cost. `bReplicates` on a startup actor with no replicated properties costs one actor-channel open per relevant client and nothing per tick; `SetNetUpdateFrequency(1)` keeps the consideration cost negligible. The pawn parameter replaces the ADR's launch counter — simpler and sufficient (a null `Launched` on a client where the pawn is irrelevant falls through to 3D, which is right).
8. **Shared files merged semantically, not only textually.** `VeloxCharacter.cpp`: 08's `SetUpCosmeticMesh` ends with 09's `RefreshWeaponWorldMesh()` so the weapon moves from the capsule fallback to `weapon_r` when the mesh arrives; `ApplyCorpseState` hides the weapon, destroys the view model, then `ApplyPlayerColor` darkens the kept skin; `EndPlay` unbinds both the settings delegate (08) and the inventory delegate (09); `OnRep_IsCorpse` plays the death sound (10) before the corpse state; `BeginPlay`/`Tick` are new overrides calling `Super`. `VeloxCombatFeedbackComponent.cpp`: inside the `.Fire` branch the order is audio + muzzle light (10), `++NumFireCues`, `OnFireCue` (09, recoil), `NotifyFired` (08, one-frame `bFiring`) — none depends on another, the B21 cue counters are untouched.
9. **Anim instance / sequence driver.** No per-frame heap work (`FVeloxAnimTuning` is a POD copy, `GetLoadedSequence` is a map find, the `VeryVerbose` log is gated by the macro); `bFiring` is true for exactly one update; `PlayAnimation` only runs when `Step` reports a change (leg state, or the run quadrant while running), so a sequence never restarts on a repeated state; proxies smooth the replicated velocity with a frame-rate-independent first-order filter; the crouch offset reset by the engine (`Character.cpp:521–527` writes `CDO Z + HalfHeightAdjust`) is re-added by `ReapplyCosmeticMeshZDelta`, and the class-default placement makes that delta 0 for the shipped asset. `PlaceholderBody` is re-centred against the mesh offset in `PostInitializeComponents` (:204), so moving the mesh to −70 did not bury the capsule body.
10. **Tests test rules.** `AnimState` (transitions, timings, cadence clamp, quadrants, direction math), `SkinChoice` (forcing matrix, wrap, unknown name), `ViewModelBob` (distance-not-time, zero airborne, recoil < 1 %, sway clamp/return, raise-lower alpha), `FootstepCadence` (spacing invariance under frame size, alternation, silence rules, banked distance), `AnnouncerRules` (countdown ceil, lead transitions, queue depth). The ADR numbers they also assert (70/0.6, 170/100/400/1000, 2/5 s) are the ADR's values, which is what a defaults check is for.

## Defects (ranked)

**D1 — High — every "own pawn" audio test is wrong for bots on a listen server or standalone.** `APawn::IsLocallyControlled()` is `Controller->IsLocalController()`, which returns true for *any* authority controller whose remote role is not `ROLE_AutonomousProxy` (`Controller.cpp:90–112`) — i.e. every `AIController` on the server. Sites: `VeloxCombatFeedbackComponent.cpp::PlayCueAudio` (`bIsFire && Pawn->IsLocallyControlled()` → 2D), `::UpdateBeamAudio` (`bOwn`), `::HandlePowerupCue` (harmless: an AIController has no announcer), `VeloxFootstepComponent.cpp::OnHealthChanged` (`pain_own`), `::HandleCorpse` (`death_own`), `VeloxJumpPad.cpp::MulticastLaunchCue_Implementation` (`jumppad_own` on `NM_ListenServer`/`NM_Standalone`). Effect: in standalone or listen games with bots (`?Bots=N`, the headless BotRun, the human's Mac playtest), every bot's fire, beam start/loop/stop, pain, death and pad launch plays 2D at full volume in the host's ears; the §10 checklist line "direction of enemy fire identifiable" cannot pass. Task 08 got the same question right (`AVeloxCharacter::IsOwnedByLocalPlayer` requires an `APlayerController`). Fix: `static bool UVeloxAudioSettings::IsLocalPlayerPawn(const APawn*)` = `Pawn && Cast<APlayerController>(Pawn->GetController()) && Pawn->IsLocallyControlled()`; replace the six sites. Regression check: standalone `-game -nullrhi L_ItemTest?Bots=2` with `log LogVeloxAudio Verbose` must show no `play2d` line for a bot pawn (18b verification step).

**D2 — Medium — simulated proxies never produce landing sounds.** `ACharacter::Landed` is only reached through `UCharacterMovementComponent::ProcessLanded` (PhysFalling on the owner/authority); `SimulateMovement` (`CharacterMovementComponent.cpp:2190`) calls `SetPostLandedPhysics` directly on touchdown (:2354) and never `Landed`. So on a client, other players' and bots' landings are silent, while the host and the owner hear them; Q3 sends `EV_FALL_*` to everyone, and a hard landing is position information. The footstep component already detects the proxy *jump* by the ground-to-air transition; the landing is the mirror case. Fix in `UVeloxFootstepComponent::TickComponent`: for `ROLE_SimulatedProxy`, `!bWasGrounded && bGrounded` → the `HandleLanded` body with `LastFallingVz` (skip the owner-only `bClientUpdating` check). ADR 0006 §9's "from `ACharacter::Landed`" is corrected in E1.

**D3 — Medium — dry fire has no hook** (flagged by task 10). The refusal point exists: `UVeloxGameplayAbility_Fire::CheckCost` adds `ActivateFailCostTag` to the relevant tags, and GAS forwards every refused activation to `UAbilitySystemComponent::AbilityFailedCallbacks` (`NotifyAbilityFailed`). Fix: `UVeloxCombatFeedbackComponent` binds `AbilityFailedCallbacks` on the ASC whose avatar is its owner, only when `IsLocalPlayerPawn`; on `Ability->IsA<UVeloxGameplayAbility_Fire>() && FailureReason.HasTag(ActivateFailCostTag)` → `Play2D(DryFireSound)`, rate-limited by a new `UVeloxAudioSettings::DryFireMinInterval` (0.25 s, Config). Q3 plays `noammo.wav` at the weapon's rate; the fixed interval is simpler and inaudible as a difference.

**D4 — Medium — weapon sounds have two homes and the weapon meshes load synchronously.** `UVeloxAudioSettings::CueSounds` (used) duplicates `UVeloxWeaponCosmetics::FireSound/ImpactSound/BeamStart/BeamLoop/BeamStop` (dead data that task 13 would naturally fill), and `MuzzleLightColor/Intensity` in the cosmetics are ignored in favour of one global light. Separately, `AVeloxCharacter::RefreshWeaponWorldMesh` and `UVeloxViewModelComponent::ShowWeapon` call `LoadSynchronous` on the cosmetics asset and its mesh at every weapon change — free today (empty meshes), a game-thread hitch at the first swap to each weapon once task 13 lands. **Ruling (E1):** ADR 0006 §9 stands — the weapon cosmetics asset is the single source of a weapon's look *and* sound; `CueSounds`, `BeamStartSound`, `BeamStopSound` leave the settings; `DryFireSound` and `SwitchSound` leave the cosmetics (Q3 has one `change.wav` and one `noammo.wav`; they stay global in the settings). Loading: `UVeloxAssetManager::LoadWeaponCosmetics` (the same two-stage, one-resident-handle pattern as `LoadCharacterCosmetics`) requested once per client pawn init for all six definitions; the cue handler, the world mesh and the view model then use `.Get()` and refresh on completion. Task 18c.

**D5 — Low — `ApplyCharacterSkin` re-chooses for a pawn without a PlayerState.** Correct in practice (item 4 above) but only because the unpossess and `bIsCorpse` share a bunch. Guard: if `!VeloxPS && AppliedSkinSlot != INDEX_NONE`, keep the applied slot and only re-tint. One `if`.

**D6 — Low — the announcer matches frags by display name** (`VeloxAnnouncerComponent.cpp::OnKillFeedEntry`: `Entry.KillerName != Local->GetPlayerName()`). Two clients with the default name `Player` both get "excellent"/"impressive" for each other's frags. Fix: compare `GetPlayerId()`; if `FVeloxKillFeedEntry` carries no id, add `int32 KillerPlayerId` next to `KillerName` (one int32 more per replicated entry).

**D7 — Low — the two skin settings have no UI rows** (flagged by task 08) and **the UI click sound has no hook** (flagged by task 10). `VeloxSettingsWidget` is hand-built: add a checkbox (`bForceEnemySkin`) and a combo of the skin names read from `DA_Cosmetics_Velox` (`ForcedEnemySkin`), and call `UVeloxAudioSettings::Play2D(UIClickSound)` from the nine `OnClicked` handlers of the three menu widgets through one static helper.

**Deferred, not defects.** Rocket-projectile light: belongs to task 13 (projectile visuals), counted against the same `MaxMovableLights` — 18c moves the `ActiveLights` list out of the feedback component's anonymous namespace into `Weapons/VeloxMovableLights.h` so the projectile can share it. Footstep over-count on a proxy snap (the capsule's replicated correction adds its distance): bounded by the correction size, inaudible at 30 Hz updates; noted. `MuzzleLightIntensity` 5000 cd / 6 m radius is bright: art-pass tuning (task 15), not a defect.

## Nits
- `VeloxCharacter.h` now includes `Character/VeloxAnimInstance.h` (and through it `Animation/AnimInstance.h`) for two by-value members; every includer of the pawn header pays for it. Acceptable for M5; a `TPimplPtr` is the fix if compile times become a topic.
- `UVeloxCombatFeedbackComponent.h`: the `DECLARE_MULTICAST_DELEGATE` block separates `GetNumFireCues` from `GetNumImpactCues`; move it above the getters.
- `AVeloxJumpPad::OnTriggerBeginOverlap`: the `const_cast<ACharacter*>` for the RPC parameter — look the pawn up non-const once (`OtherActor`) instead of casting away const.
- `UVeloxViewModelComponent::ApplyToView` sets `bUseFirstPersonParameters` while no mesh is shown (hidden component); harmless, but gate it on `ViewMesh->IsVisible()` so an empty hand renders exactly as before.
