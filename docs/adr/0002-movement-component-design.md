# ADR 0002 — Movement component design (M1)

**Status:** Accepted (2026-10-24, project lead) (architect, 2026-10-24) → accepted by the lead when the M1 task files are written.
**Scope:** everything `dev-hard` needs to turn the M0 skeleton (`Source/Velox/Movement/*`, `Character/VeloxCharacter.*`) into Quake-feel, predicted, tunable movement. Builds on ADR 0001 §3 (saved-move path, `FVeloxMoveSim`, `AddKnockback`); does not replace the skeleton. Weapon knockback sources and self-knockback prediction are M2 (next ADR); bots are M4 but §8 fixes what they will drive.
**Engine facts verified against UE 5.8.4 source** (`CharacterMovementComponent.{h,cpp}`, `Character.cpp`, `CharacterMovementReplication.h`, `GameNetworkManager.cpp`); line references below are to that cpp.

## Context

CLAUDE.md non-negotiable #1: strafe jumping, bunny hopping with no landing speed loss, Q3 friction, rocket jumps, jump pads, ramp sliding, as a `UCharacterMovementComponent` (CMC) subclass. ROADMAP M1 adds: all tunables in `UVeloxMovementSettings`, full prediction with no visible jitter at 100 ms / 2 % loss, `L_MovementTest`, automation tests, human sign-off.

What the stock CMC does that fights Q3 feel (read from source): `CalcVelocity` (l.3863) applies braking only when input is zero and clamps speed to `MaxSpeed` every tick (kills strafe-jump gain); `GetFallingLateralAcceleration` (l.4827) scales input by `AirControl` and `PhysFalling` re-runs `CalcVelocity` to limit air control on wall hits (l.4887ff); `HandleSlopeBoosting` (l.3749) forbids gaining height when sliding on a ramp in the air; `ProcessLanded` (l.6373) → `SetPostLandedPhysics` → `StartNewPhysics` → `PhysWalking` applies ground friction in the landing frame and a jump happens only in the *next* tick's `CheckJumpInput`; `PhysWalking` recomputes `Velocity = (NewLoc − OldLoc)/dt` after each iteration (l.5870) — with `bMaintainHorizontalGroundVelocity=true` this preserves speed on clean step-ups and clips it against walls, which is Q3 `PM_SlideMove` behaviour (the original claim that step-ups lose speed was wrong, A13); a ramp's vertical velocity is discarded by `MaintainHorizontalGroundVelocity` (l.5635) and the pawn is snapped to the floor on ramp exits (`ShouldCatchAir` l.6282 is `false` by default). Everything else (floor finding, stepping, substepping `MaxSimulationTimeStep`, saved moves, packed RPCs, corrections) is exactly what we want to keep.

## Decision

### 1. Physics model: Q3 vanilla core, CPM features as toggles, fixed-step velocity integration

Formulas (Q3 `bg_pmove.c`), all in UE units (cm, s), horizontal unless noted. `WishDir` = unit XY, `WishSpeed` ∈ [0, MaxGroundSpeed] (analog scale):

```
Friction(V, dt):   s=|V_xy|; if s<ε → V_xy=0; control=max(s, StopSpeed); drop=control·GroundFriction·dt;
                   V_xy *= max(s−drop, 0)/s                                         (skipped while KnockbackGrace>0)
Accelerate(V, WishDir, WishSpeed, Accel, dt):  cur=V·WishDir; add=WishSpeed−cur; if add≤0 return;
                   a=min(Accel·dt·WishSpeed, add); V += a·WishDir        (the dot-product clamp = strafe jumping)
Ground:            Friction; Accelerate(GroundAcceleration, WishSpeed). While KnockbackGrace>0: no Friction and
                   Accel = AirAcceleration (Q3 PM_WalkMove: accelerate = pm_airaccelerate under PMF_TIME_KNOCKBACK)
Air (vanilla):     Accelerate(AirAcceleration, min(WishSpeed, AirMaxWishSpeed))
Air (CPM, bAirControl): accel = (V·WishDir<0) ? AirStopAcceleration : AirAcceleration;
                   if side-only input: WishSpeed=min(WishSpeed, AirStrafeMaxWishSpeed), accel=AirStrafeAcceleration;
                   Accelerate(...); if forward/back-only input: AirControl():
                     z=V.z; V.z=0; s=|V|; V/=s; dot=V·WishDir; k=AirControlScale·AirControl·dot²·dt;
                     if dot>0: V = normalize(V·s + WishDir·k);  V*=s; V.z=z         (turns without speed change)
Jump:              V.z = JumpVelocity (set, not max); mode=Falling; the rest of that frame is an air frame
                   (AirMove + gravity, Q3 PM_WalkMove → PM_CheckJump → PM_AirMove). Landing with jump held → jump in
                   the landing frame before any friction (Q3 checks jump before PM_Friction) when bAutoHop, or when
                   the button was released since the last jump (Q3 PMF_JUMP_HELD; `bJumpLatched`, A12).
Gravity:           V.z += GravityZ·dt (engine midpoint integration, apex substep kept)
Ramp slide:        landing hit with V.z>0 and V·N > RampSlideMinNormalSpeed is not a landing → slide (Q3 PM_GroundTrace)
Ramp exit:         leaving a ramp upward keeps the ramp's climb rate V.z = −(V_xy·N)/N.z (Q3 clips V to the ground
                   plane); the pawn leaves the ground when (V_xy, V.z)·N_new > RampSlideMinNormalSpeed (A9)
ClipVelocity:      V − N·(V·N)  (UE VectorPlaneProject; Q3 OVERCLIP 1.001 is unnecessary with swept moves)
Knockback:         V += Impulse (or V = Impulse if override); KnockbackGrace = max(KnockbackGrace,
                   clamp(|Impulse|·KnockbackGracePerSpeed, KnockbackGraceMin, KnockbackGraceMax)); ground friction off
                   and ground accel = AirAcceleration while >0 (Q3 PMF_TIME_KNOCKBACK; Q3 only sets pm_time when none
                   is running, max() is a deliberate simplification)
```

**Fixed-step integration.** Velocity updates (friction, accelerate, air control) run in `n = ceil(dt/FixedStep)` equal substeps of `dt/n` (≤ `FixedStep`; default 1/125 s = Q3 `pmove_fixed 1, pmove_msec 8`). Position integration stays per move (CMC). What it buys (corrected 2026-10-24, see Amendments A1): with the wish direction constant over a move, Q3 `Accelerate` is split-invariant — the component along `WishDir` ends at `min(c0 + Accel·W·dt, W)` however `dt` is split — so substeps do **not** change vanilla strafe gain. They make the *nonlinear* terms frame-rate independent: friction `(1−f·h)^n` including the StopSpeed regime, CPM air control (`k ∝ dt` inside a normalisation) and the per-step choice of CPM air-stop/strafe acceleration from the current velocity. Measured by `FixedStepInvariance` (ground turn, release, run, CPM air control): 60 vs 240 fps differ by 0.47 % with substeps and 4.33 % without. What remains frame-rate dependent by design: steering is sampled once per move (a 240 fps client re-aims four times as often as a 60 fps one — identical to Q3 `pmove_fixed`, whose usercmds are also per client frame; with optimal steering the vanilla gain rate differs by `Accel²W²/n`, under 0.5 % between 60 and 125 fps), and the substep length varies between `FixedStep/2` and `FixedStep`. `bFixedStepIntegration=false` turns substepping off for A/B tests. Determinism (ADR 0001 §4) only requires identical inputs and dt per move, which the server replays anyway.

**Units.** `UnitScale = 2.5 cm per Q3 unit` (Q3 player 56 u → 140 cm, speed 320 → 800 cm/s, step 18 → 45 cm = UE default `MaxStepHeight`). Round, keeps numbers close to UE defaults, maps built from scratch. Alternatives (2.54 "inch", 3.2 "180 cm human") in Alternatives. Assets store UE units; `UnitScale` is for HUD display (ups) and the `velox.move.Preset` helper only.

No other input. Derived state carried across moves: `KnockbackGrace`, `bJumpLatched`, `PendingKnockback` (§5).

### 3. World-free simulation core `FVeloxMoveSim`

`Movement/VeloxMoveSim.h/.cpp`: includes only `CoreMinimal.h`; no UObject, no world, no logging. Pure functions over plain structs; the CMC calls them from `CalcVelocity`/`ProcessLanded`/`ConsumePendingKnockback`, tests call them directly.

```cpp
struct FVeloxMoveParams { /* POD copy of every UVeloxMovementSettings number above, built per move by
    UVeloxMovementSettings::BuildSimParams() which also applies velox.move.* cvar overrides (non-shipping) */ };
struct FVeloxMoveInput  { FVector WishDir = FVector::ZeroVector; /* unit XY or zero */ float WishSpeed = 0.f;
    bool bHasForwardInput = false, bHasSideInput = false, bJumpHeld = false; /* jump request this frame; bAutoHop
    gating (release between jumps when off) is the CMC's job, the sim has no press/release edge state */ };
struct FVeloxMoveState  { FVector Velocity = FVector::ZeroVector; bool bOnGround = false; float KnockbackGrace = 0.f; };
namespace VeloxMoveSim {
  int32   NumSubsteps(float Dt, const FVeloxMoveParams& P);                                   // 1 if fixed step off
  FVector ApplyFriction(const FVector& V, float Dt, const FVeloxMoveParams& P);               // XY only
  FVector Accelerate(const FVector& V, const FVector& WishDir, float WishSpeed, float Accel, float Dt);
  FVector AirControl(const FVector& V, const FVector& WishDir, float Dt, const FVeloxMoveParams& P);
  FVector GroundMove(const FVector& V, const FVeloxMoveInput& In, float Dt, float KnockbackGrace, const FVeloxMoveParams& P); // substepped
  FVector AirMove(const FVector& V, const FVeloxMoveInput& In, float Dt, const FVeloxMoveParams& P);                         // substepped, no gravity
  FVector ApplyGravity(const FVector& V, float Dt, const FVeloxMoveParams& P);               // tests/bots only; CMC uses NewFallVelocity
  FVector Jump(const FVector& V, const FVeloxMoveParams& P);                                 // Z = JumpVelocity
  FVector ClipVelocity(const FVector& V, const FVector& Normal);
  FVector ApplyKnockback(const FVector& V, const FVector& Impulse, bool bOverride);
  float   KnockbackGraceFor(const FVector& Impulse, const FVeloxMoveParams& P);
  FVector JumpPadLaunchVelocity(const FVector& From, const FVector& Target, float GravityZ);  // Target above From:
          // Q3 AimAtTarget (apex at the target); level or below: minimum-launch-speed arc; zero if unsolvable (A4)
  void    StepFrame(FVeloxMoveState& S, const FVeloxMoveInput& In, float Dt, const FVeloxMoveParams& P); // reference frame:
          // ground + bJumpHeld: Jump first, then the frame runs as air (AirMove + ApplyGravity, no friction, Q3 order);
          // ground: GroundMove, Z = 0; air: AirMove + ApplyGravity; KnockbackGrace -= Dt. No collision. Tests/bots only.
}
```
`StepFrame` is a reference model, not what the CMC executes (the CMC adds sweeps, floor logic, apex substep); the determinism and feel tests run on it, the CMC-level determinism test (§7) covers the rest.

### 4. Knockback and jump pads through the predicted path

`UVeloxMovementComponent::AddKnockback(FVector Impulse, bool bOverrideVelocity)` (ADR 0001) accumulates into `FVeloxPendingKnockback { FVector Velocity; bool bOverride; }` (own field, not the engine's `PendingImpulseToApply`/`PendingLaunchVelocity`, so it can be saved, replayed and sent in corrections). `ConsumePendingKnockback()` at the start of `PerformMovement`: `Velocity = Sim::ApplyKnockback(...)`; `KnockbackGrace = max(KnockbackGrace, Sim::KnockbackGraceFor(...))`; if `IsMovingOnGround() && (Velocity | CurrentFloor.HitResult.ImpactNormal) > RampSlideMinNormalSpeed` → `SetMovementMode(MOVE_Falling)`; `bForceNextFloorCheck = true`; clear pending. Callable on any role; the authority decides what is legitimate:

- **Server-side impulses (rockets, M2):** server calls `AddKnockback` in the explosion; the owning client learns of it through the standard correction (`ServerCheckClientError` fails at the next move → `ClientAdjustPosition`). To keep the replay consistent, the correction carries Velox state: `FVeloxMoveResponseDataContainer : FCharacterMoveResponseDataContainer` (installed with `SetMoveResponseDataContainer` in the constructor) overrides `ServerFillResponseData(const UCharacterMovementComponent&, const FClientAdjustment&)` to copy `KnockbackGrace`, `bJumpLatched` (A12) and any unconsumed pending knockback — from the snapshot the CMC took in `ServerMoveHandleClientError` for that time stamp, not from the live component (A18) — and `Serialize(UCharacterMovementComponent&, FArchive&, UPackageMap*)` with `SerializeOptionalValue` (1 bit when zero/false). `OnClientCorrectionReceived` applies them before `ClientUpdatePositionAfterServerUpdate` replays. Without this the client replays with friction on while the server skips it for up to 200 ms → a correction every `NetworkMinTimeBetweenClientAdjustments` after every hit.
- **Jump pads (predicted, no replication):** `AVeloxJumpPad : AActor`, map-placed, not replicated, `UBoxComponent` trigger (`Overlap` with Pawn only) + editor-only arrow + a collision-free `PadMesh` for the greybox (A21). Data: `EVeloxJumpPadMode { AimAtTarget, FixedVelocity }`, `TObjectPtr<AActor> Target` (any actor, usually `ATargetPoint`), `FVector LaunchVelocity`, `bool bOverrideVelocity = true` (Q3 trigger_push sets velocity; `false` adds). `OnComponentBeginOverlap` on both server and owning client (once per entry, dispatched at the end of the move's scoped update on both ends): `MoveComp->AddKnockback(ComputeLaunchVelocity(MoveComp->GetGravityZ()), bOverrideVelocity)`; `AddKnockback` ignores it while the client applies a correction teleport (A19); `ComputeLaunchVelocity` is `Sim::JumpPadLaunchVelocity(TriggerCentre, TargetLocation, GravityZ)` for `AimAtTarget`. Deterministic: same actor data, same gravity from the character's settings, same overlap during the same move on both sides; override semantics make a re-trigger during replay idempotent. Q3's `AimAtTarget` is singular for targets barely above the pad (`t = sqrt(2h/g)` → horizontal speed `d/t` explodes), so `AVeloxJumpPad` validates: `MaxLaunchSpeed` (`EditAnywhere`, default 4000 cm/s) with an editor map-check warning (`CheckForErrors`) and a one-time runtime warning when `|ComputeLaunchVelocity()|` exceeds it or is zero (unsolvable); mappers place `AimAtTarget` targets ≥ 1 m above the pad or use `FixedVelocity`. The launch point is the trigger centre (Q3) while the pawn starts from its capsule centre inside the trigger — a decimetre-scale landing error, accepted (Q3 has the same). The knockback grace a pad launch sets is harmless: the pawn is airborne for longer than `KnockbackGraceMax`. One-move latency (consumed at the next `PerformMovement`) is accepted; simulated proxies get the result via replication. Mapping rule: `AimAtTarget` targets sit over the near third of the landing area, ≈ 1 m above it (the capsule-centre apex is at the target, the pawn lands beyond it; A21). Nav-link metadata for bots is M4.
- **Rocket-jump self-knockback prediction** (client-side `AddKnockback` when the fake projectile detonates) is specified in the M2 ADR; the plumbing above already supports it. M1 ships a non-shipping console command `velox.move.TestKnockback X Y Z [override]` (server-executed in PIE) to exercise the path.

### 5. Prediction, correction, validation

`FSavedMove_Velox` gains: `SavedPendingKnockback` (captured in `SetMoveFor` **before** the move consumes it — `ReplicateMoveToServer` calls `SetMoveFor` before `PerformMovement`, l.8961/9024; sets `bForceNoCombine`), `SavedKnockbackGrace` and `bSavedJumpLatched` (start-of-move values), `bSavedHasForwardInput`, `bSavedHasSideInput`. Rule (A17, supersedes A14's restore clause): `PrepMoveFor` restores **nothing Velox-specific** — the input flags reach the replay through `UpdateFromCompressedFlags` in `MoveAutonomous`, and every carried Velox quantity (`KnockbackGrace`, `bJumpLatched`, `PendingKnockback`) is *derived* state that chains from the correction through the replayed moves exactly as the engine chains `Velocity`: `OnClientCorrectionReceived` sets the server's values, each replayed `PerformMovement` recomputes them, and pad overlaps re-fire during the replayed move that enters the trigger. The saved fields exist for `CanCombineWith`/`bForceNoCombine` and debugging. Compressed flags: `FLAG_Custom_0` jump held (exists), `FLAG_Custom_1` has-forward-input, `FLAG_Custom_2` has-side-input, `FLAG_Custom_3` reserved. `Clear()` resets all. `CanCombineWith` returns `false` when: jump-held differs (exists); `bSavedJumpLatched` differs; either move has a pending knockback; either `SavedKnockbackGrace > 0`; either `StartPackedMovementMode` is Falling and `!bCombineAirMoves`; input-presence flags differ; then `Super`. Rationale for not combining air moves: combining re-simulates the pending move with a longer dt from its start location, visibly re-placing the player mid-jump; the cost is more RPCs for clients above 60 fps (the packed RPC carries pending + new move, ≈ 40 B each; at 240 fps ≈ 5 KB/s up, 16 players ≈ 80 KB/s on the server). `IsImportantMove` stays engine.

`FVeloxNetworkMoveData`: **no new serialised fields in M1**. `Acceleration` (wishvel), `CompressedMoveFlags` and `ControlRotation` express every input; the move-data subclass stays for the day something does not fit (e.g. a per-move weapon-fire timestamp in M2).

Server validation: the client never sends speed or position intent, only wishvel + flags; the server simulates, so no speed cap is needed beyond what the engine does (`MoveAutonomous` clamps `Acceleration` to `GetMaxAcceleration()`; `GetServerMoveDeltaTime` clamps dt to `MaxMoveDeltaTime × p.NetServerMaxMoveDeltaTimeScalar`). Enable the engine's time-discrepancy (speedhack) guard. `Config/DefaultGame.ini` (the `GameNetworkManager` block lives there because `AGameNetworkManager` is `config=Game`; extend it with the time-discrepancy settings below):
```ini

ClientNetSendMoveDeltaTime=0.0166
MaxMoveDeltaTime=0.125
bMovementTimeDiscrepancyDetection=True
bMovementTimeDiscrepancyResolution=True
MovementTimeDiscrepancyMaxTimeMargin=0.25
MovementTimeDiscrepancyMinTimeMargin=-0.25
MAXPOSITIONERRORSQUARED=3.0        ; engine default (1.73 cm); kept — our sim is deterministic, so corrections are rare and tiny
[/Script/Engine.PhysicsSettings]

```
CMC correction knobs (defaults are right; set explicitly in the constructor): `NetworkMinTimeBetweenClientAdjustments 0.1`, `NetworkLargeClientCorrectionDistance 15`, `NetworkSimulatedSmoothLocationTime 0.1` (ADR 0001 lag-comp depends on it), `bNetworkSkipProxyPredictionOnNetUpdate = true`, pawn `NetUpdateFrequency 60 / MinNetUpdateFrequency 30`. Owning-client corrections are snap-and-replay (no smoothing exists for the autonomous proxy in 5.8); "no visible jitter" therefore means few and small corrections, which determinism provides. Expected residual sources: 2 % lost moves (server fills the gap with its own dt → mm-scale), x86 vs Apple-silicon float differences (sub-mm drift), server-side knockback (intended). A dev-only sanity `ensureMsgf(|Velocity| < 20 × MaxGroundSpeed)` in `PerformMovement` catches sim bugs.

Headless jitter measurement (what is automatable): `infra/ci/nettest.sh` starts `Velox L_MovementTest -server -nullrhi -log -port=7777` and one client `Velox 127.0.0.1:7777 -game -nullrhi -nosound -unattended -UseFixedTimeStep -FPS=120 -VeloxScript=StrafeRun -ini:Engine:[PacketSimulationSettings]:PktLag=100,[PacketSimulationSettings]:PktLagVariance=20,[PacketSimulationSettings]:PktLoss=2` (dev verifies `FPacketSimulationSettings::LoadConfig` picks up the section under `DO_ENABLE_NET_TEST`; fallback: the scripted component execs `Net PktLag=100` after possession). `UVeloxScriptedInputComponent` (dev-only, on the character) replays a named input script (`Content/Data/MoveScripts/*.json`: rows of `{duration, forward, right, yawRate, jump}`) through `SetLocalMoveInput`/`AddMovementInput`/`SetJumpHeld`, while the CMC counts corrections in `OnClientCorrectionReceived` (`NumCorrections`, `MaxCorrectionCm`, `SumCorrectionCm`). At script end the client logs `VeloxNetSoak: moves=N corrections=C max=X mean=Y` and quits; the script fails when `C > 3 × expected lost moves`, `X > 30 cm` or `Y > 5 cm` (initial thresholds; tune after the first real run). PIE with two clients remains the human gate.

### 7. Test plan

Unit (`Tests/VeloxMoveSimTest.cpp`, `Velox.Movement.*`, world-free, `dt = 1/125` unless stated):
- `Friction`: from 800 cm/s with no input, N ticks: above `StopSpeed` speed equals `v0·(1−f·dt)^N` within 1e-3 relative; below it decays by `StopSpeed·f·dt` per tick and reaches exactly 0, never negative.
- `GroundAccel`: from rest with forward input the speed converges to `MaxGroundSpeed` (±1e-3) and never exceeds it.
- `AirAccel`: single tick, V=(800,0): wish parallel → zero gain (the clamp); wish perpendicular → gain `> 0`; gain per tick ≤ `AirAcceleration·dt·AirMaxWishSpeed` (|ΔV| bound).
- `StrafeJump`: 125 ticks with the optimal steering angle (`cos θ = (WishSpeed − a)/|V|`, `a = AirAcceleration·dt·WishSpeed`): total gain `> 0.25 × AirAcceleration·AirMaxWishSpeed·T` and `≤ AirAcceleration·AirMaxWishSpeed·T`; holding forward only: gain `== 0`.
- `FixedStepInvariance`: a per-1/60-s wish sequence that exercises the nonlinear terms (ground run turning 3°/frame, 20 frames of release, 30 frames of forward run, 60 airborne frames of CPM forward-only air control turning 2°/frame) stepped at dt 1/60 and 1/240 → final speed and velocity within 0.5 % with fixed step on; the test also asserts they differ with it off and that the difference is larger (documents why the feature exists). A pure constant-wishdir strafe sequence would pass trivially (split-invariance of `Accelerate`) and must not be used.
- `AirControl` (CPM on): forward-only input while airborne rotates V towards WishDir with `|V|` unchanged within 1e-3; side input does not.
- `BunnyHop`: airborne at 1000 cm/s, `StepFrame` with ground contact and jump held → XY bitwise unchanged, Z == `JumpVelocity + GravityZ·dt` (the rest of the jump frame is airborne; `Jump()` alone yields Z == `JumpVelocity`), `bOnGround == false`; without jump held → exactly one friction tick applied.
- `Knockback`: on the ground, impulse 1250 cm/s → grace 0.2 s, no friction for 25 ticks, friction resumes on tick 26; while grace > 0 a ground move with input accelerates with `AirAcceleration`, not `GroundAcceleration` (one tick from (1250,0) with side input: gain == `AirAcceleration·dt·WishSpeed`); override vs additive semantics; `max()` of an existing grace.
- `JumpPad`: `JumpPadLaunchVelocity` from (0,0,0) to (800,0,320): analytic flight lands within 1 cm with Vz == 0 at the target (apex); vertical target (0,0,640): XY == 0, Z > 0; level target (1600,0,0): lands within 1 cm and Vxy == Vz (45° minimum-speed arc); below (800,0,−400): lands within 1 cm; (0,0,−100) and GravityZ == 0 → zero vector.
- `Determinism`: 600-tick mixed script run twice through `StepFrame` → bitwise-equal state.
- `SavedMoveFlags` (exists) + `SavedMoveCombine`: the `CanCombineWith` rules of §5 on hand-built moves.

### 8. What bots (M4) will drive

Bots are `AAIController`-possessed `AVeloxCharacter`s with the same component and settings asset. Guarantees from M1: input enters only via `AddMovementInput`/`SetLocalMoveInput` (the presence flags persist until the next call, so a bot sets them every frame it steers; M4 may add a `SetMoveInputWorld(WishDirWorld)` convenience that does both from the controller yaw), `Jump()`/`SetJumpHeld` (`CheckJumpInput` runs in `ControlledCharacterMove` for AI-controlled authority pawns too), `AddKnockback`; `bUseAccelerationForPaths = true` so `UPathFollowingComponent` → `RequestPathMove` → `AddInputVector`, never `RequestDirectMove`/velocity requests (which our `CalcVelocity` ignores); no teleports, no `Launch`. Read API for planning: `GetSimParams()`, `GetSpeed2D()`, `IsOnGround()`, `GetKnockbackGrace()`, `VeloxMoveSim::StepFrame`/`ApplyGravity`/`JumpPadLaunchVelocity` (so M4 can simulate a strafe-jump or pad hop ahead of time for nav links). `AVeloxJumpPad` exposes `ComputeLaunchVelocity` and `GetLandingPoint()` for nav-link generation.

## Consequences

- Hooking `CalcVelocity` and the landing/ramp/step virtuals keeps ~600 lines of engine phys code and its substepping, floor logic and replication untouched; the price is that the hooks must be re-verified on engine upgrades (the table in §2 is the checklist).
- Fixed-step velocity integration makes strafe gain frame-rate independent and the feel reproducible in tests; it is a deliberate deviation from vanilla Q3 (matches CPMA `pmove_fixed`).
- No air-move combining raises upstream RPC rate for high-fps clients (bounded, see §5) in exchange for a stable local simulation.
- The move-response subclass makes knockback a first-class predicted quantity; M2 self-knockback prediction becomes a dedup problem only.
- Everything tunable is in the asset and mirrored by cvars; `UnitScale = 2.5` fixes map scale for M3+ content — changing it later means rebuilding every map.
- Headless CI gets deterministic unit and functional coverage plus a two-process net soak; human PIE is still the M1 gate.

## Alternatives considered

- **Mover 2.0 / NetworkPrediction plugin**: rejected in ADR 0001 (CMC mandated; AI path following; maturity). Unchanged.
- **GAS-driven movement** (jump/knockback as abilities with prediction keys): the GAS prediction window is not the move replay; a predicted ability applying velocity outside `PerformMovement` desyncs on every correction. Movement state stays in the saved-move path; GAS only calls `AddKnockback`.
- **Root motion**: irrelevant to a physics-driven FPS; `bAllowPhysicsRotationDuringAnimRootMotion` and root-motion sources are never used.
- **Overriding `PhysWalking`/`PhysFalling` wholesale** (copy and edit): maximal control, but ~600 lines of engine code to maintain across versions, and every feature in §1 was expressible through the smaller hooks. Revisit only if a feel bug cannot be fixed at the hook level.
- **Expressing Q3 air physics with engine parameters** (`AirControl`, `BrakingFriction`, `MaxAcceleration`): the stock `CalcVelocity` clamps to `MaxSpeed` and lacks the dot-product rule; impossible without the override.
- **Engine `Launch()`/`AddImpulse()` for knockback and pads**: works for pads, but two paths, mass semantics, no saved/correction state; one `AddKnockback` is simpler.
- **Combining air moves** (engine default): lower RPC rate, visible re-simulation of the player's own jump; rejected by default, kept as a toggle.
- **Per-frame integration (vanilla Q3)**: faithful but rewards high frame rates; fixed step chosen.
- **Unit scale 2.54 (inch) or 3.2 (180 cm pawn)**: 2.54 gains nothing over 2.5 and loses round numbers; 3.2 makes a 180 cm pawn but Q3 proportions (jump height ≈ 80 % of body height, 320 ups) then produce a 2.6 m jump-height feel mismatch with any realistic prop scale. Maps are ours, so proportions beat realism.
- **CPM physics on by default**: better duel movement for experts, harder to learn; vanilla core with CPM toggles lets the human decide after playing both (open question).

### 2026-10-24 — design review of task 01 (`VeloxMoveSim`, `UVeloxMovementSettings`), architect

Body text above has been adjusted where an amendment changes it; this section records the decisions.

- **A1 — Fixed-step rationale corrected (§1).** The original rationale ("strafe gain per second otherwise depends on the frame rate") was wrong for this design: with the wish direction constant within a move, Q3 `Accelerate` is split-invariant, so substepping leaves vanilla strafe gain unchanged. Substeps are kept for the nonlinear terms (friction/StopSpeed, CPM air control, CPM accel selection) and for reproducible tests; the implementer's rewritten `FixedStepInvariance` test (0.47 % vs 4.33 %) is the specification now. The per-move steering sample rate and the `FixedStep/2..FixedStep` substep length are accepted residuals. No code change.
- **A2 — Jump-first order confirmed (§1, §3, §7).** `StepFrame` jumps before any ground processing and runs the rest of the frame as air (Q3 `PM_WalkMove` → `PM_CheckJump` → `PM_AirMove`); Z after a `StepFrame` jump frame is `JumpVelocity + GravityZ·dt`. The old §3 wording "GroundMove, then Jump" was a mistake. The CMC path in §2 (`ProcessLanded` → `DoJump` → `StartNewPhysics` → `PhysFalling` for the remainder) already matches; a jump started by `CheckJumpInput` before `PerformMovement` makes the whole move an air move, also as in Q3.
- **A3 — `bJumpHeld` semantics (§3).** In the sim `bJumpHeld` means "jump request this frame if on ground"; `bAutoHop` gating stays in the CMC, which owns the press/release edge (`ACharacter::bPressedJump` with `JumpMaxHoldTime = 0` clears after one frame; `bWantsJumpHeld` is the replicated held state used only when `bAutoHop`). Adding Q3 `PMF_JUMP_HELD` state to `FVeloxMoveState` would duplicate engine state for no test value. `FVeloxMoveParams::bAutoHop` is carried but unread by the sim.
- **A4 — Jump pad solution for level/below targets (§3, §4, §7).** Q3 `AimAtTarget` (apex at the target, `t = sqrt(2h/g)`, `Vxy = d/t`, `Vz = g·t`) is used for targets above the pad; for level or lower targets the minimum-launch-speed arc (`R = |Δ|`, `S = sqrt(g/2R)`, `Vxy = d·S`, `Vz = (h+R)·S`, i.e. `v² = g(R+h)`, launch angle `atan((h+R)/d)`) is used — verified: it lands exactly on the target and its apex is never below it. Q3 cannot express such pads at all, so this is an extension, not a deviation. The near-level singularity of the Q3 branch is handled by actor validation in task 04 (§4), not by the sim.
- **A5 — Defect: `AirControlScale` has speed units (§1 table).** In `CPM_Aircontrol` the term `wishdir·k` is added to `v_unit·speed` (ups), so `k = 32` is a Q3-unit speed and becomes `32 × UnitScale = 80` in cm. Default changed to 80 in the table; `UVeloxMovementSettings::AirControlScale`, `Tools/editor/create_bootstrap_content.py` and the `SettingsDefaults` test (`AirControlScale == 32 × UnitScale`) follow. Without it CPM air control turns 2.5× too slowly.
- **A6 — Defect: ground acceleration during knockback grace (§1).** Q3 `PM_WalkMove` uses `pm_airaccelerate` (not `pm_accelerate`) while `PMF_TIME_KNOCKBACK` is set — this is the "temporarily lose full control" effect that makes machine-gun hits slide a grounded player and keeps rocket knockback from being cancelled by counter-steering. `GroundMove` must use `AirAcceleration` for substeps with grace > 0. Test `Knockback` extended (§7).
- **A7 — Knockback grace semantics recorded.** `max(existing, new)` instead of Q3's "set only if no timer runs" (Q3 also lets `PMF_TIME_LAND` suppress the knockback timer for 250 ms after a hard landing; not reproduced). Grace is counted down once per `PerformMovement` by the move's dt and sampled at move start for every `CalcVelocity` call of that move; a phys-mode change mid-move sees a grace stale by at most one move — accepted. The 25-free-ticks/resume-on-26 boundary in §7 is one 8 ms frame longer than Q3's `PM_DropTimers` order; accepted.
- **A8 — Interface for tasks 02/04.** `FVeloxMoveParams` is built once per `PerformMovement` (and in `SetMovementSettings`), cached as a member and reused by every `CalcVelocity` call of that move (engine `PhysFalling` l.4933 zeroes `Velocity.Z` around `CalcVelocity` and swaps `Acceleration` for `FallAcceleration`, so `AirMove`'s "Z untouched" contract holds as is). No sim signature changes; `JumpPadLaunchVelocity` keeps three parameters, validation lives on the actor.
- Deliberately deferred (CPM features outside §1): double-jump bonus, ramp-jump Z bonus, crouch-slide. Not in M1.

### 2026-10-24 — design review of task 02 (`UVeloxMovementComponent`, `AVeloxCharacter`), architect

Reviewed against UE 5.8.4 `CharacterMovementComponent.cpp` (`PhysWalking` l.5653, `PhysFalling` l.4887, `MoveAlongFloor` l.5552, `ComputeGroundMovementDelta` l.5489, `CheckFall` l.5401, `StartFalling` l.5427, `ProcessLanded` l.6373, `StepUp` l.7561, `IsValidLandingSpot` l.7374, `FindFloor` l.7209, `Crouch`/`UnCrouch` l.3262/3355, `MoveAutonomous` l.10664, `ClientUpdatePositionAfterServerUpdate` l.8606, `FSavedMove_Character::SetMoveFor` l.12761) and `Character.cpp` (`CheckJumpInput` l.1575, `ClearJumpInput` l.1609, `ResetJumpState` l.368, `OnMovementModeChanged` l.1525). Verdict: **pass with fixes** (A13 before the human playtest; A12/A14 are task-04 instructions; the rest are small follow-ups). Body text above has been adjusted; this section records the decisions.

- **A9 — D1 ramp exit: stateless climb rate accepted; `MaintainHorizontalGroundVelocity` row withdrawn; catch-air criterion made Q3's (§1, §2, §5).** The ADR's cache could never hold a value: `PhysWalking` calls `MaintainHorizontalGroundVelocity()` at the top of every iteration, before `CalcVelocity` and the catch-air test, and `Velocity` is horizontal at that point. The implementer's `ComputeRampExitVelocityZ(N) = max(0, −(V_xy·N)/N.z)` is exactly the vertical rate `ComputeGroundMovementDelta` produces for horizontal `Delta` with `bMaintainHorizontalGroundVelocity` (`RampMovement.Z = −(N·Delta)/N.z`), so the pawn leaves the ramp with the velocity it was actually moving at. Verified on both fall paths: catch-air (`ShouldCatchAir` → `HandleWalkingOffLedge` → `StartFalling`, l.5820–5828) and walked-off-edge (`CheckFall` → `HandleWalkingOffLedge` → `StartFalling`, l.5410–5414); in both, `Velocity` is still the iteration's move velocity (the displacement recompute at l.5870 comes later and is never reached because both paths `return`). Side of a ramp: `V_xy ⟂ slope` → `V·N = 0` → `Z = 0`. Flat ledge: `N.z ≥ cos(RampExitMinAngle)` → `0`. Descending: negative climb → `0` (Q3 would keep the negative Z; a down-ramp normally ends on a floor, accepted). Deterministic: a pure function of `Velocity` and the floor normals of the move, identical on client and server; the `SavedRampExitVelocityZ` field of §5 is dropped. Change requested: replace the hard-coded `CatchAirNormalZMargin = 0.01` (a magic number that also contradicts `RampExitMinAngle = 5°`: `1 − cos 5° = 0.0038 < 0.01`, so 5–8° ramps never catch air at a platform edge) with the Q3 `PM_GroundTrace` kick-off rule already used by `IsValidLandingSpot`: catch air iff `((V_xy, Zc) | New.ImpactNormal) > RampSlideMinNormalSpeed`. One criterion for "can the pawn stay on this floor" in both directions. Optional (rare, perch-only): compute the walked-off-edge value from `OldFloor` with the `!bLineTrace` guard by overriding `CheckFall` instead of `HandleWalkingOffLedge`; not required for M1.
- **A10 — D2 crouch speed scale on the ground only (§1 table, §2).** Q3 `PM_CmdScale` has no duck term; `pm_duckScale` is applied in `PM_WalkMove` only. Confirmed. `GetMaxSpeed()` (engine readers) aligned: crouch scale in Walking/NavWalking, plain `MaxGroundSpeed` in Falling. Moot while A11 holds.
- **A11 — Crouch disabled in M1 (§1 table, §2 inputs). Decision (a) of the implementer's options.** Root cause: the engine's crouch is built around the class default object — `UnCrouch` restores `GetClass()->GetDefaultObject<ACharacter>()` capsule size (l.3362/3380), `Crouch(bClientSimulation)` on simulated proxies first resets to the CDO size (l.3288), `OnStartCrouch`/`OnEndCrouch` compute `HalfHeightAdjust` from the CDO (l.3335, `Character.cpp` l.499/518), `GetDefaultHalfHeight()` reads the CDO. With geometry applied per instance from `UVeloxPawnData` (37.5/70) the CDO stays at the `ACharacter` default (34/88), so the first `UnCrouch` would grow the pawn to the wrong size on every machine. - **A12 — `bAutoHop=false` follows Q3 `PMF_JUMP_HELD`, via a `bJumpLatched` flag (§1, §2, §5). Partly superseded by A17: `PendingKnockback` is no longer assigned in `PrepMoveFor` either; the `KnockbackGrace` rule and the `PerformMovement` order stand.** `KnockbackGrace` is derived state like `Velocity`: `PrepMoveFor` must **not** restore it from the saved move (that would overwrite the server's corrected value for the first replayed move and desynchronise every later one); it chains — `OnClientCorrectionReceived` sets it from the response container, each replayed `PerformMovement` decrements it. `SavedKnockbackGrace` exists for `CanCombineWith` and debugging only. `PendingKnockback` is input-like (a pad overlap during move N is consumed at the start of N+1) and is **assigned** in `PrepMoveFor`, never accumulated, so a re-fired overlap during the replay plus the restore stays idempotent for override launches and correct for additive ones. `MoveStartKnockbackGrace` is derived inside `PerformMovement` from the chained value and needs no saving. ### 2026-10-24 — ruling on the A13 wall-slide figure (task 05 `Velox.Movement.Scripted.WallSlide`), architect

The test measures 895.9 cm/s for a 45° slide along the corridor wall at 120 Hz; A13 expected ≈ 566 (`800·cos 45°`) ± 5 %. Read `VeloxMoveSim.cpp` (`ApplyFriction`, `Accelerate`, `GroundMove`), `VeloxMovementComponent.cpp` (`CalcVelocity`, `HandleSlopeBoosting`) and the test; compared with Q3 `PM_WalkMove` → `PM_StepSlideMove`/`PM_SlideMove`. Verdict: **the sim is Q3-faithful, A13's number was wrong; the test assertion changes, the code does not.**

- **A23 — A13's wall-slide figure corrected: the 45° wall slide settles at `a·W·cos θ / f` (≈ 943 cm/s), not `W·cos θ` (§2 table, A13, §7).** Derivation (W = `MaxGroundSpeed` 800, a = `GroundAcceleration` 10 /s, f = `GroundFriction` 6 /s, θ = 45°, substep H ≤ 8 ms, one engine clip per tick dt = 1/120 s):
  1. The engine's displacement recompute (`PhysWalking`, `Velocity = (NewLoc − OldLoc)/dt` after `SlideAlongSurface`/`StepUp`) is a projection onto the wall plane, so every tick starts with `V = (v, 0)` (x along the wall, y into it).
  2. `ApplyFriction` is a uniform scale `1 − f·H` while speed > `StopSpeed` (250), so the x and y components decouple.
  3. `Accelerate` adds `a·H·W` along `wishdir = (cos θ, sin θ)` whenever `V·wishdir < W`: the x component gains `a·H·W·cos θ` per substep regardless of the y component.
  4. Along-wall recurrence per substep: `v' = v(1 − fH) + a·H·W·cos θ`; fixed point `v* = a·W·cos θ / f = 10·800·0.7071/6 = 942.8 cm/s`, independent of H and of how many substeps run between clips (numerically 942.7 for dt = 8, 8.33, 16.7 and 33 ms).
  5. Clamp check at the fixed point: `V·wishdir ≤ (942.8 + 2·33)·0.7071 = 714 < 800` — the `addspeed` clamp never bites at 45° for dt < 50 ms. It bites only for N ≥ 7 substeps per clip (a ≥ 50 ms hitch frame → 895) or shallow walls; in general `v* = min(a·W·cos θ / f, W / cos θ)` (clamp regime for θ ≲ 33° with these parameters).
  6. Q3 does exactly the same: `PM_Friction` → `PM_Accelerate` → `PM_SlideMove` clips `pm->ps->velocity` against the wall every 8 ms frame; the same recurrence gives `10·320·0.7071/6 = 377 ups > 320 ups` — the well-known Q3 effect that hugging a wall at an angle is faster than running. 566 is the along-wall component of *wishvel*, which is not the terminal speed; the clamp is on `V·wishdir ≤ W`, not on `|V| ≤ W·cos θ`.
  7. The engine's 895.9 (= 0.950 · v*) is not a sim deviation: the equilibrium is extremely sensitive to any per-tick along-wall displacement loss δ — `Δv = δ / (f·dt²)` — so 0.02 cm per tick (sub-millimetre sweep/contact handling in the `StepUp`/`SlideAlongSurface` path) costs 48 cm/s at 120 Hz; the same δ at 60 Hz would cost ≈ 12 cm/s. The figure is therefore a property of the engine's sweeps at the test tick rate; the scripted test keeps `TickDt = 1/120` fixed.
  **Consequences.** (i) It is correct Q3 behaviour that the HUD shows > `MaxGroundSpeed` while pressing into a wall at an angle; nothing in the sim or the CMC changes. (ii) **Test assertion (replaces the A13 check):** `Expected = min(a·W·cos 45° / f, W / cos 45°)` computed from `GetSimParams()` (942.8 for the defaults); pass iff `|Velocity.Y| < 1 cm/s` (clipped), `GetSpeed2D() > MaxGroundSpeed` (the Q3 wall-hug property — catches a reintroduced `MaxSpeed` clamp or a lost clip, both of which give ≤ 800), and `0.90·Expected ≤ GetSpeed2D() ≤ 1.01·Expected` (848.5–952.2 for the defaults; the lower margin covers the engine's contact loss with 2× headroom, the upper one is float noise — the sim cannot exceed the analytic equilibrium). Drop the `AddWarning`; `AddInfo` prints measured, expected and deviation in %. (iii) If an engine upgrade moves the value outside the band, first log per tick `(NewLoc − OldLoc).X` against `Velocity.X·dt` before the recompute to confirm δ, then revisit the band — not the sim. (iv) The stairs half of A13 is unchanged.
