## Context

CLAUDE.md non-negotiables in order: movement feel (a powerup that changes speed must go through the predicted move simulation, never through a replicated multiplier the client learns late), frame rate and readability, multiplayer from day one (every item, timer and phase is server-authoritative and replicated; nothing trusts the client), bots on the same movement component (M4 bots read item state through the same API the HUD uses). Tech stack: C++ for everything network-relevant, Blueprints for UI, tuning and level scripting; GAS for pickups, powerups, health/armor; Lyra as reference, ideas not modules.

What exists (M2): ASC on `AVeloxPlayerState` with `UVeloxHealthSet` (Health, MaxHealth, Armor, MaxArmor, metas incl. the unused `IncomingHealing`) and `UVeloxAmmoSet`; `UVeloxCombatSettings` (B1, loaded on both sides) with `HealthHardCap 200`, `MaxArmor 200`, the Q3 decay (`UVeloxGE_HealthDecay`, B4), `UVeloxGE_SpawnInit`; `FVeloxDamageMath` with `FVeloxDamageInput{Damage, Armor, bSelf, bNoArmor, bNoKnockback, bProtected, KnockbackScale}`; `VeloxEffects::MakeDamageSpec(SourceASC, FVeloxDamageSpecParams)`; `UVeloxWeaponInventoryComponent` (bitmask `OwnedMask` owner-only, `CurrentIndex` to everyone, `AddWeapon(Def, Ammo)`, `ResetToLoadout`, predicted switch index, `ResolveSelectInput`); `UVeloxWeaponDefinition::PickupAmmo`; `AVeloxGameMode` (`AGameMode`, scoring in `PlayerDied`, `PendingRespawns`, `ChoosePlayerStart` via world-free `VeloxSpawn::Select`, `AssignPlayerColor`); `AVeloxGameState` with the server-local `FOnVeloxKill OnKill` and `FVeloxKillEvent`; `AVeloxPlayerController` (`ClientConfirmHit`, `ServerRequestRespawn`, hit-confirm state, `PlayerTick` ability input B6); `AVeloxHUD` (Canvas: hit marker, death overlay, non-shipping movement block); `UVeloxCombatFeedbackComponent` (native cue handling, beam, hit confirm); `UVeloxMovementComponent` with `FVeloxMoveParams`/`FVeloxMoveInput` (`WishSpeed` capped by `MaxGroundSpeed`, crouch scale), `FVeloxMoveResponseDataContainer` (A18 snapshot, `ConfirmedSelfKnockbackSeq`), move-timed events with the wrap-aware `IsMoveTimeDue` (B25), `GetServerClientMoveTimeStamp()`; `AVeloxDummyController` and `UVeloxScriptedInputComponent` for headless soaks; `Tools/editor/*.py` content scripts (data assets, input assets, maps) run with `-nullrhi`.

Build-host constraint that shapes the UI decision: no agent can open the Unreal editor (headless Linux VM; the Mac is the human's). Widget Blueprints cannot be authored by agents — the Python editor API exposes neither `UWidgetBlueprint::WidgetTree` nor the UMG designer, so a `WBP_*` asset created by script would be an empty shell. Everything in M3 that the agents must be able to build, test and iterate on is therefore C++.

Units: 1 Q3 unit = 2.5 cm (`UnitScale`); times in seconds; Q3 numbers are vanilla 1.32 defaults (`bg_misc.c`, `g_items.c`, `g_combat.c`, `g_active.c`, `g_main.c`); CPMA variants are an open question like in ADR 0003.

## Decision

### 1. Items: one definition asset, one placed actor class, one registry

- `UVeloxItemDefinition : UPrimaryDataAsset` (`Items/VeloxItemDefinition.h`, assets `Content/Items/DA_Item_<Name>` created by `Tools/editor/create_item_content.py`, idempotent like the weapon script): `FGameplayTag ItemTag` (`Velox.Item.<Type>.<Name>`), `FText DisplayName`, `EVeloxItemType Type {Health, Armor, Ammo, Weapon, Powerup}`, `int32 Quantity`, `EVeloxHealthCap HealthCap {MaxHealth, HardCap}` (health only), `float RespawnSeconds`, `FFloatInterval InitialSpawnDelay` (0–0 except powerups), `bool bGlobalPickupSound`, `bool bMajorItem` (item timers, bot priority), `float BotBaseValue` (M4), `TObjectPtr<const UVeloxWeaponDefinition> Weapon` (Weapon), `FGameplayTag AmmoTag` (Ammo), `TSubclassOf<UVeloxGE_Powerup> PowerupEffect` + `float PowerupSeconds` (Powerup), `FGameplayTag PickupCueTag` (reserved for M5; M3 cosmetics are actor-driven, §2), greybox look `FColor PlaceholderColor` + `FVector PlaceholderScale`, M5 adds mesh/sound soft refs. No item table and no net id: a placed pickup references its definition directly and clients load it with the map.
- Q3 table (the content script writes exactly this; `UVeloxCombatSettings` is not touched by it):

  | Item | Quantity | Cap | Respawn | Notes |

  | Health.Small / Medium / Large | 5 / 25 / 50 | HardCap 200 / MaxHealth / MaxHealth | 35 | Q3: only the 5 and the Mega stack past max |
  | Health.Mega | 100 | HardCap 200 | 35 | `bMajorItem` |
  | Armor.Shard / Yellow / Red | 5 / 50 / 100 | MaxArmor 200 | 25 | vanilla: every armor fills to 200; Yellow/Red `bMajorItem` |

  | Weapon.<Six> | `Weapon->PickupAmmo` (MG 40, SG 10, RL 10, LG 100, RG 10, PG 50) | — | 5 (`UVeloxGameModeDefinition::WeaponRespawnSeconds`, §5) | weapon-stay per mode, off in FFA/Duel |
  | Powerup.Quad / Haste / Regen / BattleSuit | 30 s | — | 120 | initial delay 30–60 s (Q3 `45 + crandom()*15`), `bMajorItem`, `bGlobalPickupSound` |

- `AVeloxPickup : AActor` (`Items/VeloxPickup.*`), placed in maps (`bNetLoadOnClient`), `bReplicates`, `bAlwaysRelevant = true` (item timers and bots need every item; 30–60 actors), `SetNetDormancy(DORM_DormantAll)` with `FlushNetDormancy()` on every state change, `NetUpdateFrequency 10`. Components: root scene, `UBoxComponent Trigger` 75 × 75 × 90 cm (Q3 `ITEM_RADIUS 15` u box, z −15..+21 u), `ObjectType WorldDynamic`, overlaps `Pawn` only, ignores everything else including the `Weapon` trace channel and the `Projectile` object channel (B15), generates overlap events on server and clients; `UStaticMeshComponent Placeholder` (unlit coloured cube/cylinder from the definition, `NoCollision`, slow rotation client-side only). Replicated: `float RespawnServerTime` (`OnRep`; 0 = available, otherwise the server world time at which it respawns), `TObjectPtr<APlayerState> LastTakenBy` (spectator feed, prediction confirmation), `uint8 TakeCount` (increments per take so two takes between two replications are both seen). Server-only: timer handle, `FVeloxPickupTimer` (world-free, §2). `Reset()` override: back to the initial state including a fresh initial delay (`ResetLevel`, §5). Properties: `TObjectPtr<const UVeloxItemDefinition> Definition` (EditInstanceOnly), `bool bSuspended` (no bobbing; M5).
- `UVeloxItemRegistrySubsystem : UWorldSubsystem` (`Items/VeloxItemRegistrySubsystem.*`, both sides): pickups register in `BeginPlay`; `GetPickups()`, `GetMajorPickups()`, `FindByTag(ItemTag)`, delegates `OnPickupTaken(AVeloxPickup*, APlayerState*)`, `OnPickupRespawned(AVeloxPickup*)` fired on the server by the actor and on clients from `OnRep_RespawnServerTime` (a client's first update of a placed pickup whose take is older than `UVeloxCombatSettings::PickupTakeEventMaxAgeSeconds` (1 s) updates the state without an event, C10). The HUD (§7) and M4 bots (§9) read only this API.

### 2. Pickup resolution: server-authoritative grant, Q3 rules world-free, cosmetic-only client prediction

- **Rules** in `Items/VeloxPickupRules.h` (`CoreMinimal.h` only, unit-tested): `VeloxPickupRules::CanGrab(const FVeloxPickupQuery&)` and `Gain(...)` implement Q3 `BG_CanItemBeGrabbed` + `Pickup_*`: health — grab iff `Health < Cap` (Cap = `MaxHealth` or `HealthHardCap` per definition), gain `min(Quantity, Cap − Health)`; armor — grab iff `Armor < MaxArmor`, gain `min(Quantity, MaxArmor − Armor)`; ammo — grab iff `Ammo < MaxAmount`, gain `min(Quantity, MaxAmount − Ammo)`; weapon — always grabbable, ammo gain Q3 `Pickup_Weapon`: `Have < Quantity ? Quantity − Have : 1` (dropped items would give full ammo — deferred), capped at `MaxAmount`; powerup — always grabbable, duration adds to the remaining time (Q3 `Pickup_Powerup`: `powerups[tag] += quantity × 1000`), no cap. `FVeloxPickupTimer` (same header): `Take(Now, RespawnSeconds)`, `IsAvailable(Now)`, `TimeRemaining(Now)`, `ScheduleInitial(Now, Delay)`, `Reset()`; pure arithmetic on doubles so the test can assert exact respawn instants.
- **Server flow** `AVeloxPickup::OnTriggerBeginOverlap(Pawn)` → `TryPickup(AVeloxCharacter*)`: authority, available, pawn alive and not a corpse, not `Velox.State.MatchFrozen` (§5), `CanGrab` on the pawn's PlayerState attributes → apply through GAS on the PlayerState ASC: health `UVeloxGE_Heal` (Instant, Additive on `Health`, `SetByCaller.Health` = gain — the gain is computed by the rule, the GE never knows the cap), armor `UVeloxGE_ArmorGain` (Instant, Additive on `Armor`, `SetByCaller.Armor`), ammo `UVeloxGE_AmmoCost` with a positive magnitude (`VeloxEffects::MakeAmmoGainSpec` alias), weapon `Inventory->AddWeapon(Def, Gain)` (grants the fire ability — the client can predict the first shot once the spec replicates, ADR 0003 §4), powerup §3. Then `TakeCount++`, `LastTakenBy`, `RespawnServerTime = Now + Respawn` (weapon-stay: the weapon is granted, the item stays, and a taker who already owns the weapon is refused — no ammo farming; the CTF ammo rule is M7's, C9), `FlushNetDormancy`, registry `OnPickupTaken`, server log `VeloxPickup item= by= gain= respawn_in=`, respawn timer. Respawn: `RespawnServerTime = 0`, flush, `OnPickupRespawned`, then **a pawn standing inside the trigger takes it immediately** (`GetOverlappingActors` → `TryPickup`; Q3 evaluates touches every frame). The game mode's `ItemRespawnScale` and `WeaponRespawnSeconds` (§5) are read from the GameState's definition at take time.
- **Prediction policy (100 ms RTT, justified):** the owning client predicts only what Q3's `cg_predictItems` predicts — the *event*, never the attributes. On the autonomous pawn's local overlap (fires during predicted moves) `AVeloxPickup::TryPredictTake()`: if `RespawnServerTime == 0`, no pending prediction, and `CanGrab` holds on the client's replicated attributes → hide the placeholder, play the pickup sound locally, remember `PredictedTakeCount = TakeCount`, `PredictedUntil = Now + UVeloxCombatSettings::PickupPredictionTimeout` (new, 0.5 s = two RTTs at the 250 ms ping limit), and for a weapon call `Inventory->PredictOwned(Index, PredictedUntil)` (the owning client ORs predicted bits into `OwnsIndex` so a slot press switches at once — Q3 predicts exactly `STAT_WEAPONS`; the 0.45 s drop+raise exceeds the RTT, so the fire spec has replicated by the time the switch ends). Reconciliation in `OnRep_RespawnServerTime`/`OnRep_LastTakenBy`: taken by me → confirmed (HUD "picked up X" from the registry delegate); taken by someone else → the item stays hidden, no message, the predicted weapon bit is dropped; no replication before `PredictedUntil` → the server refused (full health, race) → unhide, drop the bit. Attributes arrive ≈ RTT/2 + one PlayerState update later (≈ 60–70 ms at 100 ms RTT) and the HUD number steps then. Why not predict attributes: a predicted Instant GE on a replicated attribute is overwritten by the next replicated value (the ammo-cost caveat ADR 0003 §5 accepts for a −1 is unacceptable for a +100 that may be refused), and health is where a visible revoke hurts most; the server never reads client pickup claims. Replays (`ClientUpdatePositionAfterServerUpdate`) may re-fire the overlap; `TryPredictTake` is idempotent per `TakeCount`. Autoswitch (Q3 `cg_autoswitch`): owning-client rule in `OnRep_OwnedMask` — a newly owned weapon is selected through the normal switch ability when `UVeloxGameUserSettings::bAutoSwitchOnPickup` and the current weapon is MG or Gauntlet (Q3 default behaviour); one switch path, predicted as before.
- **Cosmetics are actor-driven, not cues:** `OnRep_RespawnServerTime` hides/shows the placeholder and plays the pickup sound at the item (skipped when this client already predicted this `TakeCount`), the respawn sound on return, and `bGlobalPickupSound` items play for everyone (Q3 `EV_GLOBAL_ITEM_PICKUP`). The `GameplayCue.Pickup.*` tags stay reserved for M5 FX on the pawn.

### 3. Powerups: C++ duration GEs on the PlayerState ASC, Quad and Battle Suit in the damage math, Regen as a periodic execution, Haste in the move timeline

- `UVeloxGE_Powerup : UGameplayEffect` (`Items/VeloxPowerupEffects.*`): HasDuration with `SetByCaller.Duration`, `StackingType None`, grants its tag; subclasses `_Quad` (`Velox.Powerup.Quad`), `_Haste` (`Velox.Powerup.Haste`), `_Regen` (`Velox.Powerup.Regen`, Period 1.0, not executed on application, execution `UVeloxRegenExecution`), `_BattleSuit` (`Velox.Powerup.BattleSuit`). Mixed replication: the owner holds the full spec (remaining time for the HUD, §7), everyone else gets the tag (`MinimalReplicationTags`) for the body tint and the scoreboard icon. Pickup while active: `ASC->ModifyActiveEffectStartTime(Handle, +PowerupSeconds)` (extends in place, replicates through `StartServerWorldTime`, no removal cue; fallback if the function is missing in 5.8: remove and re-apply with `Remaining + PowerupSeconds`). **Powerups are lost on death** (Q3 `ClientSpawn`): `UVeloxGE_SpawnInit` additionally removes effects with `Velox.Powerup` (dropping them as items is deferred). Looping cue `GameplayCue.Powerup.<Name>` added/removed with the GE: M3 handles it natively in `UVeloxCombatFeedbackComponent` (body material parameter `PowerupTint`: Quad blue, Haste yellow, Regen red, Battle Suit green on `M_PlayerBody`; readability over fidelity), M5 adds assets.
- **Quad (×3, `UVeloxCombatSettings::QuadDamageFactor 3`)** is applied where Q3 applies it — at fire, to the raw damage, before knockback: `FVeloxDamageSpecParams::DamageScale` (default 1) multiplies `Damage` in `VeloxEffects::MakeDamageSpec` (integer result, Q3 `damage *= g_quadfactor`); knockback therefore triples too (quad rocket jumps go higher, as in Q3). Hitscan: the server reads the shooter ASC's `Velox.Powerup.Quad` when resolving the shot. Projectiles: `AVeloxProjectile` gains a replicated initial-only `bool bQuad` captured at spawn (Q3 stores the factor in the missile), used at explosion for direct and splash damage to others (the base damage is scaled before the falloff, Q3 `fire_rocket`); the owner's fake, the predicted self-splash and the server's move-timed self-splash (B25) all use the **move-timeline** quad state at the fire stamp (`IsPowerupActiveAt(QuadEnd, FireMoveTimeStamp)`, C2), so a quad rocket jump is predicted with the same factor the server applies. No change to `FVeloxDamageMath::Apply`.
- **Battle Suit (victim side, Q3 `G_Damage` order):** knockback is computed from the raw damage as today, then `if bBattleSuit: bRadius → HealthLoss = ArmorLoss = 0 (knockback stays); else Damage = Damage × BattleSuitDirectDamageScale (0.5, integer)`, then self-halving, minimum 1 (B3), armor. `FVeloxDamageInput` gains `bBattleSuit`, `bRadius`; `UVeloxDamageExecution` sets them from the target's tag and the context flag. Q3 also exempts falling/slime/lava — none exist.
- **Regen (server, Q3 `ClientTimerActions`):** every second while tagged: `Health < MaxHealth → +15 capped at MaxHealth × RegenSoftCapScale (1.1)`, else `Health < HealthHardCap → +5 capped at HealthHardCap`; `UVeloxDecayExecution` returns early for Health while the target has `Velox.Powerup.Regen` (the Q3 `else` branch; armor decay unaffected). Settings: `RegenHealthPerTick 15`, `RegenOverTick 5`, `RegenSoftCapScale 1.1` on `UVeloxCombatSettings`.
- **Haste (speed × 1.3, fire rate × 1.3) — the prediction-relevant powerup.** Replicated tags reach the owner ≈ RTT/2 after application and a replicated duration GE ends on the client up to one RTT late (ADR 0003 B18 facts), so a tag-driven speed scale would mispredict ≈ 0.3 × 800 cm/s × RTT ≈ 24 cm at every pickup *and* every expiry, with echoes (A24). Decision, in the spirit of B25: **powerup end times live in the owner's move-time domain and are carried in every move response.** `UVeloxMovementComponent` gets `FVeloxPowerupMoveTimes { float HasteEnd = 0; float QuadEnd = 0; }` (`Movement/VeloxNetworkMoveData.h`). Server: `AVeloxCharacter` (server, after `InitAbilityActorInfo`) registers `ASC->RegisterGameplayTagEvent(Powerup_Haste/Quad)` and the pickup's powerup grant calls `Character->ServerRefreshPowerupMoveTimes()` (also after an extension, which fires no tag event): `End = GetServerClientMoveTimeStamp() + RemainingSeconds` (bots: world time, their stamp domain per B12), 0 when absent. The server **sends both floats in `FVeloxMoveResponseDataContainer` on acks and corrections** (`SerializeOptionalValue` against 0 — one bit while no powerup is active) and also snapshots them in `FVeloxCorrectionState` (A18) so a correction replay sees the values of its check time. Client: stores them on receipt before any replay. **Evaluation per move on both ends (C1):** `IsPowerupActive(End, MoveTime, P) = End != 0 && PowerupTimeLeft(End, MoveTime, P) > 0`, where `PowerupTimeLeft` is `End − MoveTime` reduced into `(−P/2, P/2]` and `P = MinTimeBetweenTimeStampResets` (the engine subtracts exactly `P` at a reset on both ends, so the stamp domain is modular); ends are normalised into `(0, P]`, the remaining time is clamped to `0.45 P`, and non-replayed moves drop an end more than `P/4` in the past. A natural GE expiry keeps the end (both ends flip at the same stamp); only a premature removal (death, re-apply fallback) zeroes it. The earlier `!IsMoveTimeDue(End, MoveTime, P)` wording was wrong: it drops every active powerup at the 240 s time-stamp reset. `PerformMovement` computes `SpeedScale = IsPowerupActive(HasteEnd, GetCurrentMoveTimeStamp()) ? SimParams.HasteSpeedScale : 1` and passes it as `FVeloxMoveInput::SpeedScale` (new, default 1): the sim scales the wish-speed caps `MaxGroundSpeed` and `AirMaxWishSpeed` (Q3 `ps->speed` enters only through `PM_CmdScale`, i.e. `wishspeed`); `AirStrafeMaxWishSpeed` (CPM constant), accelerations, friction, `StopSpeed`, `JumpVelocity` are untouched; `GetMaxSpeed()` applies the same scale for navigation/AI. Replays recompute the scale from the saved move's timestamp — no saved field except `bSavedHasteActive` for `CanCombineWith` (moves on different sides of the end never combine). `HasteSpeedScale 1.3` is a `UVeloxMovementSettings` tunable (it is movement feel); `HasteFireRateScale 1.3` lives in `UVeloxCombatSettings`. **Fire rate:** on the shooter's machine `UVeloxGameplayAbility_Fire` divides `FireInterval` by the scale when `IsPowerupActive(HasteEnd, ClientMoveTimeStamp)`; the server uses its own tag (exact) for the bucket refill rate and the spacing rule (B19) — the ≤ RTT disagreement at the edges is inside `FireRateJitterToleranceSeconds`. Residuals, accepted: after a Haste pickup the client predicts at ×1.0 until the first response that carries the new end (≈ one RTT) → one correction ≤ 24 cm at 100 ms, smoothed like any correction; expiry and extensions are exact (0 corrections); a Haste taken by another player costs nothing. `velox.move.HasteRun` soak (§10) measures this.

### 4. Item timers

Derived, never replicated separately: `AVeloxPickup::GetTimeUntilRespawn()` = `RespawnServerTime − GameState->GetServerWorldTimeSeconds()` on clients (the server-time estimate is accurate to a frame, B13); `LastTakenBy` names the taker. Visibility is a mode rule `EVeloxItemTimerVisibility { Nobody, Spectators, Everyone }` (§5; Duel and FFA default `Spectators` — the standard duel rule: spectators and casters see Mega/RA/YA/powerup timers, players never) applied in the HUD view model on the client; the HUD shows `bMajorItem` pickups as `<name> <mm:ss>` plus "taken by <colour>". Known gap, accepted for M3 and listed for M6 hardening: `RespawnServerTime` replicates to every client, so a modified client can display timers in Duel; a role-gated channel (spectators only) is an M6 item once spectating is a first-class flow.

### 5. Game modes as data, one phase machine on the server, replicated through the GameState

- `UVeloxGameModeDefinition : UPrimaryDataAsset` (`GameModes/VeloxGameModeDefinition.h`, assets `Content/Data/DA_GameMode_FFA`, `DA_GameMode_Duel` from `create_item_content.py`): `FGameplayTag ModeTag` (`Velox.Mode.FFA/Duel`), `FText DisplayName`, `int32 FragLimit` (FFA 20, Duel 0), `int32 TimeLimitSeconds` (FFA 600, Duel 600), `int32 MinPlayersToStart` (2, 2), `int32 MaxActivePlayers` (16, 2 — extra joiners spectate), `bool bRequireReady` (false, true), `float WarmupCountdownSeconds` (20, Q3 `g_warmup`), `EVeloxOvertimeRule { None, SuddenDeath, Timed }` (FFA None — ties stand; Duel SuddenDeath — next frag wins), `float OvertimeSeconds` (Timed only, 120), `float PostMatchSeconds` (15), `bool bWeaponStay` (false, false; CTF turns it on in M7), `float WeaponRespawnSeconds` (5; team modes 30), `float ItemRespawnScale` (1.0), `EVeloxItemTimerVisibility ItemTimers` (Spectators), `bool bLeaverForfeits` (false, true), `bool bAllowJoinDuringMatch` (true, false; C6), `TObjectPtr<const UVeloxCombatSettings> CombatSettingsOverride` (B1; null = default), `TObjectPtr<const UVeloxPawnData> PawnDataOverride` (null). `AVeloxGameMode` keeps all logic; `AVeloxGameMode_FFA` and `AVeloxGameMode_Duel` (ADR 0001) only set `GameModeDefinitionAsset` (config) and exist for `DefaultGame.ini` `GameModeClassAliases` (`?game=FFA`, `?game=Duel`) and per-map defaults. `InitGame` loads the definition; `InitGameState` replicates it (`AVeloxGameState::GameModeDefinition`, `COND_InitialOnly`) and `CombatSettingsOverride`.
- **Phase machine** `EVeloxMatchPhase : uint8 { Warmup, Countdown, Live, Overtime, PostMatch }`, owned by the server in `AVeloxGameMode::SetPhase(NewPhase)`; the engine match state stays `InProgress` from `BeginPlay` through Overtime (`ReadyToStartMatch` → true as soon as the GameState exists, so players spawn and frag during Warmup as in Q3) and becomes `WaitingPostMatch` via `EndMatch()` at PostMatch (`PlayerCanRestart` false there — no respawns during intermission). Transitions, evaluated by the world-free `VeloxMatchRules::Evaluate(const FVeloxMatchInput&) → FVeloxMatchVerdict` (`GameModes/VeloxMatchRules.h`, unit-tested) on every kill, join, leave, ready change and a 1 Hz server timer: Warmup → Countdown when `ActivePlayers ≥ MinPlayersToStart` and (`!bRequireReady` or every active player is ready); Countdown → Warmup when that stops holding; Countdown end → **`ResetLevel()`** (engine: controllers, pawns, PlayerStates — scores — pickups via `AVeloxPickup::Reset`, projectiles via `Reset` → destroy, corpses destroyed) → `RestartPlayer` for every active controller → Live with `LiveStartServerTime`; Live → PostMatch when `FragLimit > 0` and a score reaches it (evaluated on the tick after the kill, B27, C8) or when `TimeLimit` elapses with a unique leader; Live/Overtime → Warmup (with the reset) when no active player remains (C8); Live → Overtime on a tie at the time limit when the rule is not None (SuddenDeath: first frag ends; Timed: `OvertimeSeconds` then re-evaluate, repeat); Live → PostMatch (winner = the remaining player) when a Duel player leaves and `bLeaverForfeits`; PostMatch → Warmup after `PostMatchSeconds` or when at least one human is active and every human is ready again (AI always counts as ready, C8), via `RestartMatch()` = `ResetLevel()` + `SetPhase(Warmup)` + restart players. Map change (`RestartGame()`/`ServerTravel`) is M7's rotation; M3 never travels. Warmup frags count on the scoreboard and are wiped by the reset. Spawn protection, respawn delays and loadouts are unchanged (ADR 0003 §8).
- **Replication (`AVeloxGameState`, 10 Hz, push model):** `Phase` (`OnRep` → `OnPhaseChanged` delegate on both sides), `PhaseStartServerTime`, `PhaseEndServerTime` (countdown end / time-limit end / overtime end / intermission end; 0 = open-ended), `LiveStartServerTime`, `FragLimit`, `TimeLimitSeconds`, `OvertimeCount`, `WinnerPlayerState`, `GameModeDefinition` and `CombatSettingsOverride` (initial only), the kill feed (§6). Clients compute every clock from `GetServerWorldTimeSeconds()`; the engine's `ElapsedTime` is not used. The GameMode exists only on the server and never replicates (engine); nothing on a client infers a phase change except from `Phase`.
- **Ready-up and spectators:** `AVeloxPlayerState::bReady` (replicated; consumed by the transition it caused — Countdown → Live, PostMatch → Warmup — and cleared on entering PostMatch; it survives a countdown abort in both directions of Warmup ↔ Countdown, C5), `AVeloxPlayerController::ServerSetReady(bool)` from `IA_Ready` (F3) and the scoreboard button; a `ready` console command for soaks. Leaving: `Logout` re-evaluates the rules.
- **Intermission:** at PostMatch the server applies `UVeloxGE_MatchFrozen` (`GameModes/VeloxMatchEffects.*`, Infinite, grants `Velox.State.MatchFrozen`; C7) to every ASC, `CMC->DisableMovement()` on every pawn, `UVeloxDamageExecution` treats the tag like Dead (zero loss, zero knockback), fire abilities add it to `ActivationBlockedTags`, projectiles in flight explode without effect; `ClientEnterIntermission(ViewTarget)` sets the view to the map's intermission camera (first `ACameraActor` tagged `Intermission`, else the player's own pawn) and forces the scoreboard open. `ResetLevel` clears all of it (the GE is removed by `GE_SpawnInit` and the pawns are destroyed anyway). ### 6. Scoreboard data, kill feed, match clock

- `AVeloxPlayerState` replicates `int32 Kills`, `int32 Deaths`, `bReady`, plus the engine `Score` (frags incl. the −1 for suicides, as M2), `CompressedPing`, `bOnlySpectator`, `PlayerColorIndex` (B29) and `GetPlayerName()` (from `?Name=`, set by the menu, §7; M6 replaces it with platform names). `PlayerDied` increments `Kills` (killer, non-suicide) and `Deaths` (victim) next to the existing score change; `Reset()` zeroes all three. - **Kill feed** replaces the server-local delegate's reach: `FVeloxKillFeed : FFastArraySerializer` on `AVeloxGameState` with `FVeloxKillFeedEntry : FFastArraySerializerItem { uint16 Seq; FString KillerName, VictimName; uint8 KillerColor, VictimColor; FGameplayTag DamageTag; bool bSuicide; float ServerTime }` (names snapshotted — a PlayerState may leave; late joiners receive the last `KillFeedLength 8` entries). `PlayerDied` appends; `PostReplicatedAdd` and the server path both broadcast `AVeloxGameState::OnKillFeedEntry` (clients) while `OnKill` keeps the richer server-only `FVeloxKillEvent` for M4 bots. `FVeloxKillEvent` is unchanged (B29).

### 7. HUD, scoreboard, menus, settings: C++ UMG with programmatic widget trees, data through C++ view models

- **Why not Widget Blueprints in M3:** no agent can author or iterate a `WBP_*` (Context). Decision: every widget is a C++ `UUserWidget` subclass that builds its own tree in `RebuildWidget()` (`if (!WidgetTree->RootWidget) { construct canvas/panels/text blocks with WidgetTree->ConstructWidget; } return Super::RebuildWidget();`), declares its elements as `UPROPERTY(meta = (BindWidgetOptional))` and exposes `UCLASS(Blueprintable)`; the class spawned for each screen is config (`[/Script/Velox.VeloxHUD] HUDWidgetClass=…`, likewise scoreboard, menus). A `WBP_HUD` subclass authored on the Mac (M5 art pass, or the human earlier) replaces the look without a code change: when the Blueprint supplies a tree, `RebuildWidget` leaves it alone and the named bindings fill it. This honours CLAUDE.md's "Blueprints for UI" as the authored end state while keeping M3 buildable and testable headless; it is listed as open question 2 for the human. ### 11. Budgets

Pickups: 60 dormant always-relevant actors, ≈ 20 B per state change per client, two changes per cycle — negligible; server overlap cost is the engine's. Kill feed entry ≈ 80 B reliable to each client. GameState 10 Hz with ≈ 30 B of phase/clock fields. Move response grows by one bit (no powerup) or 8 bytes. HUD: one view-model refresh per frame (< 0.05 ms), widgets without materials or textures; no tick on simulated proxies' pickups beyond the placeholder rotation (clients only, `bSuspended` stops it).

## Consequences

- Items are placed actors with data definitions; adding an item is a data asset plus a placement, and bots and HUD share one registry. The price is one always-relevant actor per item, bounded by map size.
- Pickups never predict attributes; HUD numbers step ≈ 60–70 ms late at 100 ms RTT while the sound, the hidden item and a predicted weapon slot are immediate — Q3's own behaviour.
- Haste and Quad end times travel in the move-time domain (one more response field); expiry is exact on both ends and a Haste pickup costs one small correction. This extends A18's snapshot and B25's timeline rule rather than inventing a second mechanism; `architect` reviews the movement task.
- One game mode class driven by data; FFA and Duel differ only in asset values. Restarts are in-place `ResetLevel` (no travel) — fast, PIE-friendly, headless-testable; map rotation is deferred.
- UI is C++ in M3 with an explicit, config-only path to Blueprint skins. Layout quality is judged by the human on the Mac; agents verify data binding headless.
- Settings and keybinds use engine persistence (`GameUserSettings.ini`, Enhanced Input user-settings save slot); nothing custom to migrate later.

## Alternatives considered

- **Item state on the GameState (array of timers) instead of per-actor replication:** fewer actors but a second source of truth for availability and an index scheme per map; rejected.
- **Pickups as GAS abilities on the pawn (Lyra `IPickupable` + ability):** the actor overlap plus a server-side rule is simpler and keeps prediction policy explicit; rejected.
- **Predicting attribute gains (predicted Instant GEs):** overwritten by replication, revokes on refusal; rejected (§2).
- **Haste as a replicated speed multiplier read from the tag:** two mispredictions per Haste life with echoes; rejected (§3). **Haste state in the client's move data:** the server would read a client claim; rejected (ADR 0001 §3).
- **Lyra `GamePhaseSubsystem` (phases as abilities), `GameplayMessageSubsystem` for the feed, `Experience` definitions:** more machinery than one enum, one FastArray and one data asset; rejected (ADR 0001 already rejects Experiences). The *idea* of a mode definition asset referencing pawn data and settings is adopted.
- **Map travel for restarts (`RestartGame`):** reconnects every client; `ResetLevel` is Q3's `map_restart`; rejected for M3.
- **Slate (`SCompoundWidget`) HUD instead of UMG:** no Blueprint path at all; rejected. **Empty `WBP_*` shells generated by Python:** cannot carry a tree; rejected. **Canvas HUD only:** no menus; rejected.
- **Custom keybinding save format:** Enhanced Input user settings exist for exactly this; rejected.

## Lyra: adopted vs rejected (this ADR)

Adopted: world pickup actor + definition asset granting through the owner's ASC (`ALyraWorldCollectable`/`IPickupable`, as an idea); powerups as duration GEs with granted tags and looping cues; `UGameUserSettings` subclass for machine settings and Enhanced Input user settings for key profiles; data-driven mode definition; one game-state object replicating phase and feed. Rejected: inventory fragments and item instances (ADR 0003 B-series), the Lyra HUD layout/UIExtension/Common UI stack, `GamePhaseSubsystem`, `GameplayMessageSubsystem`, `SettingsShared` save-game split, the Lyra scoreboard's message-based updates (we replicate state, not messages).
