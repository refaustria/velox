## Context

CLAUDE.md non-negotiable 4: bots use the same movement component as players. The M1–M3 build already guarantees the entry points (ADR 0002 §8): input reaches `UVeloxMovementComponent` only through `AddMovementInput` (wish velocity), `SetLocalMoveInput` (CPM key presence), `Jump()/StopJumping()` + `SetJumpHeld` (auto-hop), `Crouch/UnCrouch`, and external velocity only through `AddKnockback`; `bUseAccelerationForPaths = true` so engine path following would call `RequestPathMove` → `AddInputVector`, never velocity requests (which our `CalcVelocity` ignores). `AVeloxDummyController` (M2-07) proves the pattern: an `AAIController` with `bWantsPlayerState = true` feeding `AddMovementInput`/`SetLocalMoveInput` every tick, a PlayerState with the full ASC, respawning through `AVeloxGameMode::RestartPlayer` (B28, `bAutoRespawnAIControllers`), labelled and coloured like a player (B29).

Facts that shape the design:

- **Bots live only on the server.** AI controllers do not exist on clients; a bot pawn is an ordinary authority pawn whose moves run in `UCharacterMovementComponent::ControlledCharacterMove` on the server tick (no saved moves, no prediction, no corrections). Its lag-comp samples carry world-time stamps (B12), its powerup clock is world time (C1), its projectile self-splash resolves at the explosion from the tag (C2), and its fire abilities take the "listen host / local shooter" path (B37's local-rhythm rule). Everything M2/M3 built for the listen host is what bots use; nothing new crosses the wire for a bot beyond what a player pawn already replicates.
- **The engine's AI controller fights an FPS aim model.** `UpdateControlRotation` overwrites the control rotation from the focus point or the pawn's yaw every tick and zeroes pitch unless the focus actor is a pawn (verified l.463–467). Fire abilities take their direction from `GetControlRotation()` (B6). The bot controller therefore owns the control rotation outright (§1).
- **No agent can open the editor** (ADR 0004 Context): Behaviour Trees, Blackboards, StateTrees, EQS queries and AIPerception configs are editor-authored assets. Whatever the brain is, agents must be able to write, test and iterate it headless — the same reason the M3 UI is C++. Nav meshes are normally baked in the editor for the same reason; §3 chooses runtime generation on the server.
- **Determinism and tests.** ADR 0001 §4 requires automation tests for aim-error distribution and item-value scoring, and a functional map where a bot reaches a jump-pad-only platform. The world-free-core discipline of M1–M3 (`FVeloxMoveSim`, `FVeloxDamageMath`, `VeloxPickupRules`, `VeloxMatchRules`) extends to the bot: every decision rule is a pure function over plain structs with an `FRandomStream`, wired into the controller by thin glue.
- **Budget.** 60 Hz server, ≤ 16 pawns (ADR 0001 §3). A bot must cost a small fraction of a player pawn's movement + replication cost; nav queries and traces are the only expensive operations and are rate-limited (§13).

Units: cm, s; 1 Q3 unit = 2.5 cm (`UnitScale`). Q3 bot numbers (`ai_dmq3.c`, `ai_main.c`, `fuzzy weights`) are cited where a value starts from them; CPMA/other variants are not considered.

## Decision

### 1. A bot is an `AAIController` that produces player input every server tick; it never touches velocity

`AVeloxBotController : AAIController` (`Bots/VeloxBotController.*`; `AVeloxDummyController` stays as the soak dummy and is not touched):

- Constructor: `bWantsPlayerState = true` (ASC, scoreboard, colour — ADR 0001 §2), `bSetControlRotationFromPawnOrientation = false`, `PrimaryActorTick.bCanEverTick = true`, `TickGroup = TG_PrePhysics` (default). The engine adds a pawn tick dependency on its controller (`AController::AddPawnTickDependency`), so the controller's tick runs before the pawn's movement tick of the same frame: input written in `Tick` is consumed by this frame's `ControlledCharacterMove` — the same frame relationship a player's `PlayerTick` has (B6).
- **`UpdateControlRotation(float Dt, bool bUpdatePawn)` is overridden and does not call `Super`:** it sets the control rotation to the aim model's output (§8) — pitch included — and calls `Pawn->FaceRotation(NewRotation, Dt)` (yaw only reaches the capsule via `bUseControllerRotationYaw`, as for players). `SetFocus`/`SetFocalPoint` are never used.
- **One input struct per tick, applied through the player entry points.** `FVeloxBotInput { FVector2D WishDirWorld; float WishScale (0..1); bool bJumpHeld; bool bCrouch; FRotator View; bool bFireHeld; int32 SelectSlot (0 = none); }` is produced by the brain (§2) and applied by `ApplyInput(const FVeloxBotInput&, float Dt)` in this order: (1) `SetControlRotation(View)` via the override above; (2) `Pawn->AddMovementInput(FVector(WishDirWorld, 0), WishScale)` — the engine scales it by `GetMaxAcceleration()` = wish speed exactly as a player's `Input_Move`; (3) `CMC->SetLocalMoveInput(ForwardRight)` with `ForwardRight = (WishDir · ViewForward2D, WishDir · ViewRight2D) × WishScale` — the key-presence flags a player's stick would produce; with `bAirControl` (CPM) the bot snaps the pair to pure-forward or pure-side when `|minor| < CpmKeySnap (0.3)` because the CPM rules depend on key presence (M4 ships with CPM off, approved M1 defaults); (4) jump through **exactly the character's input handlers**: `AVeloxCharacter::SetJumpInput(bool bPressed)` (new, extracted from `Input_JumpStarted/Completed`: `Jump()` + `SetJumpHeld(true)` on press, `StopJumping()` + `SetJumpHeld(false)` on release) so bots and players cannot drift apart; (5) `Crouch()/UnCrouch()` on change; (6) weapon select: `ASC->AbilityInputTagPressed(InputTag.Weapon.Slot<N>)` this tick, `Released` next tick (what `UVeloxScriptedInputComponent::SelectWeaponSlot` does); fire: `AbilityInputTagPressed/Released(InputTag.Fire)` on edges; then **`ASC->ProcessAbilityInput(Dt, false)`** — the bot's equivalent of `AVeloxPlayerController::PlayerTick` (B6: after the rotation update, before the pawn moves). The fire ability activates on the authority-local path (no RPC, no prediction key, `FGameplayAbilityTargetData_VeloxShot` built from `GetPawnViewLocation()` and `GetControlRotation()`, `ViewServerTime = Now`), exactly as on a listen host.
- Never: `MoveTo` with velocity requests, `RequestDirectMove`, `Launch`, `SetActorLocation` (except the game mode's spawn), `Velocity =`. The only external impulse a bot ever receives is `AddKnockback(Server)` from damage and `Overlap` from pads, like a player. `AVeloxBotController` holds no movement state; `UVeloxMovementComponent` reads nothing bot-specific.
- Possession lifecycle: `OnPossess` seeds the brain (`FRandomStream(MasterSeed ^ BotIndex ^ LifeCount)`), resets aim to the spawn yaw, clears path/goal/enemy memory; `OnUnPossess` (death: B8 next-tick UnPossess) stops path following and clears the state. Respawn is the existing `bAutoRespawnAIControllers` path after `MinRespawnDelay` (B28) through `ChoosePlayerStart` (bots have no fixed respawn).

Why input and not a direct velocity API: the question in the task brief. A "bot velocity" entry point would bypass `CalcVelocity` (friction, the Q3 accelerate clamp, grace), the landing-jump rule and the pad/knockback chain — i.e. a second movement model that drifts from the player's at every tuning change; it would also need its own hitbox-history semantics. Input injection costs nothing (the dummy already does it) and makes every M1 soak script a valid bot "recording".

### 2. Decision architecture: a small utility brain in C++, world-free cores, no BT/StateTree/EQS/AIPerception

- `AVeloxBotController::Tick` runs four phases, each a thin wrapper over a world-free function in `Bots/`: **Perceive** (§6, 10 Hz per bot, staggered) → **Decide** (§7, goal re-evaluation at `GoalReevaluateSeconds` or on events) → **Navigate** (§5, every tick: path following + maneuver + combat overlay → `WishDirWorld/WishScale/bJumpHeld`) → **Act** (§8/§9/§10, every tick: aim model → `View`, weapon choice → `SelectSlot`, fire rule → `bFireHeld`) → `ApplyInput`. State lives in one struct `FVeloxBotState` on the controller (goal, path handle, maneuver, enemy memory, aim model state, timers) — readable by the debug line (§14) and resettable in one place.
- `EVeloxBotGoal { None, Item, Fight, Roam }` with `FVeloxBotGoal { Type; TWeakObjectPtr<AVeloxPickup> Item; TWeakObjectPtr<APawn> Enemy; FVector Point; float Score; double SetTime; }`. The goal chooser is `VeloxBotDecision::ChooseGoal(const FVeloxBotDecisionInput&, const FVeloxBotDifficultyParams&, FRandomStream&) → FVeloxBotGoal` (`Bots/VeloxBotDecision.h`, pure): inputs are the scored item candidates (§7), the best visible enemy (§6), own health/armor/weapon state, the match phase, the current goal (for hysteresis). Rules: `PostMatch` → `None`; an enemy visible → `Fight` unless the best item's score exceeds `FightItemBias × ` the fight score (health need pulls a hurt bot to health while it keeps shooting: Q3's "retreat to item"); no enemy → best `Item` whose score > 0, else `Roam` (a random reachable nav point within `RoamRadiusCm`, or in Duel the spawn of the next major item to come up — camping, §7). Hysteresis: a new `Item` goal replaces the current one only when `NewScore > CurrentScore × GoalSwitchHysteresis` or the current item was taken/became unreachable (`OnPickupTaken` for the goal item triggers immediate re-evaluation).
- Why not Behaviour Trees / StateTree / EQS / AIPerception: all four are asset-authored and editor-debugged — unusable on the headless host (Context) and overkill for four goals and a handful of continuous rules. *(Lyra, from memory)* Lyra's `ALyraBotController` drives a BT asset with Blackboard keys and the engine `UAIPerceptionComponent`; rejected for the same reason. Nothing prevents a later M7 StateTree skin on the Mac over the same pure functions, but it is not planned. `AIModule` stays a dependency only for `AAIController`, `UPathFollowingComponent` and `ANavLinkProxy`.

### 3. Navigation data: Recast nav mesh generated at runtime on the server, whole world navigable, one agent

- `Config/DefaultEngine.ini` (dev verifies the key names against the 5.8 `BaseEngine.ini` and `RecastNavMesh.h`; the per-resolution struct is the live one, the flat `CellSize`/`CellHeight`/`AgentMaxStepHeight` are deprecated):
  ```ini
  [/Script/NavigationSystem.NavigationSystemV1]
  bAutoCreateNavigationData=True
  bWholeWorldNavigable=True           ; greybox maps have no NavMeshBoundsVolume (Python cannot author brush volumes); M5 maps may add volumes and flip this per map
  bAllowClientSideNavigation=False    ; nav data is never loaded or built on clients
  bInitialBuildingLocked=False
  -SupportedAgents=ClearArray
  +SupportedAgents=(Name="VeloxPawn",Color=(R=0,G=255,B=0,A=255),DefaultQueryExtent=(X=100,Y=100,Z=200),NavDataClass=/Script/NavigationSystem.RecastNavMesh,AgentRadius=37.5,AgentHeight=140,AgentStepHeight=45,NavWalkingSearchHeightScale=0.5)
  [/Script/NavigationSystem.RecastNavMesh]
  RuntimeGeneration=Dynamic
  AgentRadius=37.5
  AgentHeight=140
  AgentMaxSlope=45.5
  TileSizeUU=1000
  NavMeshResolutionParams=((CellSize=19,CellHeight=10,AgentMaxStepHeight=45),(CellSize=19,CellHeight=10,AgentMaxStepHeight=45),(CellSize=19,CellHeight=10,AgentMaxStepHeight=45))
  bDrawPolyEdges=False
  ```
  Agent geometry = the pawn's class defaults (ADR 0003 §6 (c): capsule 37.5 × 70 half height, `MaxStepHeight 45`, `WalkableFloorAngle 45.5°`). Cell size 19 cm (≈ half the capsule radius, the Recast rule of thumb) keeps 50 cm-wide ledges walkable; the 60 cm "must block" stair riser of `L_MovementTest` is correctly unnavigable at step height 45.
- **Why runtime `Dynamic` and not a baked mesh:** nothing on the host can open the editor, and the greybox maps are regenerated by Python scripts (`Tools/editor/create_*_map.py`) on every layout change — a baked `RecastNavMesh` actor would be stale or missing. With `Dynamic`, `UNavigationSystemV1` builds the mesh asynchronously when the server world starts (≈ 100–500 ms for a 60 × 40 m greybox at cell 19 on this VM; measured in task 01) and rebuilds affected tiles when nav-relevant actors move (none do). Clients build nothing (`bAllowClientSideNavigation=False`), so PIE clients and packaged clients pay zero. Bots wait for `UNavigationSystemV1::IsNavigationBeingBuilt(World) == false` (and `OnNavigationGenerationFinishedDelegate`) before their first path query; until then they stand (log `VeloxNav building…` once). M5's real map, authored on the Mac, may add a `NavMeshBoundsVolume` and bake (`RuntimeGeneration=Static` per map override) — the bot code does not care. Recorded alternative for a headless bake, not chosen: a `UVeloxBuildNavCommandlet` (`WITH_EDITOR`) calling the synchronous `UNavigationSystemV1::Build()` then saving the map — it needs the editor-world nav bounds problem solved first.
- **What exports to the mesh:** greybox cubes (`/Engine/BasicShapes` with simple collision, Block Pawn) do; marker/target/pad meshes (`NoCollision`) do not; `AVeloxJumpPad::Trigger` and `AVeloxPickup::Trigger` are overlap-only and therefore already irrelevant by the engine rule (verified), but both constructors additionally call `SetCanEverAffectNavigation(false)` so a later collision change cannot carve holes. Pickups and pads sit on the mesh; a bot walks through them like a player.
- Nav walking mode is not used (`NavAgentProps.bCanWalk` default; `MOVE_NavWalking` never set — the Velox CMC's `CalcVelocity` handles `NavWalking` like `Walking` but there is no reason to leave real collision).

### 4. Nav links: `AVeloxNavLink` for jump pads, drops, gap jumps and rocket jumps; cost by area, eligibility by filter, traversal by the bot's own maneuver

- `AVeloxNavLink : ANavLinkProxy` (`Bots/VeloxNavLink.*`), map-placed by the map scripts, not replicated (server-only actors would still load on clients: `bNetLoadOnClient = false`), `bSmartLinkIsRelevant = false` (simple point links only; the smart-link pause/resume machinery is not used — the Velox follower detects link segments itself, below). Properties: `EVeloxNavLinkType Type { JumpPad, Drop, Jump, JumpFast, RocketJump }`, `TObjectPtr<AVeloxJumpPad> JumpPad` (JumpPad), `float RequiredSpeedCmS` (Jump/JumpFast: informational, checked by the map script), `float RocketJumpPitchDeg = 80` (RocketJump: look-down pitch, so the rocket lands just behind the feet and pushes forward), `float RunUpSeconds = 0.3` (RocketJump), `int32 MinHealthForRocketJump = 70` (self-damage ≈ 33 after halving before armor), `bool bEnabled = true`. `PostInitializeComponents` writes `PointLinks[0]`: `Left` = start (actor-relative), `Right` = end, `Direction = LeftToRight` (`BothWays` only for `Jump`/`JumpFast` gaps that are symmetric — authored per link), `SnapRadius = 60`, `bUseSnapHeight/SnapHeight = 100` (platform tops are ≥ 300 cm apart; snapping must not grab the floor below), `SetAreaClass(UVeloxNavArea_<Type>)`, `SupportedAgents` all. Everything is `EditAnywhere` so the Python scripts set it (`unreal.VeloxNavLink`, struct kwargs per the `Tools/editor/README.md` lessons).
- **Areas and costs** (`Bots/VeloxNavAreas.h`, C++ `UNavArea` subclasses, registered automatically by the nav system): `UVeloxNavArea_JumpPad` (DefaultCost 1.0, entering 0 — pads are the fastest route), `_Drop` (1.0 / 0), `_Jump` (1.0 / 50 — a 500 cm hop any bot clears at `MaxGroundSpeed`: jump range `0.675 s × 800 = 540 cm`, ADR 0002 §7), `_JumpFast` (1.0 / 100 — needs ≥ 1100 cm/s, i.e. strafe speed: the 700 cm gap), `_RocketJump` (1.0 / 400 — Q3 bots rocket-jump only when the detour is large; costs health and a rocket). A disabled link (`bEnabled = false`) sets `UNavArea_Null` and calls `UNavigationSystemV1::UpdateActorInNavOctree` — used by tests; Dynamic generation relinks the tile.
- **Eligibility by query filter** (`Bots/VeloxNavFilters.h`, C++ `UNavigationQueryFilter` subclasses with `Areas` set in the constructor): `UVeloxNavFilter_Walk` excludes `_JumpFast` and `_RocketJump` (presets without strafe-jumping or rocket jumps); `UVeloxNavFilter_Hop` excludes `_RocketJump`; `UVeloxNavFilter_Full` excludes nothing. `AVeloxBotController::GetNavFilter()` picks per tick from the preset **and the bot's state**: `_Full` only when `bRocketJumps && OwnsRocketLauncher && Rockets ≥ 1 && Health ≥ MinHealthForRocketJump(max over links)`, else `_Hop` or `_Walk`. The path is re-queried when the eligible filter changes (the health drop under the threshold invalidates a rocket-jump route).
- **Placement** is authored in the map scripts (`create_item_test_map.py`, `create_movement_test_map.py`), not auto-generated (Q3's AAS reachability computation is weeks of work; Recast's experimental generated jump-down links are not used): pad links from every `AVeloxJumpPad` (start = pad trigger centre at floor height, end = the landing point, §4 below), drop links at every platform edge toward the floor (start 60 cm inside the edge, end on the floor 150 cm out — the engine's `MaxFallDownLength` is irrelevant for point links; the maneuver is "walk off"), gap links across the three bunny-hop gaps of `L_MovementTest` (500 → `Jump`, 700 → `JumpFast`, 900 → none: 945 cm range at 1400 cm/s is beyond a bot's reliable speed), and one `RocketJump` link in `L_ItemTest` to a **new third platform** (350 cm high, no pad, carries `Ammo.Rockets` as the reason to go there; see §14). Landing point of a pad: `AVeloxJumpPad::ComputeLandingPoint(const UWorld*)` (new): samples the ballistic arc `P(t) = Origin + V0·t + ½·g·t²` (`VeloxMoveSim::BallisticPoint`, world-free) on the **descending** branch in 1/60 s steps with a line trace between samples on `ECC_Pawn`-blocking geometry (the `Weapon` channel is fine too — world only), returns the first hit; the map scripts call it through a `-ExecCmds="velox.bots.DumpPadLandings"` check or simply place the end at the platform centre they authored (the item location), which is what task 01 does; `GetLandingPoint`'s apex caveat (ADR 0002 A21) is thereby retired for bots.
- **Traversal** is a maneuver of the Velox follower (§5), never the engine's: when the current segment is a link segment (`FNavMeshNodeFlags(PathPoint.Flags).IsNavLink()` on the segment start point; the owning `AVeloxNavLink` is found through `UVeloxBotSubsystem::FindLinkByStart(Point, SnapRadius)` — Recast inserts the link's end points as path points, so the match is exact), the follower runs `FVeloxBotManeuver { Type; Start; End; Phase; StartTime }`:
  - `JumpPad`: walk to `Start` (the pad centre, acceptance 30 cm), no jump; once airborne (the pad's `AddKnockback` fired through the same overlap as for players) hold `WishDir` toward `End` at `WishScale 1` (air accelerate steers the landing like a player holding forward), no strafe-jump wish; the segment ends on landing (`IsOnGround`) within `LinkEndAcceptanceCm (150)` of `End`, else the path is re-queried (`VeloxBotLink type=JumpPad result=missed`).
  - `Drop`: walk through `Start` toward `End` at full speed; airborne: hold toward `End`; ends on landing.
  - `Jump`/`JumpFast`: hold `WishDir` toward `End` and **jump held from `Start − TakeoffLeadCm (100)`** (auto-hop takes off at the edge; `JumpFast` additionally requires the bot to arrive with speed ≥ `RequiredSpeedCmS`, which the strafe-jump approach (§5) provides — if `GetSpeed2D() < RequiredSpeedCmS × 0.9` at `Start` the bot does not jump, backs up `RunUpCm (600)` along the incoming segment and retries once, then re-queries with `_Walk`).
  - `RocketJump` (Q3 `BotRocketJump` shape): at `Start`, if the eligibility (§4) still holds: face `End` (yaw), hold forward for `RunUpSeconds`, then in one tick set pitch `−RocketJumpPitchDeg`, select RL if not current (the switch takes 0.45 s: the maneuver waits for `SwitchEndTime` before the run-up), press jump and fire in the **same tick** (Q3 order; the rocket flies ≈ 125 cm in 0.056 s, explodes under the rising pawn, splash ≈ 66 points → 825 cm/s + 675 jump ≈ 1500 cm/s upward = 5.6 m apex, plenty for 3.5 m); then hold toward `End` until landing. The self-splash is the server's own explosion path (`GE_Damage` self → `AddKnockback(Server)`), resolved at the explosion like any listen-host shot (C2). Abort if the explosion did not launch the pawn within 0.3 s (log `result=noimpulse`) → re-query with `_Hop`.
  Every maneuver logs `VeloxBotLink bot= type= from= to= result=ok|missed|aborted dt=` (Log, `LogVeloxBots`), which the functional tests and the soak parse.

### 5. Steering: the Velox path follower drives the CMC with strafe-jumping and bunny-hopping

- `UVeloxBotPathFollowingComponent : UPathFollowingComponent` (`Bots/VeloxBotPathFollowingComponent.*`), set as the controller's path-following component class (`AAIController` constructor `ObjectInitializer.SetDefaultSubobjectClass`). Paths come from `AAIController::MoveTo(FAIMoveRequest)` with the filter of §4, `bUsePathfinding`, `AcceptanceRadius 60`, `bAllowPartialPath`; **`FollowPathSegment(float Dt)` is overridden and does not call `Super`** (the engine version would call `RequestPathMove` with its own direction and never jump): it computes the segment direction and remaining length from `GetCurrentTargetLocation()`, the next corner angle from the path points, runs the maneuver when a link segment is active (§4), otherwise `VeloxBotSteering::Steer(...)`, and writes `WishDirWorld/WishScale/bJumpHeld` into the controller's pending `FVeloxBotInput` — it never touches the movement component directly. `SetMoveSegment` (calls `Super`, then detects link segments), `UpdatePathSegment` (engine), `HasReachedCurrentTarget` (engine, with the 2-D distance for corners), `OnPathFinished` (engine, then the controller is notified to pick the next goal). Path invalidation on nav rebuild and partial paths are the engine's.
- `VeloxBotSteering` (`Bots/VeloxBotSteering.h`, `CoreMinimal.h` only, unit-tested): 
  ```cpp
  struct FVeloxSteerInput { FVector2D Velocity; bool bOnGround; FVector2D ToTarget; float SegmentRemainingCm; float NextCornerDeg; float WishSpeed; float AirAccel; float FixedStep; };
  struct FVeloxSteerParams { bool bBunnyHop; bool bStrafeJump; float MinHopDistanceCm = 400; float MaxHopCornerDeg = 35; float StrafeMaxAngleDeg = 60; float ArriveSlowdownCm = 150; };
  struct FVeloxSteerOutput { FVector2D WishDir; float WishScale; bool bJumpHeld; };
  FVeloxSteerOutput Steer(const FVeloxSteerInput&, const FVeloxSteerParams&);
  float OptimalStrafeAngleDeg(float Speed, float WishSpeed, float AirAccel, float Dt);   // acos((W - a·dt·W)/|V|), 0 when |V| ≤ W − a·dt·W
  ```
  Rules (vanilla Q3 physics, ADR 0002 §1): **ground**: `WishDir = ToTarget`, `WishScale = 1` (`ArriveSlowdownCm`: scale down linearly near the final target so the bot stops on items instead of overshooting them), `bJumpHeld = bBunnyHop && SegmentRemaining > MinHopDistanceCm && NextCornerDeg < MaxHopCornerDeg` (a bot holding jump auto-hops on every landing with zero friction — ADR 0002 `ProcessLanded`; releasing it before a sharp corner lets ground friction and ground acceleration turn it, Q3 bots do the same by simply not jumping). **Air**: if `bStrafeJump` and `|V| > WishSpeed − a_step`, `WishDir = rotate(V̂, ±θ)` with `θ = OptimalStrafeAngleDeg(|V|, W, AirAccel, FixedStep)` — the dot-product clamp's optimum, ≈ 37° at 1000 cm/s with the M1 defaults — and the sign toward `ToTarget`; when the heading error `angle(V, ToTarget)` exceeds `θ`, the wish is rotated by `min(StrafeMaxAngleDeg, error)` instead (maximum turning rate; speed is not gained but not lost either: air has no friction); without strafe-jumping `WishDir = ToTarget` (vanilla air accelerate then only corrects the heading, no gain — the "walker" presets). The bot holds the jump through the air so the landing re-jumps.
  Unit tests (`Velox.Bots.StrafeSteering`): 125 ticks of `VeloxMoveSim::StepFrame` with `Steer` closing the loop from (800, 0) toward +X → speed ≥ `1.25 × MaxGroundSpeed` and `|heading error| ≤ 10°` at the end (the ADR 0002 §7 bound, now reached by the controller rule, not a scripted angle); goal 90° off at 1000 cm/s → velocity within 15° of the goal after ≤ 60 ticks and never below 950 cm/s; walker preset → speed stays ≤ `MaxGroundSpeed + 1`; corner rule → `bJumpHeld` false when `NextCornerDeg = 60`.
- **Combat overlay** (§10) modifies the steering output before it is applied: strafing perpendicular to the enemy while still following the path direction, and dodge impulses. The overlay is additive on `WishDir` (renormalised), so the pathing never breaks.
- Stuck detection: `StuckSeconds` of `GetSpeed2D() < 50` while a path is active → re-query; three strikes → `Roam` to a random point (log `VeloxBotStuck`). Q3 bots have the same escape hatch.

### 6. Perception: FOV + world-only LOS, damage events, short memory; no `UAIPerceptionComponent`

- `FVeloxBotEnemyInfo { TWeakObjectPtr<AVeloxCharacter> Pawn; double LastSeenTime; FVector LastSeenLocation, LastSeenVelocity; bool bVisible; }` per living enemy, updated every `PerceptionIntervalSeconds (0.1)` per bot, staggered across bots by `BotIndex` so 16 bots spread 16 updates over 10 ticks. Candidates = the lag-comp subsystem's registered pawns (server-side list of living `UVeloxHitboxComponent`s — exactly the pawns that can be hit; corpses unregister), minus self, minus spectators; team filtering is M7's hook.
- Visible iff (a) the angle between the view forward and `(TargetCentre − Eye)` ≤ `PerceptionFovDeg / 2` (preset: 120° Easy … 180° Expert — Q3 bots see ≈ 90–120°), and (b) a line trace Eye → capsule centre **or** Eye → head point on `Velox_TraceChannel_Weapon` is clear — world only, pawn capsules ignore that channel (ADR 0003 §6), so other players never block sight; two traces per candidate per 0.1 s. Range cap `PerceptionRangeCm` (preset, 4000–20480).
- **Hearing is damage:** `UVeloxHealthComponent::OnDamaged` (`FVeloxDamageEvent::Instigator`) marks the instigator's info as "heard" (`LastSeenLocation` = instigator location, `bVisible` false, reaction timer armed) so the bot turns toward its attacker after `ReactionSeconds` even without LOS (Q3 `BotCheckAttack` on `enemy from damage`). Global pickup sounds and footsteps are not modelled (deferred).
- Target: the nearest visible enemy, sticky while visible (switch only to one at < `1/TargetStickiness` of the current distance); after `EnemyMemorySeconds (3)` without sight the target is dropped and the last seen location becomes a `Roam` hint.

### 7. Item routing: Q3-style value / travel time with respawn timing, through `UVeloxItemRegistrySubsystem`

- `VeloxItemValue` (`Bots/VeloxItemValue.h`, pure, unit-tested — the ADR 0001 §4 "item-value scoring" test):
  ```cpp
  struct FVeloxItemScoringInput { EVeloxItemType Type; int32 Quantity; float BotBaseValue; bool bMajorItem; EVeloxHealthCap HealthCap;
      int32 Health, MaxHealth, HealthHardCap, Armor, MaxArmor; int32 Ammo, AmmoMax; bool bOwnsWeapon; bool bOwnsWeaponUsingAmmo;
      bool bAvailable; float TimeUntilRespawn; float TravelSeconds; };
  struct FVeloxItemScoringParams { float ItemTimingSkill; float MaxWaitSeconds; float TravelOffsetSeconds = 1.0f; };
  float Need(const FVeloxItemScoringInput&);         // 0..1
  float Score(const FVeloxItemScoringInput&, const FVeloxItemScoringParams&);   // 0 = not worth going
  ```
  `Need`: health `(Cap − Health)/Cap` with `Cap` = `MaxHealth` or `HealthHardCap` per the definition (Mega: hard cap, so a 100-health bot still wants it: need 0.5); armor `(MaxArmor − Armor)/MaxArmor`; ammo `(AmmoMax − Ammo)/AmmoMax`, × 0.1 when no owned weapon uses it; weapon `1` when not owned, else `0.3 × ` the ammo need of its type (weapon-stay is off in FFA/Duel, the pickup gives ammo); powerup `1`. `Value = BotBaseValue × Need` (the Q3 tier weights already in the item assets: Mega 100, RA 90, YA 70, powerups 110, large health 40, weapons 30–60, ammo 10, shards/small health 5). Timing: `Wait = bAvailable ? 0 : max(0, TimeUntilRespawn − TravelSeconds)`; `Wait > MaxWaitSeconds × ItemTimingSkill → Score = 0` (skill 0 ignores every unavailable item; skill 1 with `MaxWaitSeconds 8` sends a duel bot to Mega/RA up to 8 s early and lets it wait there — the ROADMAP's "duel bots time Mega/RA"); `Score = Value / (TravelSeconds + Wait + TravelOffsetSeconds)` (Q3 divides the fuzzy weight by travel time; the offset keeps an item under the bot's feet finite).
- **Candidates and travel time.** `GetPickups()` from the registry (ADR 0004 §9 API only: `GetDefinition`, `IsAvailable`, `GetTimeUntilRespawn`, `GetLastTakenBy`, delegates). Pre-score every pickup with straight-line distance / `EstimatedTravelSpeed` (preset), keep the best `PathQueryCandidates (4)`, query `UNavigationSystemV1::FindPathSync` for those (path length incl. link entering costs → `TravelSeconds = Length / EstimatedTravelSpeed`), score, choose with the §2 hysteresis. Cadence `GoalReevaluateSeconds (1.0)`, staggered; immediate re-evaluation when the goal item is taken (`OnPickupTaken`) or the goal is reached. Unreachable (partial path) → score 0.
- Duel timing beyond the score: when no goal scores > 0 and the mode is Duel, `Roam` targets the major item with the smallest `TimeUntilRespawn − TravelSeconds` (camping the next Mega/RA), standing `CampOffsetCm (200)` from it; the bot takes it the moment it respawns through the ordinary overlap (`AVeloxPickup` re-checks standing pawns on respawn, ADR 0004 §2). `OnPickupTaken` by an enemy on a major item resets that item's attractiveness for its respawn cycle automatically through `TimeUntilRespawn`.
- The bot never reads a pickup's state through any path the HUD does not use; nothing in `Items/` changes except `AVeloxPickup::Trigger->SetCanEverAffectNavigation(false)` (§3).

### 8. Aim model: reaction time, smooth correlated error, rate-limited tracking, projectile lead; no rewind for bots

- `FVeloxAimModel` (`Bots/VeloxAimModel.h`, pure, unit-tested — the ADR 0001 §4 "aim-error distribution" test):
  ```cpp
  struct FVeloxAimParams { float ReactionSeconds; float ReactionJitter = 0.3f; float AimErrorDeg; float ErrorCorrelationSeconds = 0.3f;
      float TrackingSmoothingSeconds; float MaxTurnRateDegPerSec; bool bLeadProjectiles; float LeadScale = 1.0f; };
  struct FVeloxAimState { FRotator Aim; FVector2D ErrorDeg; float ReactionLeft; bool bHadTarget; };
  struct FVeloxAimInput { bool bHasTarget; FVector Eye, TargetCentre, TargetVelocity; float ProjectileSpeed /* 0 = hitscan */; FRotator IdleAim; };
  FRotator Update(FVeloxAimState&, const FVeloxAimInput&, const FVeloxAimParams&, float Dt, FRandomStream&);
  FVector LeadPoint(const FVector& Eye, const FVector& Target, const FVector& TargetVel, float ProjectileSpeed, float LeadScale); // 2 fixed-point iterations
  ```
  Rules: a target appearing (no target → target, or a new target) arms `ReactionLeft = ReactionSeconds × (1 ± ReactionJitter·U)`; while `ReactionLeft > 0` the aim keeps turning toward the previous desired rotation (no new information); then `Desired = (LeadPoint − Eye).Rotation() + ErrorDeg` where `ErrorDeg` (yaw, pitch) is an **Ornstein–Uhlenbeck process** per axis — `E += −E/τ·Dt + σ·sqrt(2·Dt/τ)·N(0,1)` with `σ = AimErrorDeg`, `τ = ErrorCorrelationSeconds` — i.e. the error wanders smoothly around the target with stationary standard deviation `σ` (Q3 draws a fresh random point in a cone every think frame, which jitters at 60 Hz; the OU process gives the "almost on, drifting" look of a human and makes the LG beam wobble rather than vibrate); the aim rotates toward `Desired` by `Δ × (1 − exp(−Dt / TrackingSmoothingSeconds))`, clamped to `MaxTurnRateDegPerSec × Dt` (fast flicks are rate-limited: a 180° turn takes 0.17–0.5 s by preset); without a target `Desired = IdleAim` (path direction, pitch 0, or the last seen enemy location while remembered). Lead: `bLeadProjectiles` → `LeadPoint` with the target's server velocity and the weapon's `ProjectileSpeed` (`LeadScale < 1` under-leads on easy presets); hitscan → no lead. All angles in degrees, `FRandomStream` injected.
  Tests: `Velox.Bots.AimError` — 20 000 steps at 1/60 s with a static target: the sampled standard deviation of each error axis within 10 % of `σ`, the mean within `0.05 σ` (no bias), the lag-1 autocorrelation within ±0.05 of `exp(−Dt/τ)` (it is correlated noise, not white), and the first aim change after a target appears occurs no earlier than `ReactionSeconds × 0.7` and no later than `× 1.3`; `Velox.Bots.AimLead` — target at 1000 cm moving 600 cm/s perpendicular, rocket 2250 cm/s: `FVeloxProjectileSim` flight from the lead direction passes within 10 cm of the target's position at impact time; `Velox.Bots.AimTurnRate` — a 180° target jump is reached in `180 / MaxTurnRate ± one tick`.
- **Fire rule** `VeloxBotCombat::ShouldFire(const FVeloxFireInput&, const FVeloxBotDifficultyParams&)` (pure): the current weapon has ammo, the target is visible, `angle(AimDir, ToTargetCentre) ≤ FireConeDeg` (preset: 12° Easy … 3° Expert) or, for splash weapons, the aim ray's world hit lies within `SplashRadius × 0.8` of the target ("ground rockets"), the range is inside the weapon band (§9), and **no self-splash danger**: for RL/PG the world hit along the aim ray must be farther than `SplashRadius + 50` (a wall in the face) and the target farther than `SplashRadius + 50`. Fire is held while true (automatic weapons), released otherwise; spawn protection ends on the first shot like for players.
- **Lag compensation interplay (stated, no code):** the bot aims at the *current* server pose and fires with `ViewServerTime = Now`, so `TraceShot` resolves `T = Now` → "newer than the latest sample → current pose" (ADR 0003 §6): zero rewind, no hint, `rewind_ms = 0` in the `VeloxShot` log. Bots are *victims* of rewound shots like any pawn (their history is recorded with world-time stamps, B12). The bot has no interpolation delay and no ping; its "humanity" is entirely the aim model's reaction time and error. Nothing in `UVeloxLagCompensationSubsystem` changes.

### 9. Weapon choice: data-driven range bands, ammo, switch hysteresis

- `VeloxWeaponChoice::Pick(const FVeloxWeaponChoiceInput&, const TArray<FVeloxBotWeaponPreference>&) → int32 TableIndex` (`Bots/VeloxWeaponChoice.h`, pure, tested): per owned weapon with ammo ≥ `AmmoPerShot`, `score = Weight × Band(Range)` where the band is `1` inside `[BestMin, BestMax]`, linear to `0.3` at `MinRange`/`MaxRange`, `0` outside; RL/PG score `0` when `Range < SplashRadius + 100`; the current weapon keeps its score × `SwitchHysteresis (1.25)` (a switch costs 0.45 s); without a target the bot pre-selects the best weapon for `PreferredRange` (preset) — Q3 bots do the same (`BotChooseWeapon` on a timer). Preferences live in the difficulty asset (§11) as `TArray<FVeloxBotWeaponPreference { FGameplayTag Weapon; float Weight; float MinRange, BestMin, BestMax, MaxRange; }>` with these defaults (cm; Q3 `fw_weights`-shaped, LG capped by its 1920 cm range): Gauntlet 0–0–100–120 weight 10; MG 0–0–20480–20480 weight 20 (fallback); SG 0–0–500–1000 weight 60; PG 150–300–1500–2500 weight 50; RL 150–300–1500–3000 weight 90; LG 0–200–1500–1900 weight 85; RG 400–1200–20480–20480 weight 100 (Easy presets scale RG/LG weights down: they are the aim-dependent weapons).
- Test `Velox.Bots.WeaponChoice`: RG at 2500 cm beats RL; LG at 500 cm with ammo beats RG; RL excluded at 150 cm; no ammo → next best; hysteresis keeps RL at a score ratio 1.2.

### 10. Dodging and strafing under fire; rocket dodge

- While `Fight` (or any goal with a visible enemy), the combat overlay adds to the steering wish: a lateral component `± Perp(ToEnemy) × StrafeAmplitude (0.7)` whose sign flips every `StrafeFlipSeconds` drawn uniformly from the preset range (0.4–1.2 s; Q3 `BotChangeViewAngles`-timed strafing), a random jump with probability `DodgeJumpChancePerSec` (Q3 bots jump while fighting; it also starts bunny-hops), and **range keeping**: wish toward the enemy when `Range > BestMax` of the current weapon, away when `< BestMin`, so a rail bot backs off and an LG bot closes in. The overlay is renormalised with the path direction (weight `FightPathWeight 0.5` when an item goal is active, else the fight has no path and the overlay is the whole wish, bounded by a `FightLeashCm` radius around the enemy's last seen point with a nav raycast so the bot does not strafe into pits — `UNavigationSystemV1::NavigationRaycast` once per flip).
- **Projectile dodge** (`bDodgeProjectiles`, Hard+): `UVeloxBotSubsystem` keeps the authority list of live `AVeloxProjectile`s (registered in `BeginPlay`/`EndPlay` on the server — 20 at most); every perception tick the bot checks projectiles not its own whose line `Start + V·t` passes within `SplashRadius + 100` of its capsule within `t ≤ 1.0 s`; after `ProjectileDodgeReactionSeconds` it overrides the lateral component perpendicular to the projectile's velocity (away from the closest approach) and jumps (Q3 `BotAvoidRocket`-shaped). Hitscan cannot be dodged by definition; the strafing above is the counter.
- Under fire without sight (§6 hearing): turn toward the attacker and strafe; no path change.

### 13. Performance budget (60 Hz server, VM figures)

- Target **≤ 150 µs mean, ≤ 600 µs peak of controller time per bot per server tick** on this VM (16 bots ≈ 2.4 ms ≈ 15 % of the frame; the movement/replication cost of the pawn is the player's and already budgeted). Composition: aim + steering + input apply every tick (≈ 20 µs, pure math), perception every 0.1 s (≤ 15 candidates × 2 traces ≈ 60 µs, amortised 6 µs), goal re-evaluation every 1 s (≤ 4 `FindPathSync` ≈ 4 × 50–150 µs on a 60 × 40 m mesh, amortised ≤ 10 µs; staggered so no frame runs more than one bot's evaluation), projectile dodge check every 0.1 s (≤ 20 projectiles, trivial). Nav mesh memory for the greybox maps < 2 MB; the Dynamic build at map start ≤ 1 s, once.
- Instrumentation: `DECLARE_CYCLE_STAT` group `STATGROUP_VeloxBots` (`Think`, `Perceive`, `Path`, `Steer`, `Apply`); the subsystem logs `VeloxBotBudget bots=N mean_us= max_us= paths=/s traces=/s` every 5 s when bots exist (Log, `LogVeloxBots`), and warns once per bot-tick above `BudgetWarnMicroseconds`. The soak (§14) asserts the mean.

## Consequences

- Bots are players without a network connection: every movement, combat, item and match rule applies to them unchanged, and every future tuning change reaches them for free. The price is that bot "skill" is bounded by what input can do — which is the Quake definition of a bot.
- The nav mesh is built on the server at map load from the collision the greybox already has; no editor step, no baked actor to keep in sync. Real maps (M5) can bake; the bot code is indifferent. Links are authored in the map scripts — a mapping convention from M4 on (every platform edge gets a drop link, every pad a pad link).
- All decision rules are pure functions with unit tests and injected randomness; the controller is glue. A `dev-hard` agent can tune feel by editing `DA_Bot_*` values and re-running the functional tests headless; the human tunes on the Mac with `velox.bots.Debug`.
- The aim model's OU error and rate-limited tracking produce human-looking misses at every difficulty; the Expert preset still never rewinds and never sees through walls.
- Cost is bounded by cadence (perception 10 Hz, paths ≤ 4/s per bot) rather than by heuristics in hot code; 16 bots fit in ≈ 15 % of a server frame.
- `AIModule`/`NavigationSystem` are used for `AAIController`, `UPathFollowingComponent`, Recast and `ANavLinkProxy` only; BT/StateTree/EQS/Perception stay unused and cannot drift the project toward editor-only workflows.

## Alternatives considered

- **Direct velocity API for bots** (`SetBotVelocity`, or `RequestDirectMove`): a second movement model; rejected (§1).
- **Engine path following as-is (`MoveTo` + `RequestPathMove`):** walks correctly on our CMC (ADR 0002 §8) but never jumps, cannot strafe-jump and treats links as walkable segments; kept as the base class for its path bookkeeping, overridden in `FollowPathSegment` (§5).
- **Smart links (`UNavLinkCustomComponent` pause/resume):** designed for door/ladder-style scripted traversal with the engine follower; our follower handles link segments itself, so the extra state machine buys nothing. Simple point links with area classes carry the costs.
- **Baked nav mesh via a headless commandlet:** possible (`UNavigationSystemV1::Build()` is synchronous) but needs nav bounds the Python map scripts cannot author (brush volumes) and a save step per map regeneration; runtime `Dynamic` generation with `bWholeWorldNavigable` costs ≤ 1 s at server start and nothing on clients. Revisit for M5/M6 shipping maps.
- **Recast's experimental generated jump-down links:** experimental in 5.8 and only for drops; authored links are explicit and testable.
- **Behaviour Tree / StateTree / EQS / AIPerception** (Lyra's stack): editor-authored assets, not authorable or debuggable on this host; the utility rules are a few hundred lines of tested C++ (§2).
- **Q3-style AAS with precomputed reachability and travel times:** the gold standard for item routing speed, weeks of work; `FindPathSync` for the top-4 candidates at 1 Hz is within budget (§13).
- **Per-think random aim cone (Q3):** jitters at 60 Hz; the OU process gives correlated, smooth error with the same stationary distribution (§8).
- **Bots with artificial latency / rewound shots for fairness:** a bot that fires at `Now` with reaction time ≥ 100 ms is already "slower" than a human at 100 ms ping; adding rewind would only make Expert bots cheat-like. Rejected.
- **A `Velox.State.Bot` tag or bot-specific movement settings:** nothing in simulation may know it drives a bot (non-negotiable 4); difficulty expresses itself only through input.

## Lyra: adopted vs rejected (this ADR)

Adopted *(Lyra, from memory)*: a server-side bot-creation component that spawns `AAIController`s with PlayerStates, assigns names from a list and a count from the game configuration (`ULyraBotCreationComponent` → `UVeloxBotSubsystem` + `?Bots=`); `bIsABot` on the PlayerState for the scoreboard; AI controllers possessing the same pawn class with the same ability sets through `PossessedBy`/`InitAbilityActorInfo` (ADR 0001). Rejected: `ALyraBotController`'s Behaviour Tree + Blackboard, `UAIPerceptionComponent` sight config, the team-agent hooks (M7), `ULyraBotCheats` (replaced by the `velox.bots.*` commands).
