M1-07: `Movement/VeloxMovementComponent.*` (`ControlledCharacterMove`, `MoveAutonomous`, `ServerMove_HandleMoveData`, `CallServerMovePacked`), `Movement/VeloxNetworkMoveData.*` (`ChooseExtraOldMove`, container fill and serialisation), `Tests/VeloxSavedMoveTest.cpp`, `Tests/VeloxMovementFunctionalTest.cpp`. Engine facts checked in UE 5.8 source: `CharacterMovementComponent.cpp` l.2190–2330 (`SimulateMovement`: proxies move their capsule by the replicated velocity every frame), l.8394–8450 (`SmoothClientPosition_Interpolate`: Linear mode lerps `MeshTranslationOffset` from `OriginalMeshTranslationOffset` to zero, nothing else), l.9928–10007 (`ServerMove_HandleMoveData`, `ServerMove_PerformMovement`: stale stamp → `LogNetPlayerMovement` **Log** line l.10005, Warning only beyond 1 s), l.9835 (`FCharacterNetworkMoveData::Serialize`: same fields for every move type); `GameStateBase.cpp` l.36 (`ServerWorldTimeSecondsUpdateFrequency = 0.1`), l.64–67 (looping timer), l.155–193 (`OnRep_ReplicatedWorldTimeSecondsDouble`: cumulative mean, reset after 250 samples, 0.5 blend); `Info.cpp` l.46 (`NetUpdateFrequency 10`); `NetDriver.cpp` l.5422–5425 (next update = now + `1/NetUpdateFrequency` + `FRand() × ServerTickTime`).

**Verdict: accept both designs. 08b: two Must-fix items (fire-rate tolerance, switch supersede) → task 08c (dev-hard, ~2.5 h); two Should-fix items (server-time estimate, fallback delay) → task 08d (dev, ~1.5 h). M1-07: ratified as ADR 0002 A35 with one Low item (repair instrumentation) → task M1-08 (dev, ~1 h).** D1 is the important result of 08b: the drawn pose of a simulated proxy was never the trajectory point at `SmoothingClientTimeStamp` (ADR 0003 §6, B13, B14 all assumed it), and the anchor-ring fix measures |dt| 0.2 ms median against the server history. The six items the dev raised are ruled below; the amendments are ADR 0003 B30–B34 and ADR 0002 A35.

## 1. Rulings

| # | Question | Ruling |
|---|---|---|
| 1 | B13/B14 premises (proxy drawn at `SmoothingClientTimeStamp`); B13 fallback delay 108 ms | **Premises wrong, corrected (B30).** `SimulateMovement` extrapolates the proxy capsule from the newest received pose every frame; Linear smoothing only decays the mesh offset left by the last correction. The drawn pose is therefore ≈ the newest received pose plus up to one update age of extrapolation, not a pose `NetworkSimulatedSmoothLocationTime` in the past. The anchor-ring `GetRenderedServerStamp` (nearest point of the received polyline + extrapolation segment, bounded below by SCT) is the right model and stays. The fallback is wrong by the same model: with no moving proxy there is nothing to rewind; the fallback becomes the last measured proxy delay if younger than 2 s, else `0.03` s (the measured mean update age), not 108 ms (08d). |
| 2 | D5 reflection-based staleness correction; exact fix in `AVeloxGameState`; projectile time reads | **Replace with the exact fix (B31, 08d).** Mechanism confirmed in the engine: the server stamps the replicated time on a 0.1 s timer, the GameState replicates every 100 ms + `FRand() × 16.7` ms, so the send-time staleness random-walks over [0, 100) ms and the client's cumulative mean converges to ≈ 50 ms behind — the measured 45–51 ms. `AVeloxGameState::PreReplication` writes `ReplicatedWorldTimeSecondsDouble = World->GetTimeSeconds()` (`PreReplication` runs only in the frame the actor is sent), which makes the staleness zero without reflection or a faster timer. `VeloxLagComp::EstimateServerTime(GameState)` stays as the single accessor (`GetServerWorldTimeSeconds()` after the fix; no half-period term) and the projectile proxy dead reckoning (`VeloxProjectile.cpp:598`) and the projectile ability (`FireProjectile.cpp:141`) use it — the proxy rocket then sits on the same server-time slice as the pawn proxies instead of ≈ 112 cm behind them. `ExpectedServerTimeStaleness` and its test are deleted. |
| 3 | D3 cheat surface (6 MG / 11 LG after idle, LG ≈ 88 dmg in one frame); `FireRateSpacingTolerance 0.25` < resend spread | **Surface accepted as inherent; the spacing tolerance is a Must-fix (B32, 08c).** Any rule that admits an honest reliable-resend burst (RTT + 80 ms of shots arriving in one frame) admits the same burst from a modified client that withholds shots — the two are indistinguishable on the wire; Q3 accepts usercmds up to 1000 ms old (`ClientThink_real`: `cmd->serverTime < level.time − 1000` is clamped, not dropped), i.e. a 1 s burst. 0.5 s is half that and bounds the long-term rate exactly. The spacing rule, however, rejects honest rails: at the 250 ms RTT limit one lost packet compresses two rails 1.5 s apart to ≈ 1.17 s on receipt, below `MinSpacing 1.25` — one rejected rail per ≈ 50 at 2 % loss for a player at the ping limit. Fix: one tolerance. `CapacityFor = 1 + FireRateJitterToleranceSeconds / Interval` (no `FireRateBurstAllowance` floor), spacing deleted — a GCRA with tolerance `T` already enforces a minimum spacing of `Interval − T` after a full bucket, so B19's spacing rule was only ever a patch for the floor of 3. Rail capacity 1.33: two rails 1.0 s apart once, then 1.5 s average; SG 1.5, RL 1.625; MG 6, LG 11 unchanged. `FireRateBurstAllowance` and `FireRateSpacingTolerance` are deleted (settings, cvars, bootstrap, docs). |
| 4 | D4: retrigger + early completion instead of only removing the GE | **Both mechanisms stay; the retrigger needs one more step (B33, 08c Must-fix).** `CompletePendingSwitch` on an accepted shot of the pending weapon is right. `bRetriggerInstancedAbility` is the only way a second switch can reach `ActivateAbility` on the server (GAS refuses an active instanced-per-actor ability otherwise) — but the engine's retrigger ends the superseded instance, which cancels its `WaitDelay`, so `OnDropFinished` → `SetCurrentIndex(Pending)` never runs for it: the server's current weapon stays the pre-switch one while the owner predicted the switched one. Consequence: a press back to that weapon within one latency after the client's drop end (RG → RL, change of mind, RL → RG) is rejected as `TargetIndex == CurrentIndex`, the server keeps a stale `PendingIndex`, and the owner shows the wrong weapon until `PredictionTimeout` (1 s). Fix: at the top of the authority branch of `ActivateAbility`, if a pending index exists and `GetSwitchRemaining(ASC) ≤ WeaponRaiseTime + SwitchTimingToleranceSeconds` (the drop end has passed within the B18 tolerance — the only state in which an honest client can have sent the press, since its own instance must have ended), complete the pending switch's inventory part (`SetCurrentIndex(Pending)`, remove `GE_WeaponSwitching`, **not** `CompletePendingSwitch()`: with `InstancedPerActor` the active instance is the new activation itself and `CompleteSwitchEarly` would end it); otherwise reject the activation (pre-08b behaviour, which a modified client earns by sending a switch during the drop). |
| 5 | B17 expected rewind ≈ 160 ms; measured 123–141 ms at 100 ms RTT | **B17's composition corrected (B34).** Rewind for a hinted shot = RTT + (update age − extrapolation progress) ≈ RTT + 20–40 ms — the smoothing lag term (100 ms) never existed (ruling 1). `[60, 250]` stays as the assertion window at 50 ms one-way; the reported median goes to STATUS as "123–141 ms at 100 ms RTT". |
| 6 | D2: FireRun judged at 100 ms RTT, `MaxRewindSeconds 0.25` | **Judged at 100 ms RTT: confirmed. `MaxRewindSeconds` 0.25 → 0.30 (B34, default only, human may veto).** The needed rewind is RTT + 20–40 ms, so 0.25 fully compensates RTT ≤ ≈ 210 ms; ADR 0003 §6 promised "a 250 ms-ping player hits what he sees" on the wrong model. 0.30 keeps the promise with ≈ 10–30 ms margin; cost is 50 ms more "shoot the past" (30 cm at 600 cm/s) and the same widening of B25's self-splash clamp — acceptable. Beyond the bound the clamp degrades gracefully (a 30 ms clamp is 18 cm at 600 cm/s, half a capsule). 08c adds a report-only `--lag 125` FireRun row that must show `hint=stamp` on ≥ n−1 rails once 0.30 is in — the proof of the promise. |
| 7 | M1-07: second old-move slot, take-off as event move | **Ratified as A35 (un-defers A32).** Root cause is exact (25 ms × 433 cm/s = 10.83 cm), the fix removes the class (two-RPC burst around a discrete event), the test reproduces pre/post. Details in §3. |
| 8 | M1-07: "losses during an unacked event are merged" trade-off | **Accepted, recorded in A35.** While an event move `E` is unacked (≈ 1 RTT) the slots carry `E` and `E−1`, not the previous move `P`; a lost RPC in that window merges `P` into the next move. Every Velox event (pad entry, held-jump landing, take-off, self-splash) is followed by air moves, where a merge is second order (`PhysFalling` trapezoid); on the ground A31 made the displacement second order too. The alternative pair `{E, P}` would *not* fix M1-07's own case (a two-RPC burst needs `E−1` in the third RPC), so the dev's choice is the right one. Revisit only on soak evidence of a > 2.5 cm non-echo stray inside the unacked window. |
| 9 | M1-07: duplicate rejection on the server; the `:962` comment; a Velox log line? | **Comment is right in substance, imprecise in reference; no Velox per-duplicate line (A35, M1-08).** Both the engine old move and the Velox extra slot go through `ServerMove_PerformMovement`, whose `VerifyClientTimeStamp` failure logs `ServerMove: TimeStamp expired` at `LogNetPlayerMovement` **Log** (l.10005; Warning only when > `net.NetServerMoveTimestampExpiredWarningThreshold` = 1 s). The VeryVerbose `ServerMoveOld:` line (l.9304) belongs to the legacy unpacked RPC path Velox does not use. A Velox line per rejected duplicate would be ≈ 2 lines per RPC per client — noise. What the soak needs is attribution of *accepted* repairs: `VeloxMoveRepaired` gains `slot=old|extra`, `nettest.sh` prints `repaired_extra=N`. The comment cites the engine function and verbosity. `docs/movement-tooling.md` "A32/A35" is correct as written. |

Local behaviour note, not a defect: `PrepareInputActivation` ignores a weapon press during the own drop (pre-08b). Q3 `PM_FinishWeaponChange` takes `cmd.weapon` at the drop end, i.e. a press during the drop retargets the switch. A feel question for task 09; recorded as an open question, no change in M2.

## 2. Defects, ranked (file:line → fix)

1. **Must-fix (08c) — honest rail/SG/RL shots rejected `reason=spacing` after one lost packet near the ping limit.** `Weapons/VeloxFireRateBucket.h:50` (`MinSpacingFor`, `Interval − 0.25`), `Combat/VeloxCombatSettings.h:175` (`FireRateSpacingTolerance 0.25`), `VeloxWeaponTests.cpp` (no rail-resend row). Measured resend compression is RTT + 80 ms (08 report), 330 ms at 250 ms RTT > 250 ms tolerance → rail pair 1.17 s < 1.25 s min spacing. Fix per ruling 3: capacity `1 + Tol/Interval`, spacing rule and both old tunables deleted; tests: rail at 250 ms RTT / 2 % resend for 600 s → 0 rejections; rail cheat at 1.0 s spacing → 2nd accepted, 3rd rejected, long-term 1/1.5 s; existing MG/LG rows unchanged (capacities 6/11).
2. **Must-fix (08c) — a superseded switch never completes its drop on the server; switch-back is rejected; stale pending index.** `Weapons/VeloxGameplayAbility_WeaponSwitch.cpp:82` (`TargetIndex == Inventory->GetCurrentIndex()` evaluated before the pending switch is resolved), `:124` (`OnDropFinished` is skipped for a retriggered instance — its `WaitDelay` task dies with `EndAbility`), `:95` (`SetPendingIndex` overwrites the stale one). Fix per ruling 4. Test rows (`Inventory` test): (a) MG→RG running, drop end passed on the client side (advance world time past Wait+Drop), server activation RG→MG → accepted, current MG, pending MG… i.e. the switch-back lands; (b) the same press with the drop still > `Raise + Tol` remaining → rejected, current unchanged, pending unchanged.
3. **Should-fix (08d) — server-time estimate by reflection and half-period guess; projectile readers uncorrected.** `Net/VeloxLagCompensationSubsystem.cpp:307–323` (`ExpectedServerTimeStaleness`, `FindFProperty` of a protected engine field), `Weapons/VeloxProjectile.cpp:598`, `Weapons/VeloxGameplayAbility_FireProjectile.cpp:141`, `GameModes/VeloxGameState.h:26` (no override). Fix per ruling 2; `Velox.Combat.RenderedStamp` unaffected; the D5 unit test is deleted with the function. Acceptance: FireRun `|rewind−view|` mean ≤ 30 ms still holds at `--lag 50` (the fallback and the stamp path must agree after the bias moves from 50 ms to ≈ 0).
4. **Should-fix (08d) — fallback interpolation delay 108 ms rests on the refuted smoothing model.** `Net/VeloxLagCompensationSubsystem.cpp:409`. Fix per ruling 1: a per-controller `LastMeasuredInterpolationDelay`/time (in the timing builder's caller state or a small struct on `AVeloxPlayerController`), used when < 2 s old, else `VeloxLagCompCVars::FallbackInterpolationDelay = 0.03`; `bDelayFromProxies` stays false for both fallback branches; `view_delay_ms` shows the value.
5. **Low (M1-08) — repair attribution and the `:962` comment.** `Movement/VeloxMovementComponent.cpp:476` (`VeloxMoveRepaired ts= dt=` — no slot), `:962` ("Log-level line" without naming the engine function). Fix per ruling 9.
6. **Low (doc only, done here) — ADR 0003 §6, B13, B14 and B17 text describe a smoothing model that does not exist; §6's `MaxRewindSeconds` sentence promises 250 ms ping on that model.** Corrected by B30, B34; the body text is left as history with the amendments binding.

Accepted without change: the 32-anchor ring (0.53 s at 60 Hz, more than `MaxClientSmoothingDeltaTime`); the SCT lower bound for the ping-pong case; the `Stamp < Newest.Stamp` reset rule; `CompletePendingSwitch` clearing `SwitchEndTime` (the shooter's own gate is local, B18); `bRetriggerInstancedAbility` on the switch (needed, ruling 4); per-script lag in `nettest.sh` with `--lag` overriding all; `ChooseExtraOldMove` eligibility (same as `ChooseOldMove`, strictly older than the chosen old move); the container's trailing 1-bit presence flag; `bJumpedThisMove` cleared in `ControlledCharacterMove`/`MoveAutonomous` (both run `CheckJumpInput` before `PerformMovement`; the replay path is `MoveAutonomous`, so a replayed take-off is flagged identically); extra move simulated via `ServerMove_PerformMovement` with type `OldMove` (no client-error check, duplicate rejected by `VerifyClientTimeStamp`).

## 3. M1-07 analysis (A35)

- **Bandwidth.** A packed move is ≈ 25–40 B (`TimeStamp` 4, `Acceleration` quantized, `Location` 12, `ControlRotation` up to 6, flags 1, optional base/mode) — the engine serialises the same fields for every move type (l.9835–9860), so the extra slot costs what A32's slot cost. Per client up: new + old + extra ≈ 100–120 B at 60 RPC/s, plus the pending half in the air (120 Hz client): ≈ 7–10 KB/s. 16 clients: ≈ 110–160 KB/s server inbound. Q3 at `cl_maxpackets 125` with `cl_packetdup 2` is in the same range. Inside the ≤ 16-player assumption (STATUS open question 6); M6 revisits the numbers with real clients.
- **Duplicates.** Two stale moves per RPC in steady state; each costs one `VerifyClientTimeStamp` compare and an early return before any movement. The Log-level engine line is formatted only when `LogNetPlayerMovement` is at Log or above.
- **Pad entries (A28/A34).** `PadRun`'s A34(iii) proof (`VeloxResend … event=1`, `old` = entry stamp, `new` = launch stamp) is unchanged: the entry move `CD` is the chosen old move of the launch move's RPC, and `CD−1` now rides in the extra slot. The launch move `E` is only `NewMove` of its own RPC and, while `CD` is unacked, is never resent (ruling 8); a lost `E` merges into the first air move with the pad knockback consumed at the start of the merged move on both ends → second order. 3/3 full-list rounds and 20/20 LatchRun confirm no regression; `PadRun` stays in the default list.
- **Self-splash move-timed events (B25).** The move at whose end the prediction was queued is an event move (`bSavedQueuedPredictedKnockback`) and wins the old-move slot; the extra slot carries the move before it, so a two-RPC burst around a rocket jump is now repaired in the original partition, the same class as M1-07's take-off. `RocketJumpRun` 0 clamps, splash `ts` equal on both ends in the 08b soak.
- **Take-off flag.** `bSavedJumpedHeld = JumpedThisMove && bSavedJumpHeld` covers tap take-offs as well (the key is down in the press frame), so every take-off is an event move; the engine's own important-move flag for the jump press is no longer needed for the slot choice.
