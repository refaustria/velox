# Design review — M2 task 03 `lag-compensation` (architect, 2026-10-25)

**Scope reviewed:** `Source/Velox/Net/VeloxLagCompensationSubsystem.h/.cpp` (new in 728cdab), `Combat/VeloxHitboxComponent.*` (registration), `GameModes/VeloxPlayerController.*` (`BuildShotTiming`), `Movement/VeloxMovementComponent.*` (`GetRenderedServerStamp`), `Tests/VeloxLagCompTest.cpp` — against ADR 0003 §5, §6, §9 and Amendments B1–B9. Engine claims verified in `/opt/UnrealEngine-5.8` (`CharacterMovementComponent.cpp`, `GameStateBase.cpp`, `LevelTick.cpp`, `World.cpp`; line numbers below).

**Verdict: accept. Nothing blocks task 04.** The two-domain design (world time for everyone, pawn stamp for the hinted pawn), the ring buffer, the live-sample newest point, the clamping and the pellet/rail collection are correct and match the ADR; the world-free split (`FVeloxHitboxHistory`, `VeloxLagComp::SelectPose/CollectRayHits`) is the right shape and the tests exercise the cases that matter. Five fixes go into a small follow-up **03b** (dev, parallel with 04; must land before 08): the ping fallback double-counts one-way latency, origin tolerance needs an eye→origin occlusion trace, the history needs a teleport discontinuity flag, NaN guards, and a `view_ms` log field for the soak. ADR 0003 gained **B10–B17** (end of the ADR). Task files 04 and 08 carry the resulting instructions under "Review notes from task 03".

## 1. Rulings on the implementer's points

| # | Point | Ruling |
|---|---|---|
| 1 | Subsystem created for every non-client world as far as the net mode is known at creation; registration gated on authority | **Accepted** (B10). `UWorld::InternalGetNetMode` (World.cpp l.9598–9675) derives `NM_Client` from the pending net game URL when no NetDriver exists yet, so in practice the client world does know; where it does not, an empty instance never ticks (`IsTickable` = entries > 0) and `RegisterHitbox` refuses client worlds and non-authority pawns. Existence is not the gate; registration is. |
| 2 | Sampling in the subsystem `Tick` at a fixed 60 Hz schedule, window 1 s / 60 samples | **Accepted** (B11). `LevelTick.cpp`: `BroadcastTickDispatch` l.1574 (remote players' moves) → `TimeSeconds +=` l.1610 → tick groups (bots/listen pawns move in `TG_PrePhysics`) → `FTickableGameObject::TickObjects` l.1821 → `BroadcastTickFlush` l.1929 (replication). A sample therefore sees every move of the frame and records exactly the pose `TickFlush` sends — the invariant the stamp hint relies on. The schedule (10 % slack, catch-up to `Now`) samples every frame at `NetServerMaxTickRate=60` and halves a 120 Hz editor server; fine. The window is **1.0 s** — that is the ADR's own value (§1 `HistoryWindowSeconds 1.0`, §6 `ceil(1.0 × 60) = 60`); the "0.5 s" in the review brief is not in the ADR. Capacity `ceil(max(Window, MaxRewind + 0.1) × 60)` keeps a slow (30 Hz) server covered for 2 s. Side fact for everyone: a fire RPC runs inside `TickDispatch`, i.e. with `Now` = the *previous* frame's `TimeSeconds` (l.1574 precedes l.1610); the live sample's clamp `WorldTime = max(Now, Newest.WorldTime)` keeps the history invariant and the result is still correct within one frame. |
| 3 | Two domains as implemented: `ViewServerTime` in world time; stamp = `ServerLastTransformUpdateTimeStamp`, equal-stamp runs → newest sample | **Accepted, including the idle→move edge case** (B12). Derivation in §3 below: the discrepancy is bounded by one sample's displacement (≤ 2 cm from a standing start under Q3 ground acceleration, ≤ 23 cm only for a knockback/pad launch from rest at 1400 cm/s) for at most one smoothing delay after the start, and it occurs in a regime where the client's own render is a lerp through poses that never existed. Recording the always-advancing `ServerAccumulatedClientTimeStamp` instead would give the same bound and lose the exact at-rest answer; clamping has nothing better to clamp to. No change. |
| 4 | Interpolation-delay estimate: mean of `(SmoothingServerTimeStamp − SmoothingClientTimeStamp) + Age` over moving proxies; fallback `ping/2000 + NetworkSimulatedSmoothLocationTime`; implementer suspects a double count | **Proxy estimate confirmed, fallback suspicion confirmed, ADR §6 corrected** (B13). `AGameStateBase::GetServerWorldTimeSeconds()` = client time + `ServerWorldTimeSecondsDelta`, where the delta is the running mean of (replicated server time − client receipt time) (`GameStateBase.cpp` l.144–192): it already lags true server time by one-way latency plus ≤ one frame of staging. The rendered pose of a proxy sits at server time `GetServerWorldTimeSeconds() − Age − (SST − SCT)` (+ staging), so the proxy formula is exact up to staging. The fallback adds half the RTT a second time. Correct fallback: `NetworkSimulatedSmoothLocationTime + 0.5 / SampleRateHz` — the first term is the Linear smoother's steady-state lag (see §3: `MinOffset = SmoothNetUpdateTime` in `SmoothCorrection` l.8305–8309 makes the client settle exactly 0.1 s behind after any idle ≥ 80 ms), the second the expected age of the last update. Low impact (the fallback only triggers when no proxy is moving) — 03b. |
| 5 | Hint = nearest simulated proxy whose rendered capsule the ray hits, with no world hit in front; stamp = `GetRenderedServerStamp()` | **Accepted** (B14). A wall in front of the nearest candidate is in front of the farther ones too, so one trace suffices. Known residual, not fixable on either side: Linear smoothing restarts a lerp towards the newest server pose on every update, so at a direction reversal the rendered path cuts the corner by up to ≈ v·D/2 (≈ 30 cm at ±600 cm/s, D = 0.1 s) for ≈ D; the stamp names the true trajectory point. The soak's 9/10 and the 37.5 cm radius absorb it. |
| 6 | `TraceShot`: origin snap at 75 cm to the server eye; world `LineTraceSingle` on `Weapon` per pellet, then `RayPose` against rewound poses; pellets merge per pawn; rail up to `MaxPenetrations`; shooter excluded | **Accepted with one addition** (B15): an eye→origin occlusion trace (defect 2). Everything else is the ADR's step list. Note for M3: pickups and other non-world actors must set `Weapon` to `Ignore`, as pawns and projectiles do, or they will eat shots. |
| 7 | Security / correctness sweep | See §2 and §4. Rewind beyond `MaxRewind` is impossible in both domains (`SelectPose` clamps world time; `PoseAtStamp` rejects a pose older than `Now − MaxRewind` and falls through). A hint for an unseen pawn only chooses *when* that pawn is tested; the ray and the server world trace still decide. The residual exposure of any client-timed lag compensation remains: a cheat may pick any pose of a target within the last 250 ms, i.e. elongate the hit volume by ≤ 250 ms × speed — accepted by the ADR, genre standard. |

## 2. Defects, ranked (file:line → fix). All go to task 03b unless marked otherwise.

1. **Medium — ping fallback double-counts one-way latency.** `Net/VeloxLagCompensationSubsystem.cpp:371–377`. Replace `HalfPing + NetworkSimulatedSmoothLocationTime` with `GetDefault<UVeloxMovementComponent>()->NetworkSimulatedSmoothLocationTime + 0.5f / UVeloxLagCompensationSubsystem::SampleRateHz`; drop the `PlayerState` lookup. Fix the header comment at `.h:101` and the ADR text (done, B13). Over-rewinds resting-then-starting pawns by ~RTT/2 today.
2. **Medium — 75 cm origin tolerance lets a client fire from behind a wall edge.** `.cpp:616–627`. After the distance check, when the client origin is kept (not snapped), `LineTraceSingleByChannel(Eye → Request.Origin, Velox_TraceChannel_Weapon, ignore shooter)`; on a block, snap to the eye and log `VeloxShotOriginSnap … reason=occluded`. One extra trace per shot, none when the origin equals the eye within 1 cm (skip the trace then). `LagCompTrace` gets a case: origin 50 cm behind the test wall → snapped.
3. **Medium — pose interpolation across a teleport produces a mid-air capsule for one sample interval.** `.cpp:80–98` (`LerpPose`), `.cpp:541–581` (`SampleAll`), `.h:27–32` (`FVeloxHitboxSample`). Per B16: `bool bDiscontinuity` on the sample, set in `SampleAll` when the first shape's centre moved more than `UVeloxCombatSettings::HitboxTeleportDistanceCm` (new field, default 150; the maximum legitimate displacement per sample is ≈ 42 cm at 2500 cm/s and 60 Hz, 84 cm at 30 Hz) from the previous sample; `PoseAtWorldTime`/`PoseAtStamp` pass the flag of the *later* bracketing point to `LerpPose`, which then returns the nearer-in-time pose instead of lerping. `MakeLiveSample` computes the flag the same way against `Newest`. Do **not** reset the history: a shot fired at the pre-teleport pose within the window must still hit (Q3 teleporter semantics, M7). Clients snap beyond `NetworkNoSmoothUpdateDistance` 384 cm (CMC l.716–717), so the nearest-pose rule matches what they drew. Unit test: synthetic history with a 1000 cm jump between t = 0.5 and 0.5 + 1/60; queries at 0.5 + 0.4/60 → pre-pose, 0.5 + 0.6/60 → post-pose, same by stamp.
4. **Low — no NaN guards on client-supplied vectors.** `.cpp:617–621` (`Origin`), `.cpp:681` (`Dir`). `Request.Origin.ContainsNaN()` → treat as out of tolerance (snap, `reason=nan`); `RawDir.ContainsNaN()` → skip the ray like a zero direction. `ViewServerTime`/`HintTargetStamp` already degrade safely (`Clamp(NaN)` yields `Now`; `PoseAtStamp(NaN)` returns false → world time), verified by reading; task 04 additionally rejects non-finite target data at `NetSerialize` (shot dropped, `VeloxShotRejected reason=invalid`).
5. **Low — the soak cannot measure the world-time estimate against the stamp path.** `.cpp:704–708` (`VeloxShot` line). Add `view_ms=%.1f` = `(Now − ClampedViewTime) × 1000` next to `rewind_ms`; keep `rewind_ms` as is (the hinted pawn's actual rewind when `hint=stamp`). B17 defines the 08 assertion `|rewind_ms − view_ms|`.
6. **Low — `HistoryCapacity` is read from the settings CDO, not the configured asset.** `.cpp:438–444`. Accepted as is: capacity only needs to cover `MaxRewind + slack`, and the subsystem initialises before any PlayerState exists. Document in the header comment; `MaxRewindSeconds`/`MaxOriginErrorCm` come per request from the shooter's PlayerState settings (B1) — task 04 must call `Request.ApplySettings(PS->GetCombatSettings())`.
7. **Info — `HintMode = Stamp` is reported for a pawn with no history yet** (just registered; `PoseAtStamp` with only the live point). Correct by the documented rule "stamp at or beyond the newest point gives the newest point", `rewind_ms = 0`. No change; the 08 assertion tolerates it (the dummy has a full history).
8. **Info — `VeloxShot` at `Log` level is 320 lines/s with 16 players on the LG.** Keep for M2 (08 parses it); M6 drops it to `Verbose` and the nettest raises it with `-LogCmds`.

## 3. Engine facts and derivations behind the rulings

- **Linear smoothing's steady-state lag is `NetworkSimulatedSmoothLocationTime` (0.1 s), reached indirectly.** `SmoothCorrection` l.8296–8313: on the first update `SCT = SST`; afterwards `SCT` is clamped to `[SST − MaxDelta, SST]` with `MaxDelta = clamp(ServerDelta × 1.25, MinOffset = SmoothNetUpdateTime, MaxClientSmoothingDeltaTime)`. `SmoothClientPosition_Interpolate` l.8405–8436: `SCT += dt`; when the lerp completes with velocity ≈ 0, `SCT = SST`. Consequences: a pawn that has moved since its first replication without stopping is drawn with lag ≈ 0 (snapping); any stop ≥ 80 ms followed by movement gives one update with lag `min(idle × 1.25, 0.5)` and then a steady 0.1 s, which nothing reduces until the next stop. So the proxy measurement `(SST − SCT) + Age` is what has to be used (it tracks all three regimes) and 0.1 s is the right expectation when no proxy is moving.
- **Idle→move edge case (B12).** Server history around a start at frame k+1: `(W_k, S0, rest)`, `(W_{k+1}, S0 + idle, pose1)`. The client's first moving update carries `SST = S0 + idle`, `SCT ∈ [S0 + idle − min(idle × 1.25, 0.5), S0 + idle]`. `PoseAtStamp` maps such an `SCT` to alpha `(SCT − S0)/idle` between rest and pose1 — ≥ 0.83 for idle ≥ 3 s, i.e. ≈ pose1, while the client draws a point between rest and pose1. Error ≤ |pose1 − rest| = one frame of movement, for ≤ 0.5 s, then the regime is steady. Before the moving update arrives the client renders rest with stamp `S0` and the server resolves the newest `S0` sample = rest — exact. After the client's stop-lerp completes the client's `SCT` snaps to `SST`, which the server resolves to the newest sample of the equal-stamp run = the live pose — exact.
- **Stamp float precision is a non-issue.** The remote-player stamp domain is `ServerAccumulatedClientTimeStamp` of the CMC's server prediction data (CMC l.3154, l.12587), created per movement component, i.e. per pawn life; bot/listen stamps are world time, reset per map. Within a 2 h life the float resolution is ≤ 0.5 ms against 16.7 ms sample spacing. Client `SmoothingClientTimeStamp` is set from the replicated float and compared as float on the wire — round-trip exact, which the equal-stamp rule needs.
- **Dead/unregistered pawns in the same frame.** Task 06 unregisters in `HandleDeath` (synchronous in `OnOutOfHealth`, B8); a later shot in the same frame finds no entry and the corpse is transparent. A rail through two pawns applies two specs; the first kill cannot affect the second (`ScratchCandidates` is built before damage is applied). Deliberate difference from Q3, where `MASK_SHOT` includes `CONTENTS_CORPSE` (B17 records it).
- **Sample-less pawns.** `MakeLiveSample` is always the newest point, so a pawn registered this frame is hittable at its spawn pose by both domains; `RewindMs` reads 0.
- **Performance.** Per shot: `Entries.Num()` × (one reverse scan of ≤ 15 samples + one 1-shape lerp) + `Dirs.Num()` × (one world line trace + ≤ 16 ray–capsule tests). Allocations: none after the first shot for ≤ 1 ray, ≤ 4 hits (`TInlineAllocator`); a shotgun's 11 rays heap-allocate `Rays` once per shot (≈ 1 KB) — acceptable, or raise the inline count to 12 in 03b for free. Sampling: 16 × 60 Hz capsule copies into pre-sized slots, no allocation. Client `BuildShotTiming`: one `TActorIterator<ACharacter>` and one line trace per shot. Within the ADR §10 budget.
- **Tests.** `LagCompRewind` covers both domains, clamps, hint fall-through, equal-stamp runs, the ADR's "hits rewound, misses current" ray; `LagCompHits` covers nearest/penetration/world-block/pellet merge/sort; `LagCompTrace` covers registration, sampling in a ticked world, `TraceShot` hit/miss/LagComp-0/exclusion/snap/world block/unregister. The stamp path is not exercised end to end in C++ (unpossessed characters never run `PerformMovement`, so their stamps stay 0); the 08 soak is where `hint=stamp` is proven — hence B17's assertions.

## 4. Checked and found correct (no change)

- Window clamping in both domains, including `MinWorldTime` on the stamp path and the fall-through order (stamp first, world time second, `Current` only without history and live).
- Live-sample invariants (`WorldTime`, `PawnStamp` never below the newest sample), `SampleAll`'s once-per-frame guard and monotonic stamp clamp.
- Ring semantics (`Head`/`Count`, `Get(0)` oldest), `Init` minimum 2, slot reuse without allocation.
- `CollectRayHits`: `Dist < WorldDist` strict, nearest first, non-penetrating ray end at the pawn with `ImpactNormal = −Dir`; `SortHits` index remap.
- `GetRenderedOffset` (mesh vs unsmoothed attach point) is the Linear-mode offset; capsule yaw-only so rotation is irrelevant.
- Registration: authority + non-client, duplicate-safe; `EndPlay` unregisters; stale weak pointers are swept in `SampleAll` and `UnregisterHitbox`.
- `velox.combat.LagComp 0` yields current poses and `rewind_ms 0`; shipping builds compile the cvars out.
- `BuildShotTiming` on a listen host returns `Now`, no hint — the server's poses are what is drawn (within the host's own 40 ms smoothing; not a shipping configuration).
