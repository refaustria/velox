# Design review — M2 task 04 `weapons-hitscan` (architect, 2026-10-25)

**Scope reviewed:** `Source/Velox/Weapons/*` (new in 12a5221), `Combat/VeloxAbilitySystemComponent.*` (event-data activation, fire routing), `Combat/VeloxGameplayAbility.h` (`PrepareInputActivation`), `Combat/VeloxGameplayEffects.cpp` (B5), `Combat/VeloxCombatSettings.*` (`WeaponTable`, `SpawnLoadout`), `Combat/VeloxGameplayCueManager.*`, `Character/VeloxCharacter.*` (cue forwarding), `GameModes/VeloxPlayerController.*` (`ClientConfirmHit`), `GameModes/VeloxPlayerState.*` (inventory, `ResetToLoadout`), `Tests/VeloxWeaponTests.cpp`, `Tools/editor/create_bootstrap_content.py` (weapon section) — against ADR 0003 §1, §4, §5, §9 with amendments B1–B17 and ADR 0002 A17/A24/A32/A33. Engine claims verified in `/opt/UnrealEngine-5.8` (`GameplayAbilities` plugin and `GameStateBase.cpp`; line numbers below).

**Verdict: accept the structure; four Must-fix items go to follow-up 04b (dev-hard, ~2–3 h) and one to 04c (dev-hard, ~1 h) before task 09. Nothing blocks 05, 06 or 07; 08 should start after 04b.** The data-driven weapon set, the bitmask inventory with granted fire abilities, the target-data flow, the server resolution through `TraceShot`, the native cue path and the event-data activation hook are the ADR's design and are correctly wired to GAS prediction (details in §4). What needs fixing is timing enforcement: the client can bank one full fire interval and double-tap, the server bucket admits three simultaneous shots, the server trusts the client's switch timing entirely while the client itself is gated by a tag that arrives one RTT late, and the client chooses the pellet-pattern seed. ADR 0003 gained **B18–B24** (end of the ADR).

## 1. Rulings on the implementer's seven departures

| # | Departure | Ruling |
|---|---|---|
| 1 | Server ignores `WeaponSwitching` and `NextFireTime` for remote shooters, accepts the pending switch target; only the bucket applies | **Fix** (B18). The premise is wrong: the switch RPC and the fire RPC travel the same path, so the server's switch timeline is shifted by the same one-way latency as the shot — only jitter and the reliable-resend compression after a lost packet (≤ 1 RTT) remain. Rule: the server accepts a shot while `GE_WeaponSwitching` has ≤ `SwitchTimingToleranceSeconds` (new, default 0.25) remaining, and a shot of the *pending* weapon within that tolerance finalises the switch (`SetCurrentIndex(Pending)`); outside it the activation fails as any blocked activation does. `NextFireTime` stays unchecked for remote shooters — the bucket plus the new minimum spacing (B19) replace it. The other half of the fix is on the client, see defect 3. |
| 2 | MG fires one ray with Q3 `Bullet_Fire` spread (1.4°); the 03 review said "one entry = Dir for MG" | **Accepted — the ADR is right and my 03 note was wrong** (B20). ADR §4 lists `MG … spread atan(200/8192)`; `FVeloxHitMath::BulletSpreadDirection` is Q3's `r = random()·2π; u = sin(r)·crandom()·spread; r = cos(r)·crandom()·spread`. Keep. `SpreadAngleDeg = 0` remains the way to get a laser MG for tests. |
| 3 | `NextFireTime` carries the remainder (Q3 weapon time) instead of `Now + Interval` | **Principle accepted, bound fixed** (B19). Q3 `PM_Weapon` decrements `weaponTime` only while it is positive, so the carried remainder is at most one frame's `msec`. `AdvanceNextFireTime` carries up to one full interval (`Now − NextFireTime < Interval`): fire at scheduled + 1.49 s, then again 10 ms later — two rails 10 ms apart, repeatable by rhythm (defect 1). Carry only when `Now − NextFireTime ≤ FrameDt`. |
| 4 | Client ends each shot without an end RPC; `bRetriggerInstancedAbility` as safety net | **Accepted** (B22). `bServerRespectsRemoteAbilityCancellation = false` makes a client end RPC pointless anyway. Retrigger on the server ends a stuck instance with `bReplicateEndAbility = true` (`AbilitySystemComponent_Abilities.cpp` l.1841–1844) → one `ClientEndAbility` RPC to a client instance that is long gone; harmless. |
| 5 | One heap allocation per shot for the target data | **Accepted** (B22). `FGameplayAbilityTargetDataHandle` owns `TSharedPtr`s; Lyra pays the same. `Request.Dirs`, `Result.Rays`, `Proxies` use inline allocators as required. |
| 6 | Weapon content in `create_bootstrap_content.py`, bucket test in `VeloxWeaponTests.cpp`; `docs/content-bootstrap.md` not updated | **Code placement accepted; the doc is owed** (04b checklist). The bootstrap script derives every number from Q3 units (`q3_spread_deg`, `Q3_UNIT_CM`) — good; the doc has no weapon section at all. |
| 7 | `velox.combat.FireTest [AimDistanceCm]` semantics; drives the real input path on a network client | **Accepted.** Non-shipping, useful for 08/09. |

## 2. Defects, ranked (file:line → fix). Must-fix items go to 04b unless marked 04c.

1. **Must-fix — fire-time carry of up to one interval (double-tap).** `Weapons/VeloxGameplayAbility_Fire.cpp:148–152` (`AdvanceNextFireTime`). Replace the condition with `Now − NextFireTime ≤ FrameDt` (`World->GetDeltaSeconds()`), i.e. Q3's one-frame carry. Make it a world-free static (`VeloxFireTiming::AdvanceNextFireTime(Next, Now, Interval, FrameDt)`) and test: held fire at 60 Hz keeps the exact rate for 1200 shots; a shot 1.49 s after the schedule of a 1.5 s weapon restarts (`Now + Interval`), so the following shot is 1.5 s later; a shot inside the crossing frame carries.
2. **Must-fix — server bucket admits three simultaneous shots.** `Weapons/VeloxFireRateBucket.h:21–45` (`TryConsume`). The bucket is full at first use and after any idle ≥ 3 intervals, so a cheat client fires three rails in one frame (300 damage), then runs dry — the *average* rate is bounded, the *burst* is not; the client-side fix (defect 1) does not bind a modified client. Add a minimum spacing on receive time: `MinSpacing = max(0, Interval − FireRateSpacingTolerance)` with `UVeloxCombatSettings::FireRateSpacingTolerance` (new, default 0.25 s — one RTT of reliable-resend compression at the ADR's 250 ms limit): rail 1.25 s, SG 0.75 s, RL 0.55 s, MG/PG/LG 0 (bucket only). Reject when `Now − LastAccepted < MinSpacing` (`reason=spacing`). Test rows: three rails at `t = 10.0` → 1 accepted; rail at `t + 1.3` accepted, at `t + 1.2` rejected; the existing LG jitter row unchanged.
3. **Must-fix — switch timing: server bypass and RTT-late client gate.** Server side `Weapons/VeloxGameplayAbility_Fire.cpp:88–101` (`CanActivateAbility`, pending accepted unconditionally), `:128–146` (`DoesAbilitySatisfyTagRequirements`, tag ignored) → instant switch for a modified client, and because the bucket is per weapon instance, every switch also brings a fresh full bucket. Client side: `GE_WeaponSwitching` is predicted, then replaced by the server's replicated copy, which the client re-anchors to `StartWorldTime = Now − (ServerTimeEstimate − StartServerWorldTime)` (`GameplayEffect.cpp` l.2952–2955, called from `PostReplicatedAdd` l.2848); `ServerTimeEstimate` lags true server time by one-way latency (B13) and the server applied the GE one-way latency after the press, so the client's tag ends **one RTT** after its own timeline (100 ms at the test latency, 250 ms at the ADR's ping limit). That is exactly the re-anchoring the ADR §5 forbids for fire rate, now on every switch. Fix per B18: (a) remove `State_WeaponSwitching` from the fire abilities' `ActivationBlockedTags` and delete the `DoesAbilitySatisfyTagRequirements` override; (b) the switch ability records `Inventory->SwitchEndTime = Now + Wait + Drop + Raise` on every machine that runs `ActivateAbility` (`VeloxGameplayAbility_WeaponSwitch.cpp:55–96`), `ResetToLoadout` clears it; (c) `CanActivateAbility`: shooter's machine → `Now ≥ SwitchEndTime`; server for a remote shooter → `SwitchRemaining ≤ SwitchTimingToleranceSeconds` where `SwitchRemaining = max(ASC->GetActiveEffectsTimeRemaining(MakeQuery_MatchAnyOwningTags({State_WeaponSwitching})))`, 0 without the GE; the pending definition is accepted only under the same condition and the accepted shot calls `Inventory->SetCurrentIndex(Pending)` before resolving. Put the decision in a world-free function (`VeloxFireTiming::IsSwitchFireAllowed(bLocal, Now, SwitchEndTime, SwitchRemaining, Tolerance)`) and test it. The `Velox.Combat.Inventory` test keeps asserting "no rail during the raise" (local timeline) and gains "rail at `SwitchEndTime` fires".
4. **Must-fix (04c) — the client chooses the pellet-pattern seed.** `Weapons/VeloxGameplayAbility_FireHitscan.cpp:227` (`MakeSeed(Shot.ShotSeq, PlayerId)` from client data), `Weapons/VeloxShotTargetData.h` (`ShotSeq`). A modified client picks, per shot, the `ShotSeq` whose pattern best covers the target: the MG becomes spread-free (≈ 2× hit rate at 20 m), the SG lands 11 pellets instead of ~5 (≈ 2× damage). Q3 draws the seed on the server and sends it in the event. Fix per B21: the server seeds from its own per-PlayerState counter (`Inventory->AllocateServerPatternSeq()` ^ `PlayerId`); the client's `ShotSeq` stays for logs and task 05's fake-projectile matching only; `FVeloxGameplayEffectContext` gains `uint8 PatternSeq` (one byte); impact cues become server-only (executed inside `FScopedPredictionWindow(ASC, FPredictionKey(), false)` so the owner receives them), the owner predicts the fire cue only, and `PlayLocalShotCosmetics` (`:326–405`) drops the per-pellet impact loop. M5 receivers rebuild the pattern from `PatternSeq`, context origin and `HitDirection`.
5. **Should-fix (04b) — beam keep-alive is a magic number and too short for loss.** `Weapons/VeloxWeaponInventoryComponent.cpp:327` (`2.5f * Interval` = 125 ms). A reliable resend after a lost packet delays the next LG shot by one RTT, so the beam flickers off at ≥ 125 ms RTT. `UVeloxCombatSettings::BeamKeepAliveSeconds` (default 0.25, cvar mirror, bootstrap field) — B23.
6. **Should-fix (04b) — the server validation path is not unit-testable.** `Weapons/VeloxGameplayAbility_FireHitscan.cpp:145–201` (`OnServerTargetData`, needs a remote actor info). Move the checks into a world-free `VeloxShotValidation::Validate(const FGameplayAbilityTargetData* Raw, FVeloxFireRateBucket&, Now, Interval, Capacity, SpacingTolerance) → EVeloxShotReject {None, Type, Rate, Spacing, Origin, Dir, Time}` and test every reason (wrong struct, NaN origin, zero and NaN dir, ±inf view time, NaN stamp, over-rate, under-spacing). The `HitscanDummy` test exercises only `ResolveServerShot`.
7. **Should-fix (04b) — `docs/content-bootstrap.md` lacks the weapon section** (departure 6): `DA_Weapon_*`, `DA_WeaponTable`, `weapon_table`/`spawn_loadout`, the Q3-unit derivation, the new settings fields of 04b.
8. **Should-fix (M5) — string work per cue.** `Weapons/VeloxCombatFeedbackComponent.cpp:29–30` (`CueTag.ToString()`, `EndsWith` per cue, 20 Hz per LG shooter per client, also in shipping for the beam state). Resolve the weapon by cue tag through the table once (`UVeloxWeaponTable::FindByCueTag`) or compare against native tags. The M5 FX pass rewrites this component; note for its author.
9. **Should-fix (09 feedback) — a switch cannot be redirected while running.** `VeloxGameplayAbility_WeaponSwitch` is InstancedPerActor without retrigger, so a second slot press during drop/raise fails on both sides (consistent, no desync). Q3 lets you change the target mid-switch. Decide after the 09 playtest; if wanted, retrigger with the remaining drop time kept.
10. **Nit — `EVeloxHitConfirmFlags` is a namespace with an enum prefix.** `GameModes/VeloxPlayerController.h:12–17`. `namespace VeloxHitConfirmFlags` or `enum class EVeloxHitConfirmFlags : uint8` + `ENUM_CLASS_FLAGS`.
11. **Nit — no finite guard on the switch event magnitude.** `VeloxGameplayAbility_WeaponSwitch.cpp:60` (`RoundToInt32(EventMagnitude)`); a NaN yields an implementation-defined int that `OwnsIndex` rejects, but guard it explicitly.
12. **Nit — `VeloxShotRejected` at `Log` is unthrottled.** `VeloxGameplayAbility_FireHitscan.cpp:137–143`. A hostile client can write one line per RPC; after N rejections per second per shooter drop to `Verbose` (08 counts rejections, so keep the first ones at `Log`).

## 3. Interaction with lag compensation (03/03b) and the join transient

- Call sequence matches the 03 review step list: `BuildShotTiming` once with the centre ray also for the SG (`FireHitscan.cpp:79`), hint copied with `bHasHint = HintTarget.IsValid()`, server `Request.ApplySettings(PlayerState settings)` (B1), `ViewServerTime/HintTarget/HintTargetStamp` from the target data, `bValidateOrigin` left true, pellets from the server's own stream, no second shot log line. Correct.
- **`view_ms=250 hint=fallback` ≈ 1 s after join** (report hand-off): two engine transients, both expected. (a) `AGameStateBase::OnRep_ReplicatedWorldTimeSecondsDouble` (`GameStateBase.cpp` l.164–193) keeps a running mean of `Replicated − ClientWorldTime` (reset every 250 samples) and half-steps towards it; the first sample is taken during the client's load frame, where the client clock and the replicated value are inconsistent by the load time, and its weight decays only as 1/N (10 samples after 1 s). (b) The proxies' Linear smoothing starts with `SmoothingClientTimeStamp = SmoothingServerTimeStamp` on the first update and can sit up to `MaxClientSmoothingDeltaTime` (0.5 s) behind for one update cycle, which puts the hinted stamp outside `MaxRewind` → `fallback` by B12's rule. Neither is a weapons defect. Rule for 08 (B24): shots in the first 5 s after possession are logged and reported, not judged; `VeloxShotFired` carries `view_delay_ms` and `server_est`; judged shots must satisfy B17 unchanged.
- Origin handling: the client sends `GetPawnViewLocation()` as `FVector_NetQuantize100` (1 cm), the server snaps beyond 75 cm, on NaN and on eye→origin occlusion (03b). `Dir` as `FVector_NetQuantizeNormal` is ≈ 0.006° coarse (1 cm at 100 m) — fine.
- A hint for the shooter's own pawn, a destroyed actor or a non-pawn is harmless: `TraceShot` excludes the shooter and the hint only chooses *when* that pawn is tested (03 review §1.7).

## 4. Checked and found correct (no change)

- **Target data and prediction keys.** `ServerSetReplicatedTargetData_Implementation` opens `FScopedPredictionWindow(this, CurrentPredictionKey)` before broadcasting (`AbilitySystemComponent_Abilities.cpp` l.4007–4030), so the server's `GE_AmmoCost` and fire cue in `OnServerTargetData` carry the client's activation key: the predicting client's infinite-duration stand-in for the predicted Instant GE (`AbilitySystemComponent.cpp` l.1066, l.1113–1116) is removed on catch-up or rejection (`GameplayEffect.cpp` l.4527–4532) and the owner skips the keyed cue multicast. A `rate` rejection ends the server ability without `GE_AmmoCost`; the client's predicted −1 is removed at catch-up and ammo re-syncs — the ADR's intended behaviour. Reliable ordering on one actor channel guarantees activation before target data; a client that never sends target data leaves an instance active until the next activation retriggers it (l.1836–1845).
- **Switch rejection rollback.** `ClientActivateAbilityFailed_Implementation` broadcasts the rejected key (predicted `GE_WeaponSwitching` removed) and `K2_EndAbility`s the instance with that key (l.2279–2330), cancelling the `WaitDelay` task before `OnDropFinished` — no stale predicted index unless latency exceeds Wait + Drop, and then the 1 s `PredictionTimeout` reverts it.
- **Beam replication under Mixed mode.** `ActiveGameplayCues` replicates with `COND_None` (`AbilitySystemComponent.cpp` l.1852–1854), simulated proxies' `FActiveGameplayCue::PostReplicatedAdd` invokes `WhileActive` unless the key is a local client key (`GameplayCueInterface.cpp` l.299–302), and the unkeyed server window (`GameplayPrediction.cpp` l.387–406) makes the owner receive it too. `OnRep_PlayerState → InitAbilityActorInfo` runs for every role (`VeloxCharacter.cpp:197–231`), so proxies have an avatar to handle cues. Correct.
- **Fire specs reach the owning client.** `FGameplayAbilitySpec::SourceObject` is a plain `UPROPERTY()` (`GameplayAbilitySpec.h` l.209–211; the `NotReplicated` one at l.89 is `FGameplayAbilitySpecDef`), `ActivatableAbilities` is `COND_ReplayOrOwner` (l.1861) — `CanRouteInputToSpec`, `FindFireSpec` and `GetDefinition` work on the owner, as the agent's network `ClientFireTest` confirmed.
- **Server-local activation.** `FGameplayAbilityActorInfo::IsLocallyControlled` (`GameplayAbilityTypes.cpp` l.107–127) is true for the listen host and for AI-controlled bots, so `IsServerForRemoteShooter` routes them to the direct path with `ViewServerTime = Now` and no hint (review step 6).
- **Event-data activation.** `InternalTryActivateAbility(Handle, {}, nullptr, nullptr, &EventData)` sends `ServerTryActivateAbilityWithEventData`; the server validates `OwnsIndex(TargetIndex)` and a real change; `EventTag` is not trusted for anything. `PrepareInputActivation` on the CDO with the pressed tag is a sound pattern for multi-tag abilities (B22). Press+release in one frame fires a `WhileInputActive` ability once (Q3 tap).
- **Inventory.** `OwnedMask` owner-only, `CurrentIndex` to everyone (M5 view models), `PendingIndex` server-only, specs granted once per weapon with `SourceObject = Def` and dynamic `InputTag.Fire`; `ResetToLoadout` keeps surviving specs, removes the rest, selects the first loadout entry and runs before `GE_SpawnInit` (`VeloxPlayerState.cpp:77–81`), so ammo and weapons have one source (B5). `AddWeapon` adds ammo through a negative `GE_AmmoCost` — right for M3 pickups. `CycleOwned` is world-free and tested.
- **Validation order and guards.** Bucket first, then struct type, `Origin.ContainsNaN`, `Dir` NaN/zero (normalised otherwise), `IsFinite(ViewServerTime)`, `IsFinite(HintTargetStamp)`; a huge finite `ViewServerTime` is clamped by `TraceShot`; nothing touches the subsystem on rejection. `NetSerialize` drops the hint without a package map and writes one bit otherwise.
- **Cues on the dedicated server** are suppressed by the engine (`GameplayCueManager.cpp` l.180–183) and the manager loads no libraries there; the test world is a game world, so the feedback assertions in `HitscanDummy` are valid.
- **Damage application.** One `MakeDamageSpec` per victim with `PelletHits` (Q3 per-pellet armor rounding, B2), remaining hits applied after a kill (B8/B17), `ClientConfirmHit` with health+armor delta clamped to 255 and the kill flag — 3 bytes, unreliable.
- **Data.** `DA_WeaponTable` carries exactly the ADR §4 numbers in slot order; `WeaponTable` test asserts them including the two Q3 spreads; `GetSpawnAmmo` sums the loadout; the class-default settings carry no loadout (asset required), which `GetOrDefault` handles.
