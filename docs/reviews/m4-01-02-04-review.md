## 2. Input-path fidelity, determinism, and the engine behind the bot

**Does the bot truly go through the player's path? Yes; no server-authority shortcut found.** Verified chain: `AVeloxBotController::Tick` (TG_PrePhysics) → the pawn and its CMC tick after the controller (`AController::SetPawn` → `AddPawnTickDependency`, Controller.cpp:539/495: a prerequisite on the CMC's tick and on the pawn's tick) → `UCharacterMovementComponent::TickComponent` runs `ControlledCharacterMove` because an AI controller on the authority is a local controller → `CheckJumpInput` consumes `bPressedJump` set by `Jump()` inside `AVeloxCharacter::SetJumpInput` (:618–633, the one jump entry point for players and bots), `ScaleInputAcceleration(ControlInputVector)` consumes the `AddMovementInput` vector exactly as the listen host's `PlayerTick` path does, `SetLocalMoveInput` receives the (forward, right) key presence the player's `Input_Move` passes (:586). Abilities: `AbilityInputTagPressed/Released` + `ProcessAbilityInput` (`VeloxAbilitySystemComponent.cpp:33–106`) with the `State_Dead` gate, after the rotation update and before the pawn moves (B6) — the fire ability then takes the authority-local path with `GetControlRotation()`/`GetPawnViewLocation()`. The control rotation is written by `SetControlRotation` + `FaceRotation` (the player's `UpdateRotation` equivalent); `UpdateControlRotation` does not call `Super`, so the engine's focus/pawn-yaw/zero-pitch logic never runs. Greppable: no `Velocity =`, `Launch`, `RequestDirectMove`, `SetActorLocation`, `StopMovementImmediately` in `Bots/`; the only `Velocity` uses are two reads for the steering input (follower :321, :425). The one place the *engine* could have written velocity behind the bot — `OnPathFinished` → `StopMovementKeepPathing` on abort/finish — is off because `ShouldStopMovementOnPathFinished()` requires `!UseAccelerationForPathFollowing()` (:623–626) and Velox sets `bUseAccelerationForPaths = true`; `AAIController::StopMovement` is `AbortMove` only (:817–823). The FT harness's `SetActorLocationAndRotation` + `StopMovementImmediately` (`VeloxBotFunctionalTest.cpp:458–462`) places the pawn at the corridor start before unfreezing the bot — a fixture, not bot code.

Inherent and accepted differences from a remote player: no saved moves, prediction or corrections (ADR 0005 Context); world-time stamps (B12); the wish magnitude is analog (`WishScale` for the arrive slowdown) where a keyboard player's is ±1 per axis — a gamepad player's input, same code path; `AAIController::OnPossess` adds a `UGameplayTasksComponent` to the pawn (AIController.cpp:514–523), which replicates by default (GameplayTasksComponent.cpp:57) — one empty replicated component per bot pawn, as on the M2 dummies; the engine's `SetMoveSegment`/`OnPathFinished` set and clear an AI "move focus" (`UpdateMoveFocus`, :1683–1697) that nothing reads because `UpdateControlRotation` is overridden. The ADR §1 acceptance wording "never reads or writes `Velocity`" was too strict — §5's `FVeloxSteerInput::Velocity` requires the read; D7 corrects the wording to "never writes".

**Determinism with the seeded stream.** Per life: `Stream.Initialize(HashCombine(MasterSeed, BotIndex, LifeCount))` (controller :314–316); `MasterSeed` is `velox.bots.Seed` when non-zero, else a `Cycles()` seed drawn once at world begin play. Every random draw of 04 goes through `Stream` (`StartRoam` :461–462); the aim model and `ChooseGoal` take the stream by reference, so 05/06 inherit this for free as long as they never touch `FMath::Rand*`. World time comes from the fixed timestep. What is *not* deterministic and is outside the bots: the spawn point (the game mode's `ChoosePlayerStart`, global RNG) — which is why the FT's Mega step ranged 2.0–11.8 s across runs with the same seed; the forced-goal FTs are robust to it by their time limits. `FPlatformTime` is used for diagnostics only. One subtlety for 05/06: the stream is shared between all consumers of a bot; the aim model will draw two Gaussians per tick, so the roam/decision draws land at different stream positions than today — still deterministic, just not comparable with 04's roam soak.

**Tick-order evidence (the report's claim) holds:** controller TG_PrePhysics, CMC `bTickBeforeOwner` with a prerequisite on the controller's tick, so the sequence within one frame is controller → CMC (`ControlledCharacterMove`) → pawn. `AAIController::Tick` calls `UpdateControlRotation` once more at its end (:62), which re-applies last tick's `State.View` before the phases run — harmless, the phases overwrite it in `ApplyInput`.
